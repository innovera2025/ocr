## P1-ocr-engine

**Decision under review:** The recommended PRIMARY OCR engine (see d-ocr-engine.md) is the right choice for Thai+English in a Dockerised CPU worker, and the OcrProvider abstraction genuinely permits swapping it.

### Lens: feasibility - REFUTED (major)

## Verdict: the engine pick survives; the *reason given for it* does not, and the port cannot deliver it.

I tried hard to kill the choice of `th_PP-OCRv5_mobile_rec` on RapidOCR/ONNX and could not. Verified against primary sources this session:
- `PaddlePaddle/th_PP-OCRv5_mobile_rec` exists on HF; RapidOCR's model list publishes `th` (泰文、英文), PP-OCRv5, **mobile only**, for onnxruntime/openvino/paddle/mnn/tensorrt, `rapidocr>=3.4.0` — §3.3's resolution box is accurate.
- RapidOCR 3.x genuinely exposes `Det.model_path` / `Rec.model_path` / `Rec.rec_keys_path` (+ `model_dir`, `rapidocr download_models`), so **D2, D4 and D12 are all implementable** — the "top adapter-blocking spike" (§12.4) is smaller than the doc fears, and offline vendored weights work.
- Output is `boxes (N,4,2)` + per-line `scores`, so `emitsLineBoxes: true` / `emitsConfidence: 'per-line'` is real.

So D1/D2 stand on their own terms. What I am refuting is the load-bearing justification and the abstraction claim.

---

### F1 (major) — The geometry that decides the whole comparison is line-level, and for Thai a line is a phrase run. The redaction requirement it is sold on is therefore unmet by *every* engine in the roster, and the port has nowhere to fix it.

`d-ocr-engine.md` §1 makes geometry the decider: *"Geometry is non-negotiable for a secure platform: redaction, field anchoring, and 'show me where this number came from' all require boxes."* R2 (§2) demands *"Per-word/line geometry"* for *"Redaction of PII"*. §8A.5 escalates it to a control: *"An engine that cannot emit boxes cannot support redaction, so the box requirement is not merely a feature preference"* — and this is what buys C2 its 14 points, which is the entire 16-point margin over Typhoon in §5.2.

But:
- PP-OCR is line-level (`emitsWordBoxes: false`, §9.5) — correctly stated.
- Tesseract is the only per-word engine (§3.6, §9.3) — **but `f-preprocessing-and-confidence.md` §1.2(c) states flatly: "A Tesseract 'word' in Thai is a phrase run."** With no inter-word spaces (§7.1), Tesseract's word boxes on Thai *are* line boxes.
- Therefore **no roster engine can produce sub-line Thai geometry.** Neither document notices that the other one proves this.
- The port has no place to put it if you obtained it. `OcrLine` (§9.2) is `{text, rawText, quad, confidence, words, script, tokens}`. `TokenSpan` is `{start, end, tokenizer}` — newmm *already gives you Thai word boundaries as character offsets*, and the contract deliberately gives them **no geometry**. There is no `charQuads`, no `TokenSpan.quad`, no `emitsCharBoxes` capability.

Failure scenario, concrete: M3 builds the PDPA redaction feature that `g-data-model.md` §5.7 already schema'd (`ExtractionField.isSensitive`, `ExtractionFieldValue.quadJson`, `DocumentAnalysis.redactionApplied`). A Thai tax invoice line reads `ชื่อ นายสมชาย ใจดี เลขประจำตัวประชาชน ๑ ๒๓๔๕ ๖๗๘๙๐ ๑๒ ๓`. The only quad available covers the whole line, so masking the national ID also masks the name field, the label, and any adjacent column the detector merged in. On a table row it destroys the row. The team then discovers the fix requires (a) CTC frame→x alignment, which needs the recogniser logits that `RapidOCR.__call__` does not return, and (b) a new field on `OcrLine` in the **domain** layer — i.e. a port change, which is exactly what §9.3's headline claim ("One new file, one registry line, **zero changes to the port**… That is the test passing") says will not be needed. The abstraction test in §9.3 passes only because it was run against three engines that all share the same blind spot.

Secondary, same class: `f-…md` **D16** adds a cumulative 3×3 `toOriginal` homography to `PreprocessResult`/`PreprocessManifest` because §2.7 rule 4 ("highlight the source span on the image") is otherwise *"unimplementable"*. `d-…md`'s `OcrPage` carries only `renderDpi` and `rotationApplied: 0|90|180|270` — no deskew angle, no crop offset, no scale. Quads leaving `OcrProvider` are in derivative pixel space with **no in-contract route back to the original page**. Doc D ships the exact version doc F declares unimplementable.

### F2 (major) — The self-declared "#1 accuracy experiment" is built on a mechanism that does the opposite of what §6 claims, and its sweep points the wrong way.

§6 point 2 / D4 / §12 spike 7: *"Thai boxes must be taller than Latin boxes… The fix lives in the detector's config (`det_db_unclip_ratio`)… the highest-leverage single tuning knob for Thai accuracy… Promoted to the #1 accuracy experiment."* Sweep `{1.5, 1.8, 2.0, 2.2}`; §9.5 says "start 1.8".

Verified from RapidOCR's own `ch_ppocr_det/utils.py` (and PaddleOCR's `db_postprocess.py`):
```python
distance = poly.area * unclip_ratio / poly.length
offset.AddPath(box, pyclipper.JT_ROUND, pyclipper.ET_CLOSEDPOLYGON)
```
This is an **isotropic** polygon offset. For a text line with w ≫ h, `distance ≈ h·r/2` — grown by the *same absolute amount* horizontally as vertically. Three consequences the doc never states:
1. **At the default it is already enormous.** r=1.5 → box height ≈ 2.5h. Going to 2.2 → ≈ 3.2h, which overruns typical Thai leading (~1.2–1.5h) and merges vertically adjacent lines.
2. **It merges horizontally.** 1.5→2.2 adds ~0.35h of reach per side along the long axis, merging whitespace-separated columns and dotted-leader fields — precisely the borderless Thai government form §7.8 names as the hard case, and the same merge that destroys the field anchors F1 is about.
3. **It shrinks the tone mark.** Verified: PP-OCRv5 rec uses `rec_image_shape [3,48,320]` — every crop is rescaled to a fixed 48-px height. A 28 % taller box means 28 % fewer pixels per glyph at the recogniser input. The knob nominated to *save* 2–5 px tone marks makes them smaller. It also silently fights `f-…md` P5's `h_line_target = 44 px` upscale (doc F concedes P5 "applies to Tesseract's constraint only" but does not connect this back to D's unclip plan).
4. **The sweep is centred below the runtime default.** RapidOCR ships `unclip_ratio = 2.0`. §9.5's "start 1.8" and three of the four sweep points therefore *reduce* box size relative to what will actually be running, while the stated hypothesis is "Thai needs taller boxes." §9.5 half-catches this ("the default is NOT a single stable number… READ the effective value at runtime") but leaves the sweep and the "start 1.8" untouched.

Net: the M2 plan's top-priority experiment will most likely measure a flat-to-negative curve and be read as "Thai tone-mark loss isn't a detection problem after all" — the wrong conclusion drawn from a correct measurement of the wrong knob.

### What I am *not* claiming
The Thai artefact, the ONNX runtime path, offline vendoring, the det⊕recogniser split, per-line boxes+scores, D6/D7/D8/D14 (NFC-only, rawText immutability, no-binarisation, no-encoding-guessing) and §7 generally all verified or held up. §0's Intel/no-arch-split correction and the fabrication guard are the strongest work in the set. The determinism claim (`deterministic: true`) is *softer* than stated — doc F's per-page `budget_ms` wall clock makes the applied preprocessing recipe load-dependent — but §1.8 fails the page rather than returning a different transcription, so I rate that minor and did not build the refutation on it.


**Safer alternative:** Keep PP-OCRv5-th on RapidOCR/ONNX as primary — that part verified. Change three things before M1 closes:

1) **Fix the geometry contract now, while it is still on paper.**
   - Add to `OcrCapabilities`: `emitsCharBoxes: boolean` and `emitsSubLineGeometry: 'char' | 'word' | 'line' | 'none'`. Set `'line'` for every current engine and say so in §2/R2: **per-word Thai geometry is unobtainable from the entire roster** (Tesseract's Thai "word" is a phrase run — f-…md §1.2(c)).
   - Give `TokenSpan` a `quad: Quad | null` (or add `charQuads: readonly Quad[] | null` to `OcrLine`), so newmm's existing character offsets have somewhere to become pixels. Nullable + capability-declared, exactly like `OcrLine.quad`, so the §9.3 no-fabrication invariant covers it.
   - Add `toOriginal: readonly [Row3, Row3, Row3]` to `OcrPage`, matching f-…md D16's `PreprocessResult.geometry`. Without it a quad leaving `OcrProvider` cannot be mapped to the original page and both redaction and click-to-source are unimplementable against the source document.
   - Implement char boxes for the PP-OCR adapter from CTC frame alignment: call RapidOCR's `TextRecognizer` directly (not `RapidOCR.__call__`) to get the logits, map argmax frame index → x-range in the 48×W crop → line quad's inverse perspective transform → page space. Validate in M2 against Tesseract per-word TSV on the *Latin* lines of the same pages, where ground-truth word boxes do exist. If the M1 spike fails, ship `emitsSubLineGeometry: 'line'` and make the over-redaction trade-off an explicit product decision, not a discovery.

2) **Replace the unclip sweep as the #1 Thai experiment with an anisotropic crop-side pad.**
   In the det⊕rec split D4 already mandates, insert a pad step between detection and `get_rotate_crop_image`: expand each quad **only along its own local short axis** by `pad_frac · h_short`, sweeping `pad_frac ∈ {0, 0.10, 0.20, 0.30}`, long axis untouched. This targets the four-register Thai stack directly, cannot merge horizontally adjacent columns, and does not perturb the detector's trained calibration. Log the resulting crop height and the implied 48-px rescale factor per line so the "fewer pixels per glyph" cost is measured, not invisible. Keep `Det.unclip_ratio` as a *secondary* experiment, re-centred on the value actually read at runtime (RapidOCR ships 2.0), sweeping **downward as well as up** — and score it on merge rate (boxes per page vs. ground-truth line count) alongside diacritic-restricted CER, so a merge-driven regression is visible.

3) **State the granularity honestly in §5.2.** C2 is worth 14 points and is the margin over Typhoon. Split it: C2a "line geometry + determinism" (which PP-OCR wins outright and Typhoon scores 1) and C2b "sub-line geometry for field-level redaction" (which **every** engine currently scores 0–1 on, including the primary). Re-run S3/S4 with C2b's points reallocated. If the recommendation still holds — and I expect it does, because C2a alone carries determinism, auditability and CPU affordability — it now holds for a reason that is true.

### Lens: security - REFUTED (major)

## Verdict

The **engine choice itself survives my lens** — and I want to say that first, because it is the half I tried hardest to break. PP-OCRv5-th on RapidOCR/ONNX in a CPU worker is the *security-preferable* option, and `m-docker-nginx-resources.md` earns it: `ocr-worker` on `ocr-internal` only, `internal: true` so Docker installs no default route (m:742, m:1624), no AI credential, no published port, `read_only: true`, `pids_limit: 512`, weights baked at build with `sha256sum -c` that **fails the build closed** when the checksums are absent (m:1490-1500), `poppler-utils` deliberately excluded in favour of in-process `pypdfium2` (m:1288). A deterministic, in-process, box-emitting, no-egress engine is exactly what you want holding the parser for attacker-supplied binaries. D1 is right, and it is right *for security reasons the document under-claims*.

**What I am refuting is the second clause: "the `OcrProvider` abstraction genuinely permits swapping it."** It does — and that is the hole. The port makes engines interchangeable peers, but the registered engines do not sit on the same side of this system's trust boundaries, and nothing in the contract expresses or enforces the difference.

### 1. The escalation policy is an attacker-controlled engine-selection primitive (primary finding)

`d-ocr-engine.md` §9.6(b) (d:1245-1255) routes a page from the deterministic CPU tier to the VLM tier when **any** of E1–E6 fires. Every one of those six triggers is computed from the uploaded pixels:

- E1 `page_confidence < 0.80`
- E3 Thai codepoint ratio < 0.5
- E5 "detector found < 5 lines but page ink coverage > 2 %"

E5 is forced by a page of engineered speckle. E3 is forced by putting Latin text on a page declared Thai. E1 is forced by degrading contrast. **The uploader therefore chooses which engine reads their document.**

That matters because of what sits on the other side:

- §8A.4 (d:759-767) records, verified from the vendor card, that Typhoon "does not include any guardrails," and that a scanned page carrying instruction-shaped text is an injection vector. `j-security-threat-model.md`:798 rates document-content prompt injection "**Near-certain at scale**."
- In Branch B the tier is `qwen-vl-gateway`, reached by `ocr-web` over `ocr-egress`, i.e. **off this box**, to a gateway whose prompt-persistence behaviour `j`:154 explicitly marks `UNVERIFIED:` (`store_prompts_in_spend_logs`), on a network `b`:1433 calls "**confirmed multi-tenant and the hop is probably plaintext**."

So the same attacker who authors the injection text also authors the blur that guarantees the page reaches the guardrail-free model, and — for a PDPA product extracting Thai National ID numbers (§8A.5) — guarantees a full-fidelity page image leaves the host. `D13` ("VLM output is a transcription candidate, never an action input") governs what happens *after* arrival. Nothing governs arrival.

**There is no gate available to build one with.** `OcrCapabilities` (d:846-858) declares only functional properties — boxes, confidence, determinism, markdown, `requiresGpu`, `maxPagesPerCall`. It has no axis for *generative*, *leaves the host*, or *guardrails*. `OcrRequest.require` (d:915-916) is `Partial<Pick<…>>` — a caller can **demand** a capability but can never **forbid** one, so `registry.select()` has no way to honour "this tenant/document class must never touch a generative or off-box engine." `k-ai-integration-and-intelligence.md` (4,806 lines) contains **zero** occurrences of "escalat", "budget", or "per-tenant" — I grepped. The gate is not elsewhere; it does not exist.

### 2. The same document family already solved this one layer down, which is the proof it is a real omission

`f-preprocessing-and-confidence.md` §1.4 (f:836-895) handles the *identical* risk class for preprocessing escalation and handles it correctly: a bounded budget ("at most ONE re-run, at most 3 Tier-2 variants, with a hard total wall-clock cap"), `budget_exceeded` → **human review, not best-effort**, structural triggers explicitly preferred over score triggers, and an instrumented **8 % trip-rate** kill-threshold. It even catches itself doing the wrong thing: *"the escalation trigger ate its own argument… branching on an uncalibrated score means the branch fires on the wrong documents."*

`d`'s engine-tier escalation is the opposite on every count: E1 is a branch on a score that §9.6(a) itself concedes is a placeholder ("until that curve exists, every threshold below is a **placeholder**"), with no budget, no per-document cap, no per-tenant cap, no trip-rate monitor, and no `budget_exceeded` → review path. The VLM pass is 1–2 orders of magnitude more expensive than the classical pass (f:§3 Branch B) and `b`:1223 warns "a vision batch can occupy a GPU long enough to visibly degrade Chat." A 500-page PDF of noise is 500 forced GPU calls against a **shared** endpoint — an availability attack on other INNOVERA products, launched from a valid upload with a valid content type. §8A.6's quotas are page-count and CPU-second; GPU-seconds and escalation count are unquotaed.

### 3. Two supporting inconsistencies that show the port is not trust-aware

- **d:1047 registers `typhoon_vlm.py` — "OpenAI-compatible client" — inside `services/ocr-worker/src/ocr_worker/engines/`**, and d:1159's contract test is "parametrised over **EVERY registered engine**." That directly contradicts `m` §2.5.3 (m:1700-1717), which rejects exactly this: *"the worker is the process that parses attacker-supplied files — it is precisely the process that must not hold a network credential… a worker with both a parser for hostile input and an outbound credential is the exact shape of an exfiltration primitive."* The abstraction's symmetry is what invites the violation: the port says the VLM is just another `OcrEngine`, so the obvious implementation puts it beside `paddle_onnx.py`. (`m` has the right answer — worker writes the render, `ocr-web` posts it — but `d` never mentions it, and `d` is the file an implementer will open.)
- **`OcrRequest` carries no tenant.** d:911 is `source: { kind, storageKey: string, contentType }` — a raw dereferenceable path — and d:918 an `idempotencyKey` with no namespace. This contradicts `g-data-model.md` K-2/`TenantScope` (*"Repository ports take a TenantScope as the first argument. **There is no overload without it**"*, g:233-236) and `j`:164 (*"the worker **re-reads** tenant and ownership from Postgres. Never trust the payload for authorization"*). Also `contentType` is caller-declared, where `j`:487 requires the **detected** type ("`detectedExt` comes from the detected type, never the supplied one"). None of these is exploitable through the port today, because the callers are tenant-scoped — but the port shape permits every one of them, and it is the artefact a second engine's author will code against.

### What would change my mind

If §9.6(b) is re-read as illustrative rather than normative, and the real routing policy is owned by `k`/`l`, this drops to minor. It cannot be: `k` has no escalation content at all, and d:1245 states the triggers imperatively with thresholds. This is the routing policy of record.

**Safer alternative:** Keep D1/D2 unchanged (PP-OCRv5-th on RapidOCR/ONNX, CPU, no-egress worker) — my lens endorses it. Fix the abstraction and the routing, before any second engine is registered (M2 / Branch B):

**1. Add a trust axis to `OcrCapabilities`** (d:846), alongside the functional flags:
```ts
readonly trust: {
  readonly generative: boolean;      // can invent text not on the page
  readonly leavesHost: boolean;      // document bytes cross the container/host boundary
  readonly guardrails: 'none' | 'vendor' | 'ours';
  readonly processorId: string | null; // named data processor for the RoPA (PDPA)
};
```
`paddle-onnx-th`/`tesseract-tha`: `{generative:false, leavesHost:false, guardrails:'ours', processorId:null}`. `qwen-vl-gateway`: `{generative:true, leavesHost:true, guardrails:'none', processorId:'<gateway>'}`.

**2. Give `OcrRequest` a `forbid` as well as a `require`** (d:915), and make `registry.select()` raise `CAPABILITY_FORBIDDEN` rather than silently choosing a wider-trust engine. Populate `forbid` from the `Organization` row, not from the caller: `{ generative?: true, leavesHost?: true }`. A tenant on a strict DPA, or a document classified as PDPA §26 sensitive, is then structurally unable to reach the VLM tier — enforced in the registry, not remembered by a use case.

**3. Give `OcrRequest` a `TenantScope`** as its first argument (matching `g` K-2), replace `storageKey: string` with an opaque, tenant-bound `StorageRef` the provider cannot forge, namespace `idempotencyKey` by `organizationId`, and make `contentType` the server-**detected** type per `j`:487.

**4. Rewrite §9.6(b) to mirror `f` §1.4's discipline, which is already proven in this doc set:**
- Split the triggers. **E4 (capability: tables/markdown requested) stays** — it is a caller-declared route, not attacker-influenced. **E1/E2/E3/E5/E6 stop escalating to the VLM entirely** and instead emit `OcrWarning` + route to **human review / quarantine**. A page with ink and no detected lines is far more likely a scan failure or an adversarial input than something a guardrail-free model should be handed.
- Attach a budget: at most `N` escalated pages per document (start N=3) and a per-tenant daily escalation cap, both decremented **in the same transaction as the job row** (the outbox/idempotency foundation is already there). Exceeding it emits `budget_exceeded` → review, never best-effort — exactly f:840's rule.
- Instrument an escalation trip rate with a kill-threshold, as f:886 does at 8 %.
- Drop E1's `< 0.80` until the M2 calibration curve exists, or replace it with f's `lowCharFrac`-style *quantity* rather than an uncalibrated score.

**5. Delete `typhoon_vlm.py` from the worker tree** (d:1047) and state in `d` what `m` §2.5.3 already decided: the VLM adapter lives **only** in `src/modules/ocr/infrastructure/providers/`, called by `ocr-web`; the worker writes the render to `ocr_file_storage` and `ocr-web` posts it. Add a dependency-cruiser/import-linter rule that fails CI if anything under `services/ocr-worker/` imports an HTTP client, so the abstraction's symmetry can never re-create the exfiltration primitive.

**6. Make `engine_version()` (d:1197) an enforced integrity check**, not a label: verify each artefact's pinned SHA-256 at `warmup()` and refuse to start on mismatch. §8A.2 already asks for this; the code sketch only hashes for display, and `docker/models.sha256` currently guards only the build, not the runtime.

### Lens: Production operations, cost, blast radius, reversibility - REFUTED (major)

I am NOT refuting the engine pick itself. On my lens, "PP-OCRv5 Thai on CPU" is the right shape: no GPU dependency (so it survives the unresolved C/D/E blocker), Apache-2.0, emits geometry, deterministic, and m-docker §4.9.2 correctly forbids putting a CUDA OCR process on the GPU that serves INNOVERA Chat — that is the single best blast-radius decision in the set. What I refute is the second half of the claim ("the OcrProvider abstraction genuinely permits swapping it") and the reversibility posture that rests on it. Three findings, in severity order.

**(1) D1 is marked reversible "easy (port)", but its own documented reversal path is blocked by three other decisions in the same estate.**
/Users/innovera/Documents/OCR/docs/architecture/m0/d-ocr-engine.md §11 D1 states reversal = "M2 CER > ~12 %; or GPU confirmed + boxes proven unnecessary", and §5.3 spells out the action: "promote Typhoon to primary, demote Paddle to a geometry-provider running alongside it." That path is not available:
- D3/Typhoon requires a GPU. /Users/innovera/Documents/OCR/docs/architecture/m0/m-docker-nginx-resources.md P5 says "GPU for OCR: **Not used.** The GPU stays dedicated to Qwen/vLLM", reversibility "hard to reverse safely", and §4.9.2 states the rule as "no OCR CUDA process on any GPU that serves INNOVERA Chat. Not 'carefully'. Not 'off-peak'." A second GPU is unbudgeted and items C/D/E are an owner blocker (d §12 blockers 1–2).
- D13 says VLM output is "a transcription *candidate*, never an action input", reversibility **hard** ("removes the audit trail the product is sold on"). Promoting Typhoon to primary means its text *is* the record — which D13 forbids.
- D13's mitigation (§8A.4 control 2) is "reconcile against the classic engine". But the S6 trigger that authorises the promotion is precisely *"PP-OCR measured bad AND Typhoon measured good"*. **The control and the trigger are mutually exclusive**: reconciling against an engine you just measured as bad is not a control.
Failure scenario: M2 runs the ≥200-page Thai corpus (§10) and PP-OCRv5-th lands above the stated gate (median CER > 5 % / p95 > 20 %). The roster remaining is Tesseract, which this document itself scores C1 = 1/5 and ThaiOCRBench full-page 0.614 (§3.6, §5.2). There is no engine. That is a milestone-scale restart arriving *after* M1 has baked model weights into the image (O7/D12, reversibility "moderate"), keyed the derivative cache on model version (f §1.6), and fit confidence maps per engineVersion. The project is carrying exactly one unbenchmarked bet with no second bet, and the docs believe they have one.

**(2) The "fallback" is not a fallback, and the failure mode it cites cannot occur.**
Tesseract is labelled FALLBACK in five places (d §1, §8, §9.1, §9.2, §9.4, D5) and its rationale in §1 is *"the network is down and we must return something with boxes"*. But D12/O7 bake the weights into the image, and the worker runs with `HF_HUB_OFFLINE=1`, `HTTP_PROXY: http://127.0.0.1:9`, and `networks: [ocr-internal]` with no egress (m §2.2). **The primary engine has no network dependency at all, so "the network is down" is not one of its failure modes.** Meanwhile there is no failover trigger defined anywhere — I grepped all 14 M0 docs; `ENGINE_UNAVAILABLE` exists as an error code (d §9.2) and nothing consumes it, and D5's "what reverses it" reads "none foreseen", so no one owns writing the policy. Worse, both providers POST to the *same* `ocr-worker` container (d §9.3: `POST /v1/recognize {engine:'tesseract'}`; m §2.2 runs one worker image at `W=1`, cpus 1.5, memory 3072M, `pids_limit: 512`). A 3am OOMKill, crashloop, or a `/scratch` volume filling takes out primary and "fallback" together — they share fate for every failure class that actually pages someone. And for the one class it *would* cover (a bad model artefact), failing over to an engine scored 1/5 on Thai emits plausible-but-wrong Thai into an audit-grade record, which for a redaction/PDPA product is worse than failing the job.

**(3) The abstraction permits swapping the code, not the *system* — and the "easy" swaps silently corrupt the auto-accept gate on money fields. This is the finding I would fix first.**
/Users/innovera/Documents/OCR/docs/architecture/m0/f-preprocessing-and-confidence.md §2.4 Step 5 defines `calibrationKey = (engine, engineVersion, modelId, scriptTag, spanKind)`. It does **not** include the backend, `renderDpi`, the detector params, or the preprocessing `pipelineVersion`. Yet:
- d §11 D2's reversal is "M1 benchmark shows Paddle ahead → native Paddle", reversibility **easy**; §12 spike 5 makes ONNX RT vs OpenVINO vs Paddle an explicit ablation; d §3.3 concedes "If M2 shows a delta, the ONNX conversion is lossy". A backend swap changing numerics is documented behaviour ([onnxruntime#20357](https://github.com/microsoft/onnxruntime/issues/20357), and the [OpenVINO EP docs](https://onnxruntime.ai/docs/execution-providers/OpenVINO-ExecutionProvider.html) on precision/optimization differences).
- `renderDpi: 300 | 400 | 600` is a **per-request** field in `OcrRequest` (d §9.2), while 300-vs-400 DPI is an M2 accuracy ablation (§10.4.ii). One calibration map is therefore serving three different score distributions today, by construction.
- D4's `det_db_unclip_ratio` sweep — called "the highest-leverage single tuning knob" and "free" (§6) — is a runtime param that is in neither the key nor the engineVersion triple.
Failure scenario, and note it is *silent*: post-M2, backend flips ONNX RT → native Paddle (a one-line change the docs call "easy"). `engineVersion` still reads `PP-OCRv5`, so `calibrationKey` is unchanged, so `calibratedP` keeps being emitted from a map fit on the *other* backend's softmax distribution. f §2.6's critical-field gate auto-accepts `grandTotal` / `vatAmount` / `bankAccountNumber` at `T_ocr = 0.98` against that stale map. Nothing alarms. The only drift detector (§2.4 Step 7) recomputes ECE **monthly** against "a rolling human-reviewed sample" — and auto-accepted fields are by construction absent from the review queue, so the monitor's sample is biased away from precisely the failures it exists to catch (selective labels). Up to 30 days of over-confident auto-accept on payment-affecting fields, with a review-rate metric that looks *better*, not worse. Note the design already fails closed correctly when it *knows* it is uncalibrated (hard gates 5/7/8 on `null`, and f §2.6 honestly budgets for the M1 review flood) — the gap is that a changed distribution does not present as `null`, it presents as a confident number.
Related, verified: m §2.2 sets `OMP_NUM_THREADS: "1"` and `ORT_INTRA_OP_NUM_THREADS: "1"` to enforce P3's `threads_per_proc = 1`. `ORT_INTRA_OP_NUM_THREADS` is not an ONNX Runtime env var, and modern Eigen-based ORT builds do not honour `OMP_NUM_THREADS`; `intra_op_num_threads` must be set via SessionOptions, defaulting to one thread per physical core ([ORT thread management](https://onnxruntime.ai/docs/performance/tune-performance/threading.html)). So the worker will spawn ~4 intra-op threads inside a `cpus: "1.5"` cgroup and eat CFS throttling, and P3's entire sizing formula rests on a setting that is not actually applied.

Sources: [ORT thread management](https://onnxruntime.ai/docs/performance/tune-performance/threading.html), [onnxruntime#20357](https://github.com/microsoft/onnxruntime/issues/20357), [OpenVINO EP](https://onnxruntime.ai/docs/execution-providers/OpenVINO-ExecutionProvider.html)

**Safer alternative:** Keep PP-OCRv5-th as primary — do not re-open the engine pick. Change four things before M1 ships.

1. **Fix the calibration key so a swap fails closed instead of lying.** Extend it to `(engine, engineVersion, modelId, scriptTag, spanKind, backend, backendVersion, renderDpi, detParamsHash, pipelineVersion)` and persist the tuple on every `EngineScore`. An unseen key yields `calibratedP = null`, which the existing hard gates 5/7/8 already handle correctly — no new gate logic, one wider key. Make a missing map a **deploy gate**: the worker image refuses to start in prod if any registered `(engine × backend × dpi)` combination it can serve has no map with `ECE ≤ 0.05`. This converts every "easy" swap in D2/D4 from a silent-wrongness path into a visible, blocking, staffable event.

2. **De-bias the drift monitor.** Add a **random 1 % audit sample of auto-accepted fields** to the human-review stream (labelled as audit, priced into the review budget) so §2.4 Step 7's ECE is estimated on an unbiased sample. Alert on the escape rate directly, not only on ECE, and page when critical-field escape exceeds the §2.6 target (proposed ≤ 0.1 %). Weekly, not monthly, for critical fields.

3. **Stop calling Tesseract a fallback until it has a written contract; and give the primary a real second bet.** Either (a) define the failover explicitly — trigger, allowed failure classes, and a hard rule that a Tesseract result on a Thai-expected page is always `flagForReview` and never auto-accepted, plus run it in a *separate* container so it does not share the primary's OOM/crashloop fate — or (b) relabel it honestly as "benchmark floor + Latin-only degraded mode" and accept that the system fails closed. Do not ship a word that implies availability cover it does not provide.

4. **Do not close M0 with an unavailable escape hatch. Make the second bet CPU-shaped.** Reconcile D1's reversal condition against P5/D13 in one place and state the truth: the Typhoon path is contingent on hardware nobody has approved. Then pick a fallback bet that survives Branch A — the two candidates already in the docs are (i) the D4 hybrid plus the `det_db_unclip_ratio` sweep (free, CPU, targets the known Thai failure mode, no new engine) and (ii) a commercial Thai API (§3.12) as a *paid escalation tier* behind the same port, which needs no GPU and no estate change. Add to M2's exit criteria: "if PP-OCRv5-th misses the gate, the named CPU-only remediation is X, costed at Y." Cost of doing this now: roughly a page of writing plus one M2 ablation already on the list. Cost of not doing it: discovering at M2 that the only documented Plan B requires a GPU the estate has explicitly refused to share.

## P2-queue

**Decision under review:** The recommended async job architecture (see h-queue-and-worker-contract.md) is safe and operable for 10-minute, 200-page, restartable OCR jobs without adding Redis in M1/M2.

### Lens: feasibility - REFUTED (major)

The substrate half of the decision survives — Postgres + `FOR UPDATE SKIP LOCKED` + UUID fencing token + content-addressed page checkpoints is a real, correct mechanism, and §4.0's polyglot argument (pg-boss/graphile-worker are Node-only; BullMQ needs a maintained client in both languages) genuinely settles "no Redis". What is refuted is the operating-envelope claim: "safe and operable for 10-minute, 200-page, restartable jobs". Three concrete defects, all verified in-file.

**(1) FATAL to the envelope — H's budget ceiling is 3x dimension J's hard ceiling, and J's enforcement mechanism turns that gap into a guaranteed DLQ loop.** `h-queue-and-worker-contract.md` §1.6 states: *"Dimension J is consistent with this document ... No conflict."* That reconciliation checked only J's database-role row and never opened J's §8.7 resource table. J §8.7 (`j-security-threat-model.md:689`) says: *"Wall time per document: **10 min** OCR + **6 min** AI = **15 min hard ceiling**", enforcement: "Job lease expiry + a supervisor kill"*, derived from J §8.2's *"**50 pages per document (hard reject at 51)** ... 50 pages x 12 s/page = 600 s = 10 minutes ... the page cap and the time budget are the same constraint expressed twice."* H §13.2 independently sets a 45-minute clamp at 25 s/page, and F caps at 200 pages/document. So the platform carries three mutually exclusive envelopes: J 50pp/15min, F 200pp, H 200pp/45min. The decision under review fuses J's "10-minute" with F's "200-page", a combination no dimension supports.
Failure scenario, using only numbers the docs already contain: a 120-page Thai scan is accepted (F/H cap). H sizes `budget_ms` = 60s + 120x25s = 51 min, clamped to 45 min, and sets `deadline_at = now() + 45min` on claim (§6.3 stmt 1). J's supervisor kills the worker container at 15 min wall clock. H's reaper pass 1 sees the expired lease, writes `state='PENDING', last_error_code='LEASE_EXPIRED'`, `attempts=2`. Reclaim → *fresh* 45-min deadline (L28's per-claim reset) → supervisor kills at 15 min again. Page checkpoints give ~36 pages of forward progress per window, so 120 pages needs ~4 windows — but `max_attempts=4` and the claim already burned one. The job reaches `DEAD` at ~1 hour with `LEASE_EXPIRED`, which §6.3 explicitly frames as *"an operator problem that belongs on the DLQ dashboard"*, having consumed a worker slot for an hour and told the customer nothing. Under load this is systematic, not incidental: every document past ~36 pages is provably impossible to complete and every one of them lands on the DLQ.
Even with J's supervisor removed, H's own arithmetic self-refutes: §13.2 admits *"a 200-page document at 25 s/page cannot finish inside a sane budget on one worker"* and hits `BUDGET_EXCEEDED` at ~page 108. §9.6 (`h-…md:2219`) classifies `BUDGET_EXCEEDED` as `"retryable": false`, so it goes terminal `FAILED` in one attempt. The entire §8 checkpoint machinery — whose stated payoff (§13.2) is *"a job that crashes at page 190 and is re-claimed gets a fresh processing budget for the remaining 10 pages"* — is reachable only via *retryable* errors and is therefore bypassed in the exact flagship scenario it was built for. Meanwhile dimension E §5.5 item 4 already designed the correct graceful path for this case (`route=SKIPPED, reason="render_budget_exhausted"`, document completes with a warning, pages 1–20 prioritised); H's §8.2 page loop has no render-budget check and never calls it, so E and H produce opposite outcomes (degraded-success vs terminal failure) for identical input. Compounding all of it: the per-page constant that every limit derives from is UNVERIFIED with a 25–50x spread across dimensions — J assumes 12 s/page (and flags *"three separate limits collapse if it is wrong"*), H assumes 25 s/page, D cites a third-party 0.5–1 s/page for RapidOCR. No page cap, budget, or replica count in this design is currently defensible.

**(2) MAJOR — statement 4a re-introduces the exact CHECK-violation defect the review claims to have removed.** The review's headline fix (§6.2) replaces `ocr_jobs_no_abort_before_run` with `CHECK (NOT (abort_requested = true AND state IN ('SUCCEEDED','DEAD')))` and adds `abort_requested = false` to statement 4b (line 1127) and reaper passes 1 and 2 (lines 1175, 1187) and, later, 4c (line 3068). **Statement 4a — complete-success — was never updated** (lines 1100–1108: it sets `state='SUCCEEDED'`, `lease_token=NULL`, `finished_at`, and nothing else). Failure: a job is RUNNING; the user cancels; `abort_requested=true` (§12.3). The worker's `stop` check happens only at page boundaries (§6.5/§8.2), so an abort landing during the final page's OCR (§13.1 budgets 45 s) or during `assemble` (60 s) + result upload is not seen — the loop has already exited on `page_no > page_count`. `finish_ok` fires 4a → `SUCCEEDED` + `abort_requested=true` → **CHECK violation, transaction aborts**. This is deterministic and permanently repeatable for that row: the result is already durable in object storage, the AI call is already billed, but the job cannot be marked done. It stays RUNNING until the 120 s lease expires, the reaper requeues it (clearing the flag) and burns an attempt; §12.3's cancel endpoint is idempotent and §12.1 has the UI showing "cancelling…" until terminal, so a user who clicks cancel again re-arms the violation. Worst case: 4 wasted attempts on already-completed work ending in `DEAD`. It also breaks the doc's own stated invariant that a completion statement *"must never be able to raise an exception on a data condition"*, R5's "0 stuck", and §12.2 rule 3 ("never abandon a paid-for AI response"). One-line fix, but it is in the single most important statement in the design and it survived a full adversarial pass.

**(3) MINOR — §6.4's chosen abort transport contradicts §12.3's listener code.** §6.4 states *"Option 1 is chosen"*: per-job channels `pg_notify('ocr_abort_v1_' || NEW.id, '')` with an empty payload, and `pg_notify('ocr_jobs_v1', '')` for wake-up. §12.3's Python still does `await conn.execute("LISTEN ocr_abort_v1")` then `json.loads(note.payload)["jobId"]` — it listens on a channel nothing publishes to any more, and would raise `JSONDecodeError` on the empty payload if it did. Separately, per-job LISTEN requires issuing `LISTEN <dynamic ident>` on the same dedicated connection whose notification generator is already being consumed by a long-lived task, which is a non-trivial concurrency constraint the doc does not address (I could not fetch psycopg's docs to confirm the exact restriction — psycopg.org returned 403 — so treat that half as unverified). Non-fatal because §12.3 correctly makes the 30 s heartbeat the guarantee and NOTIFY only an optimisation, but as written cancellation latency is 30 s, not the ≤20 s §12.1 promises.

What I could not refute, and what convinced me the substrate is right: R15 (atomic `createDocument` + `createOcrJob` in one `prisma.$transaction()`) is a genuinely decisive argument against Redis that no amount of BullMQ maturity answers; the §4.1.1 procrastinate analysis is honest and the rejection reasons (no fairness hook in `procrastinate_fetch_job_v2`, `bigserial` job ids leaking platform volume) are real; the §6.3 correction downgrading the in-flight cap from "by construction" to "statistical under READ COMMITTED" is technically correct; and §6.6's `fillfactor=70` / HOT-update reasoning for a table taking 200 progress updates per document is the right analysis and is usually missing entirely from designs like this.

**Safer alternative:** Keep Postgres and keep every mechanism (fencing token, SKIP LOCKED claim, content-addressed page checkpoints, no Redis). Fix the envelope and the two defects before M1:

1. **Reconcile the page/time envelope in one place before the first migration.** Add a single `docs/architecture/m0/limits.md` owning `MAX_PAGES_PER_DOCUMENT`, `PER_PAGE_BUDGET_MS`, `PER_DOCUMENT_WALL_CLOCK_S`, `MAX_RENDER_PAGES_PER_DOCUMENT` and `queueTtlMs`; F, H, J, E and M import it and none restates a number. Ship M1 at **J's 50-page cap** (the conservative one, and the one already wired into NGINX `client_max_body_size`, ClamAV, and `MAX_TIFF_FRAMES = 50`), and state the decision under review as "50-page, 15-minute, restartable" until dimension N's benchmark replaces the 12 s vs 25 s per-page guess with a measured p95. Re-derive every limit from that one measurement — J §8.2 already says exactly this and H did not honour it.

2. **Delete J §8.7's supervisor kill, or raise it above `budget_ms`.** These are two independent watchdogs enforcing incompatible ceilings on the same job, and lease expiry in H means *retry*, not *terminate*. H's `deadline_at` + reaper pass 2 is the correct and sufficient mechanism; the supervisor should only kill on RSS, never on wall clock.

3. **Make budget exhaustion degrade, not fail.** Replace §13.2 enforcement point 2 (`if now() > deadline: raise Terminal("BUDGET_EXCEEDED")`) with dimension E's already-designed path: mark the remaining OCR-routed pages `route=SKIPPED, reason="render_budget_exhausted"` (E §5.5 item 4, honouring E's pages-1–20-first priority), finish via statement 4a with `degraded=true`, and surface the gap list. Reserve `BUDGET_EXCEEDED` for a worker that has wedged with zero page progress since the last heartbeat — which is what the code was actually meant to detect. Add a regression test: a document sized at 3x its budget completes `SUCCEEDED/degraded` with a page gap list, and produces zero DLQ rows.

4. **Add `abort_requested = false, abort_reason = NULL` to statement 4a**, and add a schema-level soak assertion (the doc already proposes one for the reaper): seed a row in every reachable `(state, abort_requested, lease_token, deadline_at, started_at)` combination and assert every one of statements 1, 2, 3, 4a, 4b, 4c and all three reaper passes completes without raising. That test is what would have caught both this and the original reaper wedge.

5. **Update §12.3's listener to §6.4's chosen per-job channel** (or reverse §6.4 back to one channel with an HMAC'd job id, which is simpler to operate and is the stated option 2) — and pick one, in one section, so the implementer is not choosing.

6. **Reconcile H §14.3 with J §8.7 and the documented host.** H specifies `replicas: 4, mem_limit: 3g, cpus: "2.0"` = 12 GiB / 8 vCPU; J specifies 2 GB and 1.0 CPU per worker on a 4-vCPU host; §1.7 records the Docker VM as 8 vCPU / **7.75 GiB**. H's compose stanza cannot start 4 replicas on the documented dev machine, and the resulting kernel OOM-kills would fire the §8.2 crash-recovery path continuously — which would look exactly like a queue bug and is not one.

### Lens: SECURITY - REFUTED (major)

The Postgres substrate choice survives my lens — Redis would be strictly worse here, and I found nothing that makes "no Redis in M1/M2" unsafe. What fails is the second half of the claim: **"safe."** The isolation model bolted onto the queue is enforced by the honest worker's own SQL text, not by the database, against the one component every sibling document designates as certain to be compromised. Three concrete, substantiated defects, all in `/Users/innovera/Documents/OCR/docs/architecture/m0/h-queue-and-worker-contract.md`.

---

**1. Fencing is a convention, not a control. `ocr_worker` can write any organisation's job row with no lease at all. (§11.2 + §11.5)**

§11.5 grants `CREATE POLICY queue_all_orgs ON ocr_jobs FOR ALL TO ocr_worker USING (true) WITH CHECK (true)` (line 2948), and §11.2 grants `UPDATE (state, result, result_uri, degraded, last_error_code, available_at, …) ON ocr_jobs TO ocr_worker` (lines 2695–2700). A column-level `GRANT UPDATE` constrains *which columns* may be written; it places no constraint whatsoever on the `WHERE` clause. The `WHERE lease_token = $2` guard exists only inside statements 4a/4b/4c, which are text the worker itself chooses to send.

So a compromised worker executes, in one statement:

```sql
UPDATE ocr_jobs SET state='SUCCEEDED', result_uri='<attacker key>', degraded=false,
                    finished_at=now() WHERE tenant_id='<victim org>' AND state='RUNNING';
```

No lease token needed. This is permitted by the grants and by RLS as specified.

The consequences cascade through the design's own machinery:
- **§11.2.1's `SECURITY DEFINER` outbox trigger fires on exactly this.** `AFTER UPDATE OF state … WHEN (NEW.state IN ('SUCCEEDED','FAILED','DEAD','CANCELLED'))` has **no lease check**. §11.2.1 asserts: *"The worker still cannot forge an event. It can only cause the ones this function emits … for a row it holds the lease on."* Both clauses are false. The attacker gets a genuine, signed-by-the-database `document.extracted` outbox event for a victim organisation, carrying an attacker-chosen `resultUri`, which webhooks, search indexing and billing then consume as authentic.
- **Cross-tenant content injection into the system of record.** §9.5's status endpoint and dimension L's API serve `result_uri` to the victim tenant. The attacker chooses that key. Because §16.1's `AI_EXTRACT` stage runs the assembled text through the LiteLLM gateway, this is also a prompt-injection path *into another tenant's* extraction run — the one place the design assumes content is already trusted-by-provenance.
- **Platform DoS in one statement:** `UPDATE ocr_jobs SET state='DEAD'` across all orgs, or `available_at = now() + interval '30 days'`.

Even the token-based path is open: `lease_token` is explicitly in the granted SELECT column list (line 2753), and the RLS policy is `USING (true)`. `SELECT id, tenant_id, payload, lease_token FROM ocr_jobs WHERE state='RUNNING'` returns a live, valid capability for every running job on the platform. That also **defeats decision L26**, the sole mitigation for the accepted residual risk L25. §11.3 claims *"Reading another organisation's key from `ocr_jobs` then buys the attacker nothing — they have no credential that can fetch it."* But the credential is minted per claim by `ocr-web` and must be authorised by *something the worker presents*; the only candidate in the document is the lease token, which the attacker can read for any job. Worse, the document never specifies how the worker authenticates to that credential-minting endpoint at all — the trust boundary on which the entire corrected §11.3 security story rests is unspecified.

Realistic scenario, using the project's own threat model: dimension J §5.2 says *"we cannot prevent decoder RCE. We can only make it worthless"*, and rates worker RCE from a crafted PDF as Medium likelihood with a continuous CVE class (it cites CVE-2026-10118, CVE-2026-3029). An attacker signs up as a tenant, uploads a weaponised PDF, gets code execution in `ocr-worker`, reads the DSN from the environment, and then — over hours, quietly, without tripping `ocr_lease_lost_total` — harvests lease tokens and mints per-document storage credentials for every job that flows through the platform. H's decision L8 states the goal explicitly: *"A dedicated role makes that compromise worth almost nothing."* As specified, it is worth nearly everything in the queue plane.

---

**2. The document collapses dimension G's "two roles, two blast radii" into one and records it as a naming conflict. (§11.5 vs `g-data-model.md` lines 1320–1327)**

G says, verbatim: *"the claim runs as a third role, `ocr_queue`, which has `SELECT, UPDATE` on `extraction_jobs` and a policy of `USING (true)` — but has **no privileges at all** on `documents`, `document_pages`, `ocr_results` … **Once a job is claimed, the processing transaction switches to `ocr_app` with `app.current_org` set from the claimed row. Two roles, two blast radii.**"*

G's design deliberately confines the `USING (true)` window to the single claim statement. H §11.5 declares *"`ocr_worker` **is** G's `ocr_queue`. They are the same role under two names; that is the whole conflict"* (line 2931) — and then extends the cross-tenant `USING (true)` policy to **all four** queue tables for the **entire processing lifetime**. That is not a naming conflict; it is the deletion of G's second blast radius, adopted silently.

What that widening exposes cross-tenant, beyond `ocr_jobs`:
- `ai_calls` — `SELECT` yields `response_uri` for every organisation (object keys holding raw model responses, i.e. extracted document content), plus per-customer token counts and `cost_micros`. §15.2 states per-organisation cost is deliberately *not* a metric because it is *"commercially sensitive"* — and then leaves the underlying table cross-tenant readable by the most-likely-compromised process. **`UPDATE` on `ai_calls` is granted too** (line 2690), so the attacker can rewrite billing records: zero their own org's `cost_micros`, or inflate a competitor's. §15.2 names `ai_calls` as the billing source of truth, so this is direct financial-integrity tampering, not just disclosure.
- `ocr_page_results` — `blocks_uri` for every page of every tenant's documents.

---

**3. The 90-day PDPA audit trail is deliberately unfenced and cross-tenant writable. (§10.3 table, §6.6)**

§10.3 classifies the `ocr_job_events` insert as *"harmless (append-only audit); a duplicate event is correct history"* and leaves it unfenced. But §6.6 sets its retention to 90 days specifically *"for an audit trail that a Thai PDPA subject-access request may need to answer"*, adopting G's number over the draft's 30. An audit log that the most-likely-compromised component can write arbitrary rows into, for any organisation, with worker-controlled `detail` JSONB, is not a record you can answer a regulator with — and unbounded cross-tenant `INSERT` is also a storage-exhaustion vector with no quota in the document.

---

**What I checked and could not break.** Fairness/starvation (§7) is honestly caveated; the per-tenant page cache is correctly tenant-scoped (L7); the `LISTEN` metadata side channel is already found and fixed (§6.4); pixel/OOM/pids/tmpfs exhaustion is covered by J §5.3; the `est_pages`, `oldest_pending_s`, and budget-clock defects are already caught. The review pass on this document is genuinely strong. The gap is specifically that §19.7's security sweep audited *what the honest worker's statements do* and never audited *what the granted role is able to do*.

**Safer alternative:** Do not widen or narrow grants — remove the worker's direct DML entirely and make the lease a database-enforced control. Six specific changes, all before the M1 migration is written:

1. **Turn the seven protocol statements into `SECURITY DEFINER` functions owned by `ocr_owner`**: `ocr_claim_v1`, `ocr_heartbeat_v1`, `ocr_progress_v1`, `ocr_finish_ok_v1`, `ocr_finish_err_v1`, `ocr_cancel_v1`, `ocr_page_upsert_v1`, `ocr_event_v1`, `ocr_ai_reserve_v1`, `ocr_ai_complete_v1`. Then `REVOKE ALL ON ocr_jobs, ocr_page_results, ocr_job_events, ai_calls FROM ocr_worker; GRANT EXECUTE ON <those functions> TO ocr_worker; REVOKE EXECUTE … FROM PUBLIC`. Every function takes `(job_id, lease_token, …)` and re-validates `lease_token AND state='RUNNING'` in the same statement. Harden each exactly as §11.2.1 already specifies for the outbox trigger: pinned `search_path`, no dynamic SQL, non-superuser owner. The document already reaches for this pattern twice (L27's trigger, §8.3's `ocr_fan_in_v1`) — generalise it instead of applying it twice by accident. Cost is one migration; §6.3's SQL is unchanged, it just moves inside the functions, so Option A2's "language-neutral contract" property survives.

2. **Make the lease token a secret, not a readable column.** Store `lease_token_hash bytea` (SHA-256); `ocr_claim_v1` returns the plaintext exactly once, to the claimer. No SELECT path ever yields a usable token. This closes the token-harvesting path even if (1) is only partially adopted.

3. **The worker gets no `SELECT` on `ocr_jobs` at all.** `ocr_claim_v1` returns the claimed row's payload; that is the only legitimate read. This converts L25's accepted residual risk ("a compromised worker can enumerate every organisation's document identifiers and storage keys platform-wide") into "cannot enumerate at all", for free — and lets you delete the accepted-risk row rather than push it into J's STRIDE table.

4. **Restore G's second blast radius (`g-data-model.md` line 1325).** After `ocr_claim_v1` returns, the processing transaction runs as a distinct role with `SET LOCAL app.current_org = <claimed org>` and the ordinary `org_isolation` policy, so `ocr_page_results`, `ocr_job_events` and `ai_calls` are touched only under single-org RLS. Only the claim itself runs cross-tenant. Reopen Q0 to cover this, not just the table name and priority direction: today Q0 is scoped to naming and ordering, and this is the substantive divergence hiding underneath it.

5. **Bind the object-storage credential to the claim, not to a re-presentable token.** `ocr_claim_v1` returns a single-use `claim_nonce` (row-stored, consumed on redemption, tied to job id + org + document + lease expiry). `ocr-web`'s minting endpoint accepts the nonce, never a lease token, and the worker→`ocr-web` channel is mutually authenticated (mTLS or a per-replica secret) so a stolen DB role alone is not sufficient. Specify this endpoint's authentication explicitly — it is currently the unstated foundation of decision L26.

6. **Add the negative tests R13 is missing.** Alongside `SELECT 1 FROM users`, assert as `ocr_worker`: `UPDATE ocr_jobs SET state='SUCCEEDED' WHERE id=<another org's job>` raises permission denied; `SELECT lease_token FROM ocr_jobs` raises permission denied; `SELECT response_uri FROM ai_calls` raises permission denied; `UPDATE ai_calls SET cost_micros=0` raises permission denied; `INSERT INTO ocr_job_events` outside the function raises permission denied. Generate these from the Prisma schema the same way §11.2 already generates the deny-list test, so a future migration cannot silently widen the surface.

If (1) is judged too large for M1, the minimum viable stopgap is (2) + a `BEFORE UPDATE` trigger on `ocr_jobs` that rejects any row change where `OLD.state='RUNNING' AND OLD.lease_token IS DISTINCT FROM current_setting('app.lease_token', true)::uuid`. That is one trigger and it converts fencing from convention into enforcement — but it does not close (3), (4) or the `ai_calls` billing-tamper path, so treat it as a bridge, not the answer.

### Lens: operations - REFUTED (major)

The "without Redis" half of this decision survives my lens and I will not attack it: §5.1's cost list is honest, R15 (transactional enqueue) is a real safety property Redis destroys, `m-docker-nginx-resources.md` O2 reaches the same conclusion independently, and §5.3's triggers T1-T5 are falsifiable and measurement-gated. Adding Redis would add a datastore, a relay process and a durability model for zero gain at this scale. That is correct.

The "safe and operable for 10-minute, 200-page, restartable jobs" half is refuted by the project's own numbers.

**1. Under L5 there is no scaling lever for single-document latency, and 10 minutes is off the table.** L5 (§0) fixes one job per document with an internal page loop; §8.3's per-page fan-out is "Not in M1" and §17.3 defers it to Branch V or an unmeasured shortfall. So per-document wall time = pages x per_page_seconds, *invariant in cluster size* — adding workers never speeds up one document. `m-docker-nginx-resources.md` §4.4.1 (review-corrected, authoritative) gives 4.5 CPU-s/page and states plainly "a single 400-page scanned document occupies the entire service for half an hour" — i.e. 4.5 s/page wall. 200 pages = 15 min, not 10. And on the *recommended* host (§4.4.1, "VPS 4 vCPU / 16 GB") **W = 1**: one worker container total. That single 200-page document consumes 100% of platform capacity for 15 minutes. 10 minutes is reachable only at the extreme optimistic end of an explicitly unmeasured estimate range (3.0 CPU-s), with the document alone on the box.

**2. H's own budget constant says the job terminally fails.** §13.2 computes `budgetMs` with `perPageBudgetMs` = **25 s classical** — 5.5x M's 4.5 CPU-s. Two M0 documents differ by 5.5x on the one number that decides feasibility, and both are flagged unmeasured (Q4 open). At H's own 25 s: 200 pages = 83 min against a hard 45-min ceiling. §13.2 admits it — "a 200-page document at 25 s/page cannot finish inside a sane budget on one worker" — and then ships that budget anyway.

**3. The new defect: `BUDGET_EXCEEDED` non-retryable cancels L28 and strands every §8 checkpoint.** §9.6 lists `{"code":"BUDGET_EXCEEDED","retryable":false,...,"http":504}`, and §13.2's closing line justifies it: *"Retrying a job that ran out of time yields the same result more slowly."* **That rationale is false in this design.** §8.1's content-addressed `ocr_page_results` means a retry skips every `DONE` page and resumes at the deadline point — attempt 2 is strictly cheaper and makes guaranteed forward progress. This is pre-checkpoint reasoning carried into a design that invalidates it. The direct consequence: §13.2's own advertised "second-order benefit" of L28 — *"a job that crashes at page 190 and is re-claimed gets a fresh processing budget for the remaining 10 pages, which is what §8's page-checkpoint story assumed all along"* — is dead on the timeout path, and the stated worst case `max_attempts x budget_ms = 4 x 45 min` is unreachable via budget. A long document gets exactly **one** 45-minute attempt, ever. Not flagged in §19; the review found the enqueue-clock bug (L28) and stopped one step short.

**4. The 3am scenario, concretely.** 02:40, Thai customer uploads a 200-page scanned contract bundle (accepted: §14.1 `maxDocumentPages` = 2000). Priority 200, claimed immediately, `deadline_at = now + 45 min`, W=1 so it holds the entire platform. Per-page cost lands above 13.5 s (H's own planning number is 25 s). At 03:25 the worker hits §13.2 enforcement point 2, raises terminal `BUDGET_EXCEEDED`, statement 4b writes `state='FAILED'`. Now count the operator's levers:
- `ocr_dlq` (§15.1) is `WHERE state = 'DEAD'` — a `FAILED` job **is not in the DLQ**.
- L15's one-UPDATE requeue is DEAD-only. **There is no documented requeue path.**
- `OcrBudgetExceeded` (§15.3) is a **ticket**, threshold >5/h. Nobody is paged; the customer finds out.
- Meanwhile `OcrQueueStalled` *does* page at `oldest_pending_s > 900` — with the runbook meaning "jobs exist and nothing is draining / all workers dead or wedged". The workers are healthy and busy. The page is actively misleading.
- 108 pages of paid-for, checkpointed OCR sit in `ocr_page_results`, unreachable.

The only working recovery is undocumented: the customer re-uploads identical bytes, §8.1's cache hits on the same sha256, attempt 2 finishes the tail. The de facto SLA on a large document is "re-upload twice."

**5. The inversion that makes this an on-call hazard.** An operator who bounces the worker container *before* the deadline gets a strictly better outcome than one who does nothing: SIGKILL → lease expires → reaper pass 1 writes `LEASE_EXPIRED` (retryable, maxAttempts 6) → re-claim → fresh 45-min budget per L28 → resumes from checkpoints → completes. Letting the system run to its own deadline produces a terminal failure. **The design rewards killing the workers,** and whether a customer's document completes depends on whether someone happened to restart a container inside the right 45-minute window. That is not an operable system.

**6. Admission control accepts work the platform provably cannot do.** `maxDocumentPages` = 2000 (§14.1). Real ceiling = 45 min / per_page_s = ~600 pages at M's number, ~108 at H's own. The gap between the advertised limit and the achievable limit is 3x-18x, and every document in that gap is accepted, charged a worker slot for 45 minutes, and returned a 504. `est_pages` — added in review for §14.2 — already exists at enqueue, so the check that would close this is free and simply absent.

**7. No dimension states a per-document latency requirement at all.** §3's R1-R21 contain none; §15.2 calls `ocr_queue_oldest_pending_seconds` "the primary SLO" (queue wait, not completion); §15.3 has no alert on `ocr_job_duration_seconds`. `d-ocr-engine.md` §371 computes multi-page wall time as *"A 50-page PDF at 2 s/page on 4 workers ≈ 25 s wall"* — spreading pages across workers, which L5 forbids. So the one place the corpus reasons about document latency assumes an architecture H rejected, and the discrepancy runs in the direction that makes 10 minutes look achievable.

**Reversibility.** The substrate is reversible (§5.2's port abstraction is real). What is *not* cheaply reversible is L5 + the deferral of §8.3: single-document latency is the property this decision is being asserted on, and it is the one property the M1 architecture has no lever for. Deferring fan-out defers the only fix.

**Safer alternative:** Keep PostgreSQL. Keep no Redis. Fix five things, none of which reopen the substrate decision.

**(1) Make `BUDGET_EXCEEDED` progress-conditional instead of flatly terminal.** In `contracts/error-codes.json` set `{"code":"BUDGET_EXCEEDED","retryable":true,"maxAttempts":4}` and have the worker pass §6.3 statement 4b's `$5 retryable` as `(pages_completed_this_attempt > 0)`. A job that timed out having finished at least one new page gets another budget and resumes from the §8.1 checkpoints; a job that timed out having finished zero pages is genuinely wedged and stays terminal on first occurrence under a distinct code `BUDGET_EXCEEDED_NO_PROGRESS`. This is one bind parameter over machinery that already exists, and it makes L28's advertised benefit true instead of dead. Alert split: `BUDGET_EXCEEDED` (slow) stays a ticket; `BUDGET_EXCEEDED_NO_PROGRESS` (stuck) becomes a page, which is what the current ticket was actually trying to catch.

**(2) Add a feasibility gate at upload, derived rather than hardcoded.** Reject at enqueue (HTTP 413, `msgKey: err.document_too_long_for_tier`, Thai + English per §9.6) any document where `est_pages x perPageBudgetMs > budgetCeilingMs x safetyFactor`. Delete the flat `maxDocumentPages = 2000` and derive it from the same per-page constant that feeds `budgetMs`, so the advertised limit and the achievable limit are the same number by construction and both move when Q4's benchmark lands. Failing fast at upload with an honest message costs the customer 2 seconds; failing at 45 minutes costs them the whole platform's capacity and gives them a 504.

**(3) Make Q4 blocking, and set defaults from the pessimistic end until it closes.** H §13.2's 25 s/page and `m-docker-nginx-resources.md` P1's 4.5 CPU-s/page differ by 5.5x and neither is measured. Until the M2 benchmark lands, set `maxDocumentPages` from the pessimistic constant (~100 pages), not the optimistic one, and state the single-document latency ceiling that follows in the product tier. Promote Q4 in §17.1 from "eng / M2 benchmark" to a gate on writing any of `budgetMs`, `maxDocumentPages`, or the fan-out trigger into config.

**(4) Convert §8.3's fan-out trigger from a deferral into an M2 SLO gate.** Replace §17.3's "Branch V, or measured throughput below target" with: *if the M2 benchmark shows `p95_pages x per_page_s` above the stated single-document latency SLO, per-page fan-out is in M2 scope.* Under L5 there is no other lever — replicas do not reduce single-document latency — so this is the only mechanism that can ever satisfy the workload the decision claims to serve. The fan-in barrier is already written (§8.3, ~10 lines of SQL) and needs no Redis, so this costs scope, not architecture.

**(5) Give the on-call an actual lever, independent of (1).** Widen `ocr_dlq` (§15.1) to `WHERE state = 'DEAD' OR (state = 'FAILED' AND last_error_code IN ('BUDGET_EXCEEDED','QUEUE_WAIT_EXCEEDED','STORAGE_UNAVAILABLE'))`, and extend L15's one-UPDATE requeue to cover it. Add `ocr_job_duration_seconds` to §15.3 with a per-document latency alert. Write the runbook line that does not exist today: *a job that failed on budget has usable checkpoints; requeueing it resumes from the last completed page* — so 3am has an answer other than restarting containers or asking the customer to upload it again.

Net effect: the substrate decision stands untouched, the queue protocol in §6 is unchanged, and the platform stops accepting work it cannot finish, stops throwing away checkpointed work it already paid for, and stops rewarding the operator for killing it.

## 2. The DB-credential boundary, as specified, cannot claim a single job.

The §6.3 claim statement (h:995-1031) reads four columns the L25-corrected `GRANT SELECT (...)` list (h:2752-2755) omits: `j.priority` (ORDER BY), `j.available_at` (WHERE **and** ORDER BY), `j.budget_ms` (RHS of `deadline_at = now() + make_interval(secs => j.budget_ms/1000.0)`), `j.started_at` (RHS of `COALESCE(j.started_at, now())`). PostgreSQL requires SELECT on every column referenced, not just projected — verified against the PG 17 docs (postgresql.org/docs/17/ddl-priv.html): *"This privilege is also needed to reference existing column values in UPDATE, DELETE, or MERGE"*, and *"any nontrivial UPDATE command will require SELECT privilege as well, since it must reference table columns to determine which rows to update, and/or to compute new values."* First claim as `ocr_worker` → permission denied; the queue is permanently empty and every other test passes.

Independently, the same statement **writes** `deadline_at` (h:1025, decision L28) — and `deadline_at` is absent from `GRANT UPDATE (...)` (h:2695-2700), with h:2711-2713 stating in prose that the worker *"cannot change … `budget_ms`, `deadline_at`."* §6.3 and §11.2 directly contradict each other on a column L28 requires the claim to set.

These are one-migration fixes. ## 3. The mitigation that makes the boundary safe does not exist on the backend M1 deploys.

H is admirably honest at L25: table-wide SELECT on `ocr_jobs` lets a compromised worker enumerate **every** organisation's storage keys, and this is closed by L26 — a per-claim, per-document, short-lived credential (STS `AssumeRole` with a session policy), giving blast radius *"one document, for one lease"* (h:2870). H's own Q8 (h:3551) flags whether the backend supports this as open.

M answers it, and the answer is no. `m-docker-nginx-resources.md:1788`: the M1 object store is the **local Docker volume `ocr_file_storage`**, *"`ocr-web` **and** `ocr-worker`, both uid 10001 … must match."* There is no STS. H's local-backend equivalent — *"a signed capability token … validated by the storage adapter on every call"* (h:2861-2864) — is validated by code **inside the worker process**, against a filesystem the worker already has mounted. So on the backend M1 actually ships, L26's blast-radius claim is false and the true radius is the draft's own rejected position: every document of every organisation, indefinitely — which is precisely the compromised-worker scenario h §11.1 names as the most likely one in the system.

## Finding 2 (major) — the credential boundary's own mitigation (L26) rests on an unspecified binding, and the naive implementation fully reopens L25

H §11.2's L25 correction admits the real hole: `GRANT SELECT … ON ocr_jobs` is unfiltered, so *"the worker can `SELECT payload FROM ocr_jobs` and read **every organisation's** `source.bucket` and `source.key`"*, and *"a compromised worker … can read every document on the platform."* The stated fix (L26) is a per-claim, per-document scoped credential *"minted by `ocr-web` and returned by the claim"*.

But §6.3's claim is **raw SQL executed by the worker**, and the note bolted onto it says *"the claim RPC — **not this raw statement** — additionally mints and returns"* the credential, with §11.3 conceding *"the claim is no longer only SQL … paid in `ocr-web`'s claim endpoint."* **That endpoint is never specified.** The two implementations both fail:

- **If `ocr-web` runs the claim SQL**, it needs the cross-organisation RLS policy and claim grants → Finding 1 item 2, in the credential boundary too.
- **If the worker claims via SQL and then calls `ocr-web` to mint a credential**, the naive shape is `POST /internal/claim-credential {documentId, bucket, key}`. A compromised worker already has, by L25's own admission, a platform-wide list of `(organizationId, documentId, bucket, key)`. It names any of them and gets a valid scoped credential. **Blast radius returns to "every document of every organisation" — the exact figure the L26 table claims to reduce to "one document, for one lease."**

## P4-native-vs-ocr-routing

**Decision under review:** The per-page native-text-sufficiency heuristic and its thresholds (see e-native-extraction-routing.md) will correctly route real-world PDFs, including mixed and badly-pre-OCRed documents, without silently losing content.

### Lens: FEASIBILITY - REFUTED (major)

The library facts underneath this decision hold up — I verified against the pdfplumber stable README that `page.images` really does carry `srcsize` (so `dominant_image_native_dpi` is implementable), that the char-key list is exactly as quoted (`non_stroking_color`, `mcid`, `tag`, `ncs` all present, and no render-mode key, confirming the §4.5(a) PDFium detour is necessary), and that `x_tolerance_ratio` is a real `extract_text()` parameter defaulting to `None`. The per-page framing, the signal set, and the `NormalizedDocument` provenance model are sound. But the specific claim under review — that the heuristic and its thresholds route real-world PDFs, *including mixed and badly-pre-OCRed documents, without silently losing content* — is false on at least three concrete document shapes, plus two implementability walls. All five are in the docs as written, not hypotheticals.

**1. The "badly-pre-OCRed" case is exactly the case the gate cannot see (e-native-extraction-routing.md §4.3 lines 551-568, §4.4, §4.5(d) line 852).** `ocrLayerFingerprint` is computed in `PageSignals` (line 407) and then used in precisely one place: as an OR-term inside the `is_sandwich` predicate. It never reduces trust. Meanwhile §4.5(d) states in prose that a Tesseract sandwich must be "treat[ed] as **suspect by default**" and marks ABBYY's Thai quality UNVERIFIED — and `route_page` then trusts both. Worse, `assess()` (§4.4) tests **orthographic well-formedness only**: `garbageRatio`, `orphanMarkRatio`, `danglingPreVowelRatio`, `thaiRatio + asciiPrintableRatio`. A *wrong recognition that is still valid Thai* passes every one. The pathological subcase is numbers, which is what this product is for: a total of `2,150,000` mis-OCRed as `2,150,090`, or `๓` read as `๙`, scores garbage 0.0, orphan 0.0, dangling 0.0, thai+ascii 1.0 → `trusted_strict = True` → with `charDensity ≥ 10` and no font-substitution risk → `NATIVE, "sandwich_layer_clean"`. The page is never rendered, never re-OCRed, and no warning fires. §4.9's own reversal criterion ("flip the default to `never` if calibration shows >10% of clean-gating sandwich layers are materially worse") is unmeasurable *before* the calibration corpus exists — so the risky default `if-clean` is on during exactly the window in which it is unvalidated. The §4.5a rationale that consumer scanners "produce a layer of Latin gibberish, which the §4.4 gate rejects outright" is true of *no-Thai-model* firmware and simply untrue of Tesseract-tha, ABBYY FineReader Thai, and Adobe Scan, which are the sandwich producers a Thai office actually generates.

**2. Images on NATIVE-routed pages are never read, and no warning says so (§4.3 steps 4 and 6, contradicted by §11 line 1705).** Step 4 returns `NATIVE` whenever `charDensity ≥ 12` and `imageAreaRatio < T_IMAGE_SIGNIFICANT = 0.25`; step 6 returns `NATIVE` whenever `charDensity < 3` and `imageAreaRatio < T_IMAGE_SPARSE_TRIGGER = 0.15`. §11 then asserts "If a PDF page's images matter, the page is already routed `OCR` or `HYBRID` and the **whole page is rendered**" and uses that assertion to declare PDF embedded-image OCR explicitly out of scope. The two statements are inconsistent by construction. Realistic scenario: a Thai quotation (ใบเสนอราคา) exported from Word — dense native body text — with the authorised-signature block and the red company seal (ตราประทับ) pasted as a JPEG bottom-right, typically 8–20% of A4. → step 4 → `NATIVE`. Signatory name and seal are never rendered, never OCRed, never extracted as an asset. And unlike E20, which carefully emits `hidden_text_suppressed: N`, there is **no** corresponding `unread_image_area` warning anywhere, so neither the UI, the audit record, nor the AI layer learns that a fifth of the page's ink was skipped. That is the definition of silently losing content. The inconsistency is self-evident inside the doc: `T_IMAGE_PRESENT = 0.05` is enough to force HYBRID in the *moderate* band (step 5), but the *dense* band tolerates 5× more un-read image, with no stated reason.

**3. Text converted to outlines is invisible to every signal, and `VECTOR_ONLY` is a terminal route.** `vectorInkRatio` is read in exactly two places, both in `route_page` (lines 516, 532) — only when `total_chars == 0` or when quality already failed. Steps 4/5/6 never consult it. (a) A page whose body was converted to curves but which keeps a native header/footer (say 200 chars on A4 → `charDensity ≈ 2.1`, `imageAreaRatio ≈ 0`) falls to step 6 → `NATIVE, "sparse_text_no_image"`; the entire body is lost with no warning. (b) A wholly-outlined page hits step 0 → `VECTOR_ONLY` — and grep across the whole M0 set confirms nothing ever renders or OCRs `VECTOR_ONLY`: it gets no `renderUri`, and §5.5's budget and prioritisation rules speak only of "OCR-routed pages". The enum comment calls it "drawings/CAD with no text layer", but it is also the bucket outlined text lands in. Outlining Thai text is not exotic — it is the standard workaround for Thai font embedding/licensing problems in CorelDRAW/Illustrator/InDesign print workflows, which is where a large share of Thai print-shop-produced PDFs come from.

**4. There are two conflicting native-vs-OCR gates in the M0 set, violating E1's own invariant.** §1 line 62: "there must be exactly one implementation of the routing heuristic." But f-preprocessing-and-confidence.md §P1b defines an independent **Tier 0, always-on** gate: "If the page yields ≥ 20 extractable characters with a real font mapping and contains fewer than 3 raster images covering < 50% of the page area → **skip OCR entirely**", flagged "This must exist from M1 day one." Different units (absolute char count vs chars/in²), different image test (a *count* of 3 plus a 50% area cap vs 0.25/0.15 area thresholds), and strictly more permissive on the mixed page. E's own motivating example §4.1 case 2 — "a scanned attachment image occupying the lower half of page 3" — sits exactly on P1b's 50% boundary; a 45%-area pasted scan is `HYBRID` under E and "skip OCR" under F. Neither document says which owns the decision, and an engineer building the OCR worker will implement P1b as specified because F marks it mandatory Tier 0.

**5. E20's per-character invisible-text filter has no join key and is not implementable as written (§4.5a rule 1 vs §4.5(a)).** Render mode comes from `pypdfium2` (`tp.count_chars()`, `FPDFText_GetTextRenderMode(tp.raw, i)`); the emitted text comes from `pdfplumber.page.chars` / `extract_text()`. These are two independent parsers producing different character sequences — PDFium's text page synthesises whitespace and applies its own ordering; pdfplumber returns only real glyphs — so index *i* in one is not index *i* in the other. E20 nonetheless says "the per-character render mode from probe (a) is the filter." Grep confirms no alignment is specified anywhere. The only available join is bbox matching, which is where Thai breaks worst: a base consonant, its above-vowel and its tone mark share nearly the same x-range and are stacked within a few points of y. A misaligned filter fails silently in the worst direction — it suppresses *visible* Thai characters as "hidden", converting an anti-prompt-injection control into a Thai-specific data-loss mechanism. (The §4.5(b) pypdf visitor is the parser that *is* in pdfminer's content-stream order, but the doc itself says it is run-level, not char-level, and admits it omits the `q`/`Q` graphics-state stack.)

None of this refutes per-page routing as an architecture — it refutes the claim that *these* thresholds and *this* control flow are safe to ship. Each defect is a localised fix, which is why I score this major rather than fatal; but every one of them must land before M1, because four of the five fail silently and the fifth fails silently on Thai specifically.

**Safer alternative:** Seven concrete changes, in priority order.

1. **Do not trust a third party's OCR layer on orthography alone.** Replace the `sandwich_layer_clean` shortcut with a render-and-verify cross-check: for any page that would return `sandwich_layer_clean`, render at 150 dpi (cheap — 2.1 MiB greyscale) and run sampling OCR on 2–3 line crops; require normalised character-level agreement ≥ 0.90 on the sampled lines **and exact agreement on every digit run** before returning NATIVE, otherwise return OCR. F §P1b already gestures at this ("Thai-block ratio within ±0.25 of the OCR sample pass on a 3-line crop") — promote it into `route_page` and tighten it to digit exactness, since digits are the class every check in `assess()` is blind to.

2. **Ship `trustExistingOcrLayer = "never"` as the default; make `if-clean` an opt-in per-tenant setting.** §4.9's stated reversal criterion cannot be evaluated until the calibration corpus exists, so the default during the unmeasured window should be the one that is expensive rather than the one that is silently wrong. Additionally gate the trust path on the fingerprint the doc already computes: never take `sandwich_layer_clean` when `ocrLayerFingerprint == "tesseract"` (§4.5(d) already calls it suspect) or when it is `None` (unknown producer).

3. **Add a residual-ink rule to steps 4/5/6, not just step 0.** After a NATIVE decision, compute the ink coverage *not* covered by word boxes (reuse the same 200×200 `coverage_ratio` mask: `unread = coverage(images ∪ vectors) − coverage(images ∪ vectors ∩ words)`). If `unread ≥ 0.03`, upgrade to HYBRID. If the render budget forbids it, keep NATIVE but emit a **mandatory** `unread_ink_area: <ratio>` page warning that propagates to the document warnings and the UI. Also lower `T_IMAGE_SIGNIFICANT` from 0.25 to 0.05 so the dense band matches `T_IMAGE_PRESENT` already used in the moderate band; there is no stated justification for the dense band tolerating 5× more unread image.

4. **Make `VECTOR_ONLY` a rendering route.** By definition it is a page with ink and no readable text, which is the strongest possible OCR signal. Render and OCR it exactly as `OCR`; if the budget binds, mark it `SKIPPED` with `reason="render_budget_exhausted"` — never terminate it silently. Add `vectorInkRatio ≥ 0.15` as an OCR/HYBRID trigger in steps 5 and 6 so partially-outlined pages are caught too.

5. **Delete f-preprocessing-and-confidence.md §P1b's thresholds** and replace them with "consume `route` from the extractor's `NormalizedDocument`; never re-decide." Add the CI guard E1 already implies: a lint/test that fails if any character-count or image-area gate appears in the OCR worker.

6. **Fix E20's filter by removing the cross-parser join.** Either (a) emit the text from PDFium's textpage as well, so character and render mode come from the same object at the same index, and demote pdfplumber to geometry/signals only; or (b) apply suppression at **run** level using the §4.5(b) pypdf `visitor_operand_before` path, which is in the same content-stream order as pdfminer, and add the `q`/`Q` graphics-state stack the doc admits is missing. Whichever is chosen, add a fixture test on a Thai sandwich PDF asserting that zero *visible* characters are suppressed.

7. **Extend §4.9's stratification** with the three shapes above as named strata, each with a hard recall assertion in `tests/routing/test_thresholds.py`: (i) PDFs whose text is converted to outlines, (ii) dense-native pages carrying a pasted signature/seal image at 5–25% area, (iii) Thai OCR sandwiches that are orthographically clean but contain wrong digits. All three currently route NATIVE and all three would pass the sweep as written, because the sweep's label ("would OCR produce materially better text?") is never asked of pages the router never considered risky.

### Lens: security - REFUTED (major)

The heuristic is well-built for ADVERSARY = "bad PDF generator". It is not built for ADVERSARY = "person who chose the bytes". Three of its terminal routes hand an uploader direct, unverified control over what the machine reads, and in each case the page's actual pixels are never decoded by anything. The claim "without silently losing content" is also the wrong safety property: the worst case here is not loss, it is silent SUBSTITUTION.

=== 1. The `sandwich_layer_clean` route is a content-forgery channel (the headline) ===

File: e-native-extraction-routing.md §4.3 step 2, §4.5a rule 4, §4.5 "Default policy: trustExistingOcrLayer = if-clean".

Exact claims: (a) `route_page` returns `PageRoute.NATIVE, "sandwich_layer_clean"` when `imageAreaRatio >= 0.80`, an invisibility signal fires, `quality.trusted_strict`, `charDensity >= 10`, no font-substitution risk; (b) E20 rule 4: "when a page routes NATIVE with reason sandwich_layer_clean, the invisible layer IS the content, and it is emitted with extractionMethod = pdf.existing_ocr_layer"; (c) §5 rasterises only "the pages that do need OCR", and §5.5 "Native pages are never skipped — they are nearly free", i.e. this page is never rendered.

Failure mode: `trusted_strict` is a Thai ORTHOGRAPHY test (garbage/orphan-mark/dangling-pre-vowel/script ratios). It measures whether a string is well-formed Thai. It cannot measure whether the string matches the picture underneath it, and nothing else in the design does either. A forged layer is not merely undetectable — it scores PERFECTLY, because an attacker writes clean text.

Scenario, using this doc's own stated corpus (Thai supplier invoices/quotations): a supplier — or anyone who can reach the tenant's intake, which for invoices is by definition not the tenant — uploads `invoice.pdf`. One page, one full-bleed 300-dpi scan showing ฿17,400 (imageAreaRatio ~0.95 ≥ 0.80). Underneath, a Tr-3 layer written with pypdf (or ocrmypdf over a doctored raster) reading ฿1,740,000 with a different bank account. It carries `/Producer: Tesseract` and `GlyphLessFont` — which §4.5(d) treats as *evidence it is a real OCR layer*, i.e. as the reason to ENTER the trust branch rather than as a reason for suspicion. assess() → garbage 0, orphan 0, dangling 0, thai≈1 → `trusted_strict`. charDensity ~30 ≥ 10. GlyphLessFont is embedded → no substitution risk. Route: NATIVE.

What then follows mechanically from the rest of the design:
 - The page is never rasterised, so the visible pixels are never decoded by anything, ever.
 - E20's suppression and the `hidden_text_suppressed: N` warning — the ONE mitigation §13.1 rule 4 says this dimension owes the AI layer — are explicitly disabled on this path.
 - §13.1 rule 2 ("attributes appear only when non-default"; default = native, full confidence) serialises it as a bare `[PAGE n]`. The model gets no signal that 100% of that page came from an unverified third party's invisible layer.
 - §12.1 sets `confidence = null` for native, so f-preprocessing §2.6's human-review flag rule has no number to trip on.
 - f-preprocessing D20 names server-side grounding as "the enforcement point" and §2.5 grounds extracted values against the extracted text — which IS the forged layer. Grounding passes at maximum score.
Net: one crafted upload yields a high-confidence, fully-grounded, review-flag-free extraction that contradicts the document a human sees. Same channel carries prompt injection with E20 off.

This also contradicts a sibling doc. j-security-threat-model.md:862 says hidden text "is invisible to the human reviewer and is therefore *only* addressed to the model. Treat it as a strong injection signal, and exclude it from the text sent to the model." E20 rule 4 does the exact opposite on the one path where the emitted text is 100% invisible and 100% attacker-authored. Two docs, opposite rules, no reconciliation.

§4.9 cannot catch this: its label is "would OCR produce materially better text than the native layer?" A human labelling a forged layer answers "no, it's excellent." The calibration objective is blind to forgery by construction.

Corroboration that this is the recognised attack and the recognised detector: mismatch between the embedded text layer and OCR of the page raster is the standard indicator of a hidden-text-layer attack (search: PDF hidden text layer attack / ocrmypdf sandwich renderer). The design has both halves available and never compares them.

=== 2. Analyzer and renderer disagree; three routes exit without rendering (silent loss) ===

(a) VECTOR_ONLY has NO defined behaviour anywhere. `grep -n VECTOR_ONLY *.md` returns 5 hits: the enum, the return in step 0, an aside in §4.8a, and two model/type declarations. §5 covers only "pages that do need OCR". So the design as written never renders or OCRs a VECTOR_ONLY page. That population is not exotic: text converted to outlines is one menu item in Illustrator/Inkscape and a routine artefact of design-tool and some e-tax exports. charCount 0, vectorInkRatio high → VECTOR_ONLY → whole page dropped, while a human sees a complete invoice. As an attacker primitive it is one command.

(b) Annotation appearance streams are invisible to the analyzer but visible to the renderer. `page.chars/images/lines/curves/rects` come from pdfminer's content-stream interpretation, which does not process annotation APs (pdfminer.six issue #531); `annotationTextCharCount` reads annotation dictionaries, not their APs. Yet §5.1 sets `draw_annots=True` precisely because "Thai business PDFs carry stamps and signatures as annotations surprisingly often." So a page inked entirely by a stamp/FreeText AP scores charCount 0, imageAreaRatio 0, vectorInkRatio 0 → `EMPTY, "no_text_no_ink"` → never rendered. That is exactly §4.1's own motivating case ("the signature page is never OCRed and the signatures/stamps are silently lost") reappearing through a different door. Attacker version: innocuous content stream (routes NATIVE, never rendered) + the real terms in annotation APs that a human sees in Acrobat and the pipeline never touches.

Both are the same root cause: the routing decision is made against a different rendering of the page than the one a human sees, and no route reconciles them.

=== 3. `Policy` provenance is unspecified and `"always"` exists ===
§1's contract puts `policy` in the `/v1/extract` request body; nothing states it is server-derived from tenant config and non-overridable per request. §4.5 says `"never"` "should be selectable per-tenant", which implies the whole Literal is tenant-reachable — including `"always"`, which returns NATIVE for any sandwich page with NO quality gate at all. A tenant admin who flips it to save money silently opts into trusting arbitrary third-party invisible text verbatim.

=== 4. Two smaller ones, named not manufactured ===
 - Cost steerability: three routes fail toward OCR (`quality_gate_missing`, `degenerate_text_layout`, `undecodable_text`). Correct choices, but they make the expensive path attacker-selectable, and §1 says `maxRenderPages` is "the ONLY render-budget knob" — per document. Nothing in E ties render/OCR count to a per-tenant rate or spend cap, so a 200 MB upload reliably buys the full 400 renders + 400 OCR passes.
 - §4.9 "Log every routing decision in production with the full PageSignals blob", pooled cross-tenant for calibration. `fontNames: frozenset[str]` is the only free-text field in that blob and it is attacker-controlled (subset font names frequently carry the original font name and occasionally authoring-tool strings). Hash or allowlist it before it crosses a tenant boundary into a shared store.

=== Why major and not fatal ===
The per-page architecture is what makes every fix cheap and additive — that is the design's real strength and I am not asking for a redesign. But #1 defeats the product's core claim on its core corpus, and #2 is silent loss of exactly the content §4.1 exists to protect. Neither may ship.

**Safer alternative:** Three changes, all additive to the existing per-page structure.

(1) DELETE the E20 rule-4 carve-out. Replace the `sandwich_layer_clean` → NATIVE edge with a VERIFY route: render the page once at 150 dpi greyscale and run the OCR engine on 2-3 line boxes chosen at random FROM THE INVISIBLE LAYER'S OWN BBOXES (not the whole page). Require per-line agreement >= 0.85 after `thaiFold()` (f-preprocessing D18). Agree → keep the layer, emit with `extractionMethod=pdf.existing_ocr_layer` AND `attrs.layerVerified="sampled"`, and surface the verified/unverified distinction in §13.1's page attributes so it is no longer "default". Disagree, or the sample is unreadable → route OCR and raise a document-level `ocr_layer_mismatch` warning that FORCES human review (this is the industry-standard hidden-text-layer detector). Cost: one cheap render plus ~3 line recognitions per sandwich page — a small fraction of a full OCR pass, so most of the economic win that motivated `if-clean` survives. Make `"always"` unreachable from any tenant-settable surface: drop the literal, or gate it behind a server-side flag that also stamps `requiresHumanReview=true` on every document it touches. State explicitly, in §1, that `policy` is server-derived from tenant configuration and is not accepted from a client request body.

(2) ADD AN INK-CORROBORATION PROBE to every route that terminates without rendering — `EMPTY`, `VECTOR_ONLY`, and `NATIVE` where `total_chars < T_SPARSE_CHARS_PER_IN2 * pageAreaIn2`. Render at 72 dpi greyscale (A4 = ~0.5 MB, single-digit ms) and compute `inkFrac` — f-preprocessing §1.2b's A0 pass already defines exactly this measurement, so it is reuse, not new machinery. If `inkFrac > ~0.005` while the analyzer reported no ink, the analyzer and the renderer disagree: route the page `OCR` with reason `analyzer_renderer_disagreement` and warn. One mechanism closes annotation-AP content, tiling-pattern fills, and any future pdfplumber/PDFium divergence, instead of enumerating PDF features forever. In the same change, give `VECTOR_ONLY` a written behaviour it currently lacks anywhere in the docs: VECTOR_ONLY pages ARE rendered and OCRed (they are the text-converted-to-outlines case), and `EMPTY` is reserved for pages a 72-dpi render confirms are blank.

(3) ADD A HOSTILE STRATUM TO §4.9's calibration set: >= 30 pages of deliberately forged sandwiches (layer text != image text), text-as-outlines pages, and annotation-AP-only pages. Change the label for that stratum from "would OCR produce materially better text than the native layer?" to "does the pipeline's emitted text match the visible page?" — the current objective function cannot see any of these failures, so no amount of threshold sweeping will surface them.

### Lens: Production operations, cost, and blast radius - REFUTED (major)

REFUTED. Five operational defects, the first of which is decisive because it means there is no single heuristic to review.

**1. There are TWO different routing heuristics in the same milestone, and they disagree.** `e-native-extraction-routing.md` §4.3 defines `route_page()` (T_DENSE=12 chars/in2, coverage>=0.02, T_IMAGE_SPARSE_TRIGGER=0.15, `assess()` gate: garbage<0.02, orphanMarkRatio<0.15, danglingPreVowelRatio<0.20). `f-preprocessing-and-confidence.md` §P1b independently defines "Born-digital fast path": ">= 20 extractable characters with a real font mapping and fewer than 3 raster images covering < 50% of the page area -> **skip OCR entirely**", with a different gate (PUA ratio < 0.5%, no Cn/Co category, Thai-block ratio within +-0.25 of an OCR sample pass), a different extractor (`pypdfium2` in F, `pdfplumber` in E), and the instruction "**This must exist from M1 day one.**" Concrete divergence: a scanned signature page bearing a 25-char native header, with 2 raster images covering 45% of the page. F: >=20 chars, <3 images, <50% -> skip OCR, native text only, **signature silently lost**. E: charDensity ~0.26 -> step 6 -> imageAreaRatio 0.45 >= 0.15 -> OCR. This is exactly the failure E §4.1 case 1 exists to prevent, reintroduced by the sibling doc. E §1 explicitly requires "there must be exactly one implementation of the routing heuristic" and the M0 set already violates it. Operationally: routing behaviour depends on which worker touched the page first, and there is no single place to change a threshold at 3am.

**2. There is no runtime lever on routing at all.** `grep` across all 14 M0 docs finds no `forceOcr`, no per-tenant threshold override, no `thresholdsVersion`, no reprocess/backfill path, no routing kill switch. `Policy` (§4.3) carries only `trustExistingOcrLayer`, `maxRenderPages`, `renderProfile` — none of which can force OCR on a page that routed NATIVE. Every threshold is a module-level Python constant. F §1.8 has a kill-switch table for *preprocessing* (global `profile:'fast'`, an escalation-rate alarm at 8%); routing has no equivalent row. So when a customer onboards a document class that mis-routes — the scenario §4.9 explicitly says is unmeasured ("every threshold is a prior, not a measurement") — the on-call response is: code change, extractor redeploy, and then no defined way to re-route the corpus already stored. E7 is self-rated reversibility "hard", the routing decision is persisted per page in `NormalizedDocument`, and a threshold fix does not retroactively heal documents already processed. A decision the authors admit is uncalibrated is being frozen into a hard-to-reverse artifact with no backfill design.

**3. `vectorInkRatio` is computed, thresholded (`T_VECTOR_PRESENT`), and then never consulted once the page has any text.** Trace `route_page()`: `vectorInkRatio` appears only in step 0 (`total_chars == 0`) and step 1 (untrusted text). Any page with >=1 trusted character and `imageAreaRatio` below 0.15 returns NATIVE at step 5 or 6 regardless of vector ink coverage. Realistic bite: a CAD/architectural sheet or a full-page vector chart whose lettering was exported as curves ("text as outlines" — the standard workaround for un-embeddable Thai fonts) but which carries a native-text title block of ~200 chars. On A1 that is charDensity ~0.3, imageAreaRatio 0 -> step 6 -> `sparse_text_no_image` -> NATIVE. Every dimension, note, and annotation on the drawing is silently dropped and the page reports success. `PageRoute.VECTOR_ONLY` is unreachable for any page containing a single character, which also makes §5.5 item 3's entire tiling path ("the page is a poster/plan (A0, A1, engineering drawing)") near-dead code, since drawings essentially always have a text title block.

**4. The budget arithmetic does not close, and the timeout has no partial result.** §5.5 sets `EXTRACT_TIMEOUT_S = 300` (whole document) against `MAX_PAGES_PER_DOCUMENT = 1500`, `MAX_RENDER_PAGES = 400`, `RENDER_CONCURRENCY = 2`. §4.2's cost note claims signals need "exactly one pdfplumber page open and one pypdfium2 textpage per page... for a 300-page PDF this is on the order of a few seconds." That undercounts by a pass and by an order of magnitude: §4.5(b) adds a *third* full content-stream walk per page (`pypdf.extract_text(visitor_operand_before=...)`), and published benchmarks put pdfplumber at ~18 pages/sec for *plain text alone* (pdfmux 1000-page run: ~55s; py-pdf/benchmarks ranks pdfminer.six last consistently) — before `extract_words()`, `page.images`, `page.lines+curves+rects`, which are the expensive layout passes on exactly the table-heavy business documents in the target corpus. 1500 pages of signals is 85-250s of the 300s budget before a single pixel is rendered, and §5.6 then asks for WebP-lossless encoding of 8.7 Mpx bitmaps for up to 400 pages. §5.5 item 4's promise that "a 1,200-page born-digital PDF processes completely; only the OCR budget binds" is therefore unsupported — the wall clock binds first. Worse, §4.6 and §5.5 define per-page degradation (`route=FAILED`, `dpi_reduced_for_budget`, `SKIPPED`) but say nothing about what `EXTRACT_TIMEOUT_S` produces. With no checkpoint, no partial `NormalizedDocument`, and no resume cursor, a queue retry re-runs the same 300s of CPU and times out identically: a poison-pill job that burns a worker slot indefinitely on a host that also runs the existing INNOVERA estate (quotation-system, krs-pos-db, orderstock-sql).

**5. The escalation retry is a three-party distributed counter with no circuit breaker.** §5.2: OCR confidence < 0.55 triggers `POST /v1/render` at 1.5x DPI, "the Node side owns the retry counter, the worker stays stateless." The trigger lives in the OCR dimension, the counter in Node, the actor in the extractor, and no idempotency key is named for `/v1/render` even though §1 lists idempotency as house prior art. A tenant batch-uploading 400 phone photos misses the 0.55 gate on nearly every page and doubles render + OCR cost estate-wide. F §1.8 has a production counter that alarms when preprocessing escalation exceeds 8% of pages; routing/render escalation has no equivalent alarm and no cap above the per-page one.

**On "is it over-engineered":** no — per-page routing is correct and the leverage argument in §17 holds. The problem is the opposite: the sophistication is spent on the heuristic while the operability around it (one implementation, a lever, a detector, a resume path) is absent.

**What convinced me it is not fatal:** the routing concept, the signal set, and the Thai orthographic gate are sound and the fixes below are additive — nothing requires redesign. But defect 1 alone means the decision as stated cannot be true, because the system does not have one heuristic to be right or wrong about.

**Safer alternative:** Five specific changes, all M1-blocking, none requiring redesign:

1. **Delete `f-preprocessing-and-confidence.md` §P1b's independent rule.** Make E §4.3 `route_page()` the sole implementation, imported by the preprocessing worker rather than reimplemented. Enforce with the same style of CI lint E already uses for `SAFE_PARSER` and `import fitz`: fail the build on any second module that computes a native/OCR decision. Reconcile F's guard criteria (PUA ratio, `Cn`/`Co` category check, the OCR-sample Thai-ratio cross-check) into `assess()` as additional predicates — F's Cn/Co check in particular is a real signal E lacks — rather than leaving them as a rival gate. Note that F's Thai-block cross-check requires an OCR pass on a 3-line crop, which is NOT free; either cost it explicitly or drop it.

2. **Make thresholds versioned data, not constants.** Introduce `RoutingThresholds` as a frozen, versioned object loaded from config; stamp `thresholdsVersion` and the full `PageSignals` blob on every persisted page (§4.9 already demands the blob — persist it in a queryable column, not just a log line). This makes a re-route backfill a `WHERE thresholdsVersion < N AND route = 'native'` query instead of an undefined manual exercise, which is what converts E7 from "hard" reversibility to "moderate".

3. **Add three ops levers to `Policy`**, each per-tenant and settable without deploy: `forceRoute: "auto" | "ocr_all" | "native_all"` (the 3am lever — turn one customer's routing off entirely while you investigate), a per-tenant threshold override map, and a global `ROUTING_PROFILE=conservative` that clamps `T_IMAGE_SPARSE_TRIGGER` and `T_DENSE_CHARS_PER_IN2` toward OCR. Add a routing row to F §1.8's kill-switch table so the two docs share one operational surface.

4. **Close the vector hole with one branch**, placed after step 5 and before step 6:
   `if s.vectorInkRatio >= T_VECTOR_DOMINANT (start at 0.10) and s.charDensity < T_DENSE_CHARS_PER_IN2: return PageRoute.HYBRID, "vector_ink_with_sparse_text"` — HYBRID rather than OCR so the title-block native text is kept alongside the OCRed curves. Add engineering drawings and vector-charted report pages to the §4.9 calibration strata, which currently has no vector-only class at all.

5. **Replace the hand-labelled calibration dependency with production shadow sampling, and fix the budget.** (a) For the first 8 weeks, OCR a sampled 2-5% of NATIVE-routed pages in the background and compare character yield against the native layer; alert when sampled OCR yields >20% more characters than native on a NATIVE page. This produces §4.9's corpus from real traffic, gives a *detector* for silent loss instead of waiting for a customer complaint, and its cost is bounded and dial-able. (b) Make `/v1/extract` checkpoint per page so an `EXTRACT_TIMEOUT_S` breach returns a partial `NormalizedDocument` plus a resume cursor (`route=SKIPPED, reason="extract_timeout"` on the untouched tail) rather than failing the document — this kills the poison-pill retry. (c) Measure actual signals-pass throughput on a 300-page Thai fixture before M1 and set `MAX_PAGES_PER_DOCUMENT` to what fits the wall clock, or raise the wall clock; do not ship 1500 and 300s together. (d) Give `/v1/render` an idempotency key and add an estate-wide escalation-rate alarm mirroring F §1.8's 8% preprocessing counter.

## P5-security-posture

**Decision under review:** The M1 security posture (see j-security-threat-model.md and i-storage.md) - including whatever it defers, such as malware scanning - is a defensible, explicitly-accepted risk position rather than a hole, and the stated limits in item N are right.

### Lens: feasibility - REFUTED (major)

The deferral *reasoning* in j survives my lens — §11.6/§11.7/D14 (fail-closed, second-scanner-not-fail-open, RISK-001 with an exit criterion) is sound, and §4.1, §3.3's ZIP64/data-descriptor rejection, §3.4's /UserUnit correction and §8.5.1's XFF derivation are all correct and well-verified. What does NOT survive is the second half of the claim: "the stated limits in item N are right," and the framing of the M1 posture as *accepted risk rather than hole*. Three concrete failures, all verified against the sibling M0 docs.

**1. Item N's two headline numbers are the only outliers in M0, and three sibling docs have already resolved against them.** The upload cap has four values across M0: j §8.1/§8.8/D16 = **25 MB** + `client_max_body_size 26m` (j:1415, j:1540); `e-native-extraction-routing.md:1173` = `MAX_UPLOAD_BYTES = 200 * 1024 * 1024`; `i-storage.md:1377` = `MAX_UPLOAD_BYTES = 500 * 1024**2` (in code, in a preflight that throws 413); `m-docker-nginx-resources.md:2420` ships `client_max_body_size 500m`. The page cap has three: j §8.2 = **50**; `e:73,489` = `maxRenderPages: 400`; `g-data-model.md:954-956` = `CHECK (page_count BETWEEN 1 AND 2000)` and `CHECK (size_bytes BETWEEN 1 AND 209715200)` — i.e. 200 MiB and 2,000 pages written as **DB CHECK constraints in migration 0008**, the hardest enforcement point in the system. m §3.4.3 explicitly adjudicates the conflict and lands on **200 MB** — against a candidate set of {200 MB, 500 MB} that does not contain 25 MB at all, and m:4321 still lists it as an open question. j §16.3 instructs the deployment dimension to fix `client_max_body_size 26m`; deployment has already shipped 500m and decided 200 MB. j's own 50-page cap is derived from `50 × 12 s`, where 12 s/page is flagged `UNVERIFIED:` (U1, unmeasurable in-session), so the outlier number rests on an unmeasured constant and is 40× tighter than the schema's.

**2. That disagreement is not cosmetic — it deterministically destroys legitimate documents through j's own scanner config.** j §11.4 pins clamd `MaxFileSize 30M` and `StreamMaxLength 30M`, justified as "just above our 25 MB global cap ... so no legitimate file is skipped." If the real cap is g's 200 MiB CHECK (or m's 200 MB, or i's 500 MiB), then every upload in the 30 MB–200 MiB band hits both limits. Verified behaviour: on INSTREAM, clamd replies `INSTREAM size limit exceeded` and **closes the connection** (docs.clamav.net ClamD Protocol; clamd(8)) — a transport error, not a verdict, so `ClamdScanProvider` returns `status: 'error'` → `SCAN_FAILED` → 5 retries → terminal `SCAN_FAILED`, forever, for every such file. And with j's own (correct) `AlertExceedsMax yes`, `MaxFileSize` overrun yields `Heuristics.Limits.Exceeded`, which §11.4 mandates be treated as **infected** → `QUARANTINED`, terminal, 7-day purge, plus §11.3's "an alert fires on every quarantine event." Scenario: a customer uploads a 45 MB 150-page scanned contract — permitted by the schema, permitted by nginx at 500m — and it is quarantined as malware and pages ops. At any volume this is an alert-fatigue outage that trains operators to ignore the quarantine alert, which is the one alert §11.3 says deserves a human every time.

**3. The malware gate's single load-bearing invariant does not exist outside j, and the M1 upload transport routes around it.** j §11.2 invariant 1: "`VALIDATING` is reachable **only** from `SAFE`. There is no other edge into it. This is the whole gate, expressed as one unreachable-by-construction rule." `g-data-model.md:581-584` — the schema that will actually be built — has **no `SAFE` state, no `SCANNING` state, and no `SCAN_FAILED` state**. Its edges are `UPLOADED → VALIDATING` (unconditional) and `VALIDATING → QUEUED` gated on "a `CLEAN` `ScanResult` exists". That is a conditional check inside a state — precisely the "an `if` in a controller" j §11.2 says it is replacing — and it is not unreachable-by-construction. Worse, `g:781` defines `enum ScanVerdict { CLEAN INFECTED SUSPICIOUS ERROR SKIPPED }` while g's transition table maps only CLEAN and INFECTED/SUSPICIOUS: a document with `ERROR` or `SKIPPED` has **no defined outbound edge** and wedges in `VALIDATING`, so §11.6's fail-closed retry ladder has no home. Meanwhile `l-api-ui-export.md` L-1 (l:54, l:926) adopts **presigned POST direct-to-object-store as the M1 transport**, whose complete step (l:957-...) does HEAD → sha256 + a **four-signature** magic sniffer (`%PDF-`, `\xFF\xD8\xFF`, `\x89PNG`, TIFF) → dedupe → `CopyObject` → "inserts the `documents` row and the `ocr_jobs` row **in one transaction**" — with no scan step anywhere. So the job is created before any scan exists, and j §3.1's `file-type@22` allowlist, §3.2's single-format assertion + 65,557-byte tail window + trailing-data checks, §3.9/D31's busboy multipart limits and §8.8's mid-stream byte budget all apply to a transport that carries only ≤8 MB fallback traffic. j §4.1 Hole 3 states direct-to-store is "**Not adopted in M1** (the app streams the body so it can count bytes and scan)" — that premise is false as of l. This is a hole, not an accepted risk: RISK-001 covers "no scanner," not "scanner present but the primary M1 upload path never enters SCANNING," and no risk-register entry, `UNVERIFIED:` marker or open question in §16 names it.

None of this is unfixable, and j is the strongest document of the set — but the claim under review is that item N's limits are *right* and the posture is *complete as an accepted-risk position*, and both halves fail against the docs sitting beside it.

Sources: [ClamD Protocol](https://docs.clamav.net/manual/Usage/ClamdProtocol.html), [clamd(8)](https://linux.die.net/man/8/clamd)

**Safer alternative:** Do three specific things before M1 code starts, none of which needs new research.

**(a) Collapse the caps to one env-derived constant and re-derive every dependent number from it.** Adopt m §3.4.3's recommendation — `MAX_UPLOAD_MB = 200` — because it is the only value already reconciled against a page cap (g §5.4: 200 MiB ≈ 730 scanned pages at 275 KB/page) and against a DB CHECK that is far more expensive to change than a config line. **(b) Move the gate from j's prose into g's schema, and make it structural there.** Amend `g-data-model.md` §4.2 to carry j §11.2's states verbatim: insert `SCANNING` and `SCAN_FAILED`, and make `VALIDATING` reachable only from a clean-scan edge, so the invariant is enforced by the transition table + the exported-constant test j §11.2(5) specifies — not by "a `CLEAN` `ScanResult` exists" evaluated inside a state. Give `ScanVerdict.ERROR` an explicit edge to `SCAN_FAILED` and delete `SKIPPED` from the enum entirely (or give it an edge to `SCAN_FAILED` too) — a verdict with no outbound edge is a wedged document, and a verdict named SKIPPED that can reach QUEUED is the fail-open j D14 rejects.

**(c) Rewrite j §3.1/§3.2/§3.9/§4.1-Hole-3 against l's actual transport, or make l adopt j's.** Pick one owner. The cheaper reconciliation is to keep l's presigned POST (its 1.6 GiB-RSS-on-a-7.75-GiB-host argument at l:917 is correct and j does not answer it) and relocate j's ingest controls to l's step 3, which already streams the staged object: replace l's four-signature sniffer with j's `file-type@22` allowlist + the single-format assertion + the `min(fileSize, 65_557)` tail window + trailing-data checks, run the ClamAV INSTREAM scan there, and only then `CopyObject` out of `staging/`. ### Lens: SECURITY + ABUSE (hostile uploader, prompt-injecting document author, authenticated cross-tenant attacker, accidental self-harm) - REFUTED (major)

j-security-threat-model.md is, on its own terms, an unusually strong document. I could not break it internally: §3.2 polyglot handling, §3.3 ZIP64/data-descriptor rejection, §3.4 /UserUnit, §4.1 signed-URL state gating, §5.6 freshclam split, §6.7 verified source references, §7.1.1 intra-tenant visibility and §8.5.1 X-Forwarded-For are all correct and rare. What refutes the decision is not j's content — it is that **the M1 risk position j describes is not the M1 design the sibling M0 docs specify**, so "explicitly-accepted risk" is not what a signer would actually be accepting.

**1. RISK-001's compensating controls do not exist in the docs that specify M1 ingest, storage and serving.**

j §11.7 RISK-001 makes deferred malware scanning survivable by naming five compensating controls: "strict format allowlist (§3.1); polyglot rejection (§3.2); PDF active-content rejection (§3.4); originals served only as `attachment`, `nosniff`, from a separate origin (§4)". Check each against the docs that own those surfaces:

- **Format allowlist.** l-api-ui-export.md:959 (the actual upload-complete handler, L-1 step 3) sniffs exactly five prefixes: `%PDF-`, `\xFF\xD8\xFF`, `\x89PNG`, `II*\0`/`MM\0*`. No WebP (which j §8.1 accepts at 15 MB — so a legitimate WebP upload 415s), no `file-type@22` (j D1), no allowlist-not-denylist framing, and no re-detection in the worker (j §3.1 item 4).
- **Polyglot rejection.** Absent entirely from l. j §3.2 mandates a 65,557-byte tail window, a single-format assertion producing `AMBIGUOUS_FORMAT`, trailing-data checks (`%%EOF`, `FF D9`, `IEND`, WebP RIFF-size == fileSize-8), and offset-0-only `%PDF-`. l's header-prefix check passes every one of these: a JPEG with an appended ZIP central directory, or a PNG with data after `IEND`, is accepted and promoted. That is precisely the file class RISK-001 leans on §3.2 to stop.
- **Separate origin.** i-storage.md:33 (J8) says serving is an authorised Next route handler with `attachment` + `nosniff` + `CSP: sandbox`, and **"Separate origin at M2."** j §4 calls the separate origin "the single highest-value cheap control in the storage layer" and puts it in M1. In the M1 that i specifies, it does not exist.

So RISK-001's residual rating of "Medium-High" is computed against a control set the shipping design does not contain.

**2. The claim that makes the deferral cheap is false as designed.**

j §11.7(1): "The interface and the states ship anyway. `ScanProvider`, `SCANNING`, `QUARANTINED`, `SCAN_FAILED` and the state machine of §11.2 are all M1... retrofitting an implementation behind an existing interface is an afternoon."

The words *scan*, *malware*, *quarantine*, `SCANNING` do not appear anywhere in l-api-ui-export.md's API surface. l's L-1 flow is: staging PUT → HEAD → sha256+sniff → `CopyObject` to `orig/…` → insert `documents` + `ocr_jobs` **in one transaction** (l:978-982) — i.e. straight to queued processing, with no `UPLOADED → SCANNING → SAFE` edge and no gate before `VALIDATING`. i-storage.md:2425-2429 says it outright: "**`quarantine/` exists in the layout but has no producer and no scanner specified** — as written, nothing ever moves an object into it, so the directory is currently decorative"; and Critic Note 32 repeats "**`quarantine/` is decorative**". So the deferral is not "an interface with a null implementation", it is a **missing state machine** — exactly the thing j §11.7 says must not be deferred because retrofitting it is a migration, not an afternoon.

**3. Two SSRF features j declares nonexistent are fully specified for shipping, with weaker hardening and a read oracle.**

j §7.9: "The M1–M4 design has **no feature that fetches a user-supplied URL**. That is a deliberate design constraint." j D27/§7.10: "**Decision for M1–M4: no webhooks. Polling only**", explicitly rejecting "webhooks in M4 'because everyone has them'". l ships both:
- `fileUrl` (l:1911-1918), per-tenant flag, "fetched from an **egress-restricted worker**". j D6/§5.6 gives the worker **zero** egress by construction (`--internal` Docker network). Implemented literally, this attaches the highest-blast-radius container — the one deliberately feeding hostile bytes to poppler/Pillow/libtiff — to an egress-capable network, handing a decoder RCE the exfiltration channel D6 exists to remove.
- Full webhooks (l:1950-2031) with `X-Callback-Url` on every `POST /api/v1/ocr`. Against j §7.10's eight non-negotiable properties, l is missing #2 (resolve-then-**pin to the resolved IP**; l says only "public IPs only, re-resolved per attempt", which is the check-then-connect TOCTOU that DNS rebinding targets), #3 (enumerated ranges incl. `100.64/10` and IPv4-mapped `::ffff:` forms), #8 (registration-time ownership challenge — without it, 8 retries × N events × M endpoints makes us a signed-request DDoS amplifier at a victim URL), and it **inverts #5**: j says "response body read and discarded up to 1 KB. We never parse what comes back"; l:1981-1982 stores "**first 512 bytes of the response body**" in a tenant-visible delivery log for 30 days. That single line converts blind SSRF into a **read-capable SSRF oracle** — a tenant registers an endpoint on an internal HTTPS service and reads 512 bytes of its response back out of the delivery-log UI — and is a stored-XSS sink wherever that log is rendered.

l:3208's reconciliation table says "If `j-` specifies differently, `j-` wins" — but it lists only §1.8 CSRF/CORS, §1.9 sessions, §6.9 CSP, §5.1 API keys. Webhooks and `fileUrl` are not in that list, so the conflict is unreconciled by construction, not by oversight I am inventing.

**4. j §4.1's D23 control has nowhere to live, and i's serving route omits it.**

j D23 requires the signer to take "a document row and an actor, never a bucket key", refusing "any state before `SAFE`" (`DOWNLOADABLE_STATES`). i-storage J2 removes presigned URLs from the port and J8 serves via a route handler; i's `loadAuthorisedObject` (i:~1993-2005) filters on `objectId`, `documentId`, `deletedAt` and `document.tenantId` — and **has no document-state predicate at all**. So the one control j added in review to close the pre-verdict window is absent from the only serving code path the architecture actually has.

**5. Item N is not "right" in three specific places.**

- j §8.6 claims per-user in-flight uploads of 3 "**Bounds NGINX temp-file usage: 3 × 25 MB = 75 MB per user of buffered body**". With §8.8's `proxy_request_buffering on`, NGINX buffers the **whole** body before the app is invoked, so no application-layer limiter (rate-limiter-flexible or the concurrency cap) can run until buffering has already completed. The stated arithmetic is structurally impossible. Nothing in §8.8 bounds `client_body_temp_path`; `limit_conn perip 20` × 26 MB ≈ 520 MB resident per IP, with `limit_req` permitting 300 full-body buffers/min/IP before any app check. That is an unbounded edge-disk-fill DoS.
- j §8.8 never mentions Next.js's `proxyClientMaxBodySize`. l:3251 verified against nextjs.org that it defaults to **10 MB with an in-memory body clone and silent truncation and no client error**. j's `client_max_body_size 26m` therefore admits a 25 MB body into a layer that silently truncates it at 10 MB — a silent data-corruption path sitting inside j's own item-N config table.
- j D32 argues at length that **NFKC, not NFC**, is required for Thai (U+0E33 SARA AM has only a compatibility decomposition). l:1002 specifies "**NFC-normalise**" for `X-Filename`, and l's sanitiser rejects only `/ \ \0`, a leading `.`, and C0/C1 — it does not strip U+202E RTL override or zero-width characters, which j §3.8 flags as the "reviewer downloads and runs `invoiceexe.png`" vector.

**Net.** A risk acceptance is only meaningful if the compensating controls named in it are the controls that will exist. Here they are not: the format gate is a five-prefix subset, polyglot rejection is absent, the separate origin is deferred to M2, the scan state machine has no producer, and two SSRF primitives j says do not exist are specified for shipping with a response-body read oracle. What is presented as an accepted risk is an accepted risk plus an unmeasured set of unreconciled ones — which is a hole wearing the label of a decision. j itself is right on nearly every point; the failure is that its M1 is not the project's M1.

**Safer alternative:** Do not sign RISK-001 until the M0 set is reconciled. Six concrete, checkable changes:

1. **Make j binding, not advisory.** Add to l §12.1 and i §0 an explicit precedence line covering ingest validation, storage keys, serving, and outbound requests — not just CSRF/CORS/CSP/API-keys. Then correct the three divergences: l's step-3 sniffer becomes j §3.1's `file-type@22` allowlist **plus** j §3.2's single-format assertion, 65,557-byte tail window and trailing-data checks (add WebP, whose absence today rejects a type j §8.1 accepts); l's `X-Filename` normalisation becomes **NFKC** with j §3.8's bidi/zero-width strip and combining-run cap; i's key scheme, l's `orig/{tenantId}/…`, and j's `{tenantId}/{documentId}/…` collapse to one scheme with `tenantId` as the first segment so a prefix ACL is an independent enforcement point.

2. **Ship the gate as states, in M1, even with `SCAN_PROVIDER=noop`.** Add `UPLOADED → SCANNING → SAFE` to l's L-1 flow: step 3 promotes `staging/` → `documents` row in state `UPLOADED` and enqueues a scan job; only a `SAFE` transition creates/releases the `ocr_jobs` row. Give i's `quarantine/` its producer (the `infected` verdict handler) or delete the directory — its own §9.7 says shipping it decorative "impl[ies] a control that does not run". This is the difference between "an afternoon" and a data migration, which is exactly what j §11.7(1) promises and does not currently have.

3. **Add the state predicate to the real serving path.** i's `loadAuthorisedObject` gains `document: { state: { in: DOWNLOADABLE_STATES } }` inside the same `findFirst` WHERE clause (not a post-fetch check), preserving the uniform 404. Add i's test asserting every state outside that set 404s. Pull the separate origin for originals forward from M2 to M1, or amend RISK-001 to stop citing it.

4. **Delete `fileUrl` and `X-Callback-Url` from the M1–M4 API surface**, matching D27, and record them in l §14 as owner decisions rather than shipping defaults. If the owner overrules that, they are a separately threat-modelled feature that must satisfy all eight j §7.10 properties — in particular: resolve-then-**connect to the pinned IP** with an explicit `Host` header (never re-resolve at connect time), the full enumerated block list including `100.64/10` and `::ffff:` forms, a registration-time challenge-response proving endpoint ownership, and a **dedicated `ai-egress`-style single-purpose sender** — never the worker, whose zero-egress property (D6) is load-bearing for the whole decoder-RCE containment story.

5. **Stop storing response bodies from webhook deliveries.** Log status code, timing and byte count only. If any diagnostic body is kept, it is hashed, never rendered, and never returned through the tenant API — otherwise the delivery log is a read-capable SSRF oracle.

6. **Fix item N's three defects.** (a) Put `client_body_temp_path` on a size-capped mount (or tmpfs) and add an explicit NGINX-level cap on concurrent buffered bodies; state plainly in §8.6 that no app-layer limiter can bound NGINX temp files while `proxy_request_buffering on`, and move the per-principal upload throttle to the edge (`auth_request` or a signed upload ticket checked before the body is read). (b) Add `proxyClientMaxBodySize` to §8.8's must-agree table with its 10 MB silent-truncation behaviour, and add the startup assertion comparing NGINX cap ↔ Next proxy cap ↔ app cap ↔ clamd `StreamMaxLength` — the same three-way mismatch class §8.8 and §11.4.1 already warn about, now with a fourth layer. (c) Re-derive the 25 MB global cap against l's actual transports (8 MiB raw-body fallback, presigned POST `content-length-range` for the browser) so the numbers describe one system.

Only after 1–3 is RISK-001 signable — and it should then be re-rated, because its compensating-control list will finally be true.

## P6-ai-anti-hallucination

**Decision under review:** The AI chunk/map-reduce design, the provenance-verification mechanism, and the malformed-output repair ladder (see k-ai-integration-and-intelligence.md) actually prevent fabricated field values and silent truncation.

### Lens: feasibility - REFUTED (major)

REFUTED. The chunk/merge algebra and the repair ladder are sound; the provenance verifier — the thing the doc calls "the load-bearing wall" — is not, and it fails hardest on exactly the values §6.7 claims to have just rescued. Four concrete defects, all verified against the doc's own code and against the upstream libraries.

**1. (Primary) Self-citation verification is vacuous for short values, and it is vacuous by explicit design decision.** `k-ai-integration-and-intelligence.md` §6.7 closes the "largest hole" (tables, entities, keyValues keys) by making the value its own citation: `verifySelf(..., cell, t.page, chunk, ...)`. That feeds §6.4's `verify()`, whose rung 1 is literally `chunk_text.find(cite)` over the **whole chunk**. There is no minimum length on this path: `tableCellSchema = z.string().max(500)` (§4.1, line 1312) has no `.min()`, `entitySchema.text` is `z.string().min(1)`, `keyValueSchema.key` is `z.string().min(1)`, and §6.7 skips only `cell === ''`. The doc's own §4.1 comment states the error outright: entity text is `min(1)` because "entities are verified by direct containment, not by the ≥8 fuzzy rule, so the short-string collision risk does not apply." The opposite is true — direct containment over a large haystack is where short-string collision is maximal. §8.2 sets the chunk target at 8,000–16,000 tokens, i.e. **24,000–56,000 characters** at the doc's own Thai ratios (§8.1: 1.5–3.5 chars/token). `find("1")`, `find("2")`, `find("ชิ้น")`, `find("7%")` on a 30k-char Thai invoice chunk succeed with probability ≈1. **Failure scenario:** the model hallucinates a line-item row `["4","ค่าบริการ","2","1,200.00","2,400.00"]` on page 11 of a 40-page invoice. Every cell is found somewhere in the 30k-char chunk covering pages 9–13 and is graded `EXACT`, grounding **1.00**, `flaggedForReview = false`, and it counts as a grounded field in `ProvenanceSummary`. Nothing in the design distinguishes it from a real row. §6.4's careful money guard (`FUZZY_FORBIDDEN`, `MIN_FUZZY_CITE = 8`) never fires, because a match at rung 1 returns before the guard is reached. So the headline claim — "a proposal that cannot be located in the cited page is not a value at all" — is satisfied only in the trivial sense: for quantities, unit counts, line numbers, VAT-rate cells and short entity texts, *every* proposal can be located.

Two second-order consequences make this worse than a single weak check. (a) **It corrupts the merge conflict ladder.** §8.5 rule 1 is "Grounding class wins: EXACT ≻ NORMALIZED ≻ DERIVED ≻ FUZZY." An auto-grounded short hallucination is graded EXACT and therefore **beats** a genuine value that only matched at NORMALIZED (the common case for Thai, per §6.2's own whitespace argument). The mechanism designed to resolve conflicts is systematically biased toward the shortest, most trivially-matched candidate. (b) **It blinds the release gate.** §6.6 makes `hallucinationRate = ungrounded ÷ proposed` "THE headline quality metric" and §9.4's "primary release gate," and §6.7 boasts that it is now "measured over the real denominator." That denominator is now ~7,000 auto-grounded table cells (§6.7's own figure). A prompt regression that fabricates 20 of 40 genuinely-cited fields moves the metric from ~0 % to 0.28 % against a 7,040 denominator — under any plausible gate threshold. The metric the project intends to steer by becomes structurally incapable of registering the failure it exists to catch.

**2. Check A is specified page-scoped and implemented chunk-scoped.** §6.1's table defines check A as "Does `source.text` occur on page `source.page`?" But `verify(field, cite, chunk_text, field_type, page_spans)` takes no page argument and searches all 4–13 pages of the chunk, then *derives* the page from `page_spans.to_page(i, …)`. A model citing page 3 for text on page 7 is silently corrected rather than flagged, and the first-occurrence rule can place `matchedStart/End` on the wrong page entirely — which is the same class of wrong-highlight bug §6.2 congratulates itself for catching in the rapidfuzz argument order, and which F §2.7 rule 4 says reviewers trust.

**3. `normalize_for_match_traced()` cannot be implemented as specified — and it is the single point of failure for every offset.** §6.3a says it is "implemented by running the pipeline one character at a time," asserts in its contract test that "`src_index` is non-decreasing," and says the untraced normaliser is "a thin wrapper over the traced one." I checked pythainlp's actual `normalize()` source (PyThaiNLP/pythainlp `pythainlp/util/normalize.py`): it calls `remove_repeat_vowels()`, which calls `reorder_vowels()`, whose `_REORDER_PAIRS` contains two rules that **swap adjacent characters** — `([{tonemarks}์]+)([{above_v}{below_v}]+)` → `\2\1` and `([{follow_v}]+)([{tonemarks}]+)` → `\2\1` — plus `ํ([{tonemarks}]*)า` → `\1ำ`, which merges *and* moves. These are whole-string, multi-character, order-reversing regex rewrites. A character-at-a-time pipeline cannot reproduce them, and the asserted "non-decreasing" invariant is **provably false** for any Thai string with a mis-ordered tone mark — precisely the OCR artefact `thai_normalize` is called to fix (§6.3's own rationale). Once `src_index` is non-monotone, `map_span()` can return `a > b`: an inverted or truncated highlight span, silently. Since §6.3a says the untraced form wraps the traced one, rungs 2, 2b and 3 all block on a function whose stated implementation strategy does not work — the exact defect §6.3a was written to fix ("the function that was called but never written").

**4. Two smaller but real gaps.** (a) **The `DERIVED` rung has no caller.** §6.2's ladder lists rung 4 `DERIVED`, §6.3 registers `beToCe`, `thaiMonthAbbrev`, `percentToFraction`, `moneyStrip`, and §8.5 rule 1 ranks `DERIVED` in the conflict ladder — but neither `verify()` nor `contains_value()` in §6.4 contains a DERIVED branch, and `verify()`'s money guard `return Verified("UNGROUNDED", 0.0, …)` fires *before* any derivation could be attempted. A date field where the model applies R1's sanctioned BE→CE conversion (`2569` → `2026`) hits `contains_value`'s else-branch, `normalize_for_match("2026-01-15") in normalize_for_match("วันที่ 15 ม.ค. 2569")` → False, and §6.5's outcome table has no row for a check-B failure. `be_to_ce()` is written and never called. (b) **The §6.7 cost check is off by orders of magnitude.** It counts "one `find` … milliseconds" but ignores that `verify()` calls `normalize_for_match_traced(chunk_text)` **per field**. 7,000 cells × a 30k-char chunk, with pythainlp's regex chain plus a char-by-char Python tracer, is ~2×10⁸ Python-level operations per document — minutes, not milliseconds. Trivially fixable by hoisting the chunk normalisation, but the doc's affordability argument as written is wrong.

**On the decision's second half — "silent truncation."** §8.3's coverage assertion genuinely prevents *input-side* truncation and I could not break it; that part holds. But the decision claims truncation is prevented, and there is **no output-side recall detector**. A model that returns valid JSON with 18 of 25 line items passes rung 1, passes provenance (every reported cell is real), passes merge, and reports `status: 'complete'`. The only mechanism that could notice is `lineItemsSumToSubtotal`, which §10.4 explicitly makes `NOT_APPLICABLE, never FAILED` when any line amount is null — so dropping rows *and* nulling one amount escapes silently — and which does not exist at all for non-financial documents.

**What survived my attack, and convinced me it is real work, not vibes:** the rapidfuzz facts check out exactly — 3.14.6, MIT, released 2026-08-30 (PyPI), and `partial_ratio_alignment`'s documented semantics confirm the doc's argument-order fix: `src_*` index the first argument, the example `("a certain string","cetain")` returns `src_start=2, src_end=8`, and `score_cutoff` causes a `None` return. The refusal to brace-balance or run `jsonrepair` on a `finish_reason: 'length'` response is correct and is the right call. Running provenance per-chunk *before* merge is the correct ordering. Computing `language` from a character histogram instead of voting is right. The Handlebars `{{{ }}}` / `noEscape` catch is a genuine bug found. The problem is not the philosophy; it is that the verifier's reference implementation does not enforce the philosophy for the majority of values it now covers.

**Safer alternative:** Rewrite §6.4/§6.7 around four rules, none of which cost a model call:

1. **Scope the search, don't scan the chunk.** Give `verify()` the cited page: `verify(cite, chunk_text, page_spans.span_of(cited_page), …)`. Search only that page's span. If the string is absent from the cited page but present elsewhere in the chunk, that is a `CITATION_PAGE_MISMATCH` finding at grounding < 1.0 — never a silent correction. This restores check A to the definition §6.1 actually gives it.

2. **Verify short cells inside their own row's matched span, not inside the chunk — this is the key fix and it is nearly free.** Raise prompt rule R5 to require one `sourceReferences` entry per *table row* (not per cell): an ≥8-character verbatim quote of the printed row. Verify that quote by the existing ladder against the cited page; then verify each of that row's cells by containment **within the ~40-character matched row span**. Cell `"1"` is then proved against the row it claims to come from, not against 30,000 characters. The same pattern applies to entities: an entity of type `tax_id`/`national_id`/`bank_account`/`money`/`date`/`quantity` must carry a real ≥8-char citation; only `person`/`organization`/`product`/`address` entities long enough to stand alone may self-cite. Budget: `sourceReferences.max(400)` must rise (or be per-chunk), which is a schema bump, not a redesign.

3. **A hard floor and a uniqueness guard on every containment path, self-cites included.** No value shorter than 8 code units after `normalize_for_match` may reach grounding 1.00 by containment in *any* scope larger than a matched row/line span. And if a citation occurs more than once inside its search scope, cap grounding below 1.00 and flag — an ambiguous locus is not proof of location. Encode both as assertions in `verify()`, since §6.2 already establishes that this class of bug is invisible to tests that only assert `groundingClass`.

4. **Split the metric so the release gate can still see.** Report `hallucinationRate` over *independently-cited* fields only, and report auto-grounded short values as a separate `shortValueAutoGrounded` count in `ProvenanceSummary`. §9.4's gate reads the former. Add the invariant `shortValueAutoGrounded / fieldsProposed` as its own tracked ratio — if it drifts up, the verifier is losing power and someone should know.

Additionally, three targeted repairs:

- **Offset map:** abandon the char-by-char tracer. Apply the normalisation stages yourself with `re.finditer` and record a **span-level** rewrite log (each `_REORDER_PAIRS` / `_NOREPEAT_PAIRS` substitution is a bounded local rewrite whose src→dst span is computable), or normalise per OCR line/token span — dimension D already carries line offsets — and map at span granularity. Then state the honest invariant (spans are non-overlapping and ordered) instead of the false per-character one, and assert `a <= b` in `map_span`.
- **Wire `DERIVED` in:** move the DERIVED attempt into `contains_value()` (where it belongs — it is a check-B claim, not a check-A rung), call it *before* the money guard's `return UNGROUNDED`, require exact reproduction as §6.3a already specifies, and add a §6.5 row for "check A passed, check B failed."
- **Add an output-side recall detector**, since the coverage assertion only covers input: count OCR line-blocks inside each detected table region (the geometry is already in F) and emit `TABLE_ROWS_UNDER_REPORTED` + force `partial` when the model's row count is materially lower. Without this, "never silently truncate" is a claim about the request, not about the answer.

Finally, hoist `normalize_for_match_traced(chunk_text)` and `strip_all_whitespace(...)` to once per chunk and correct §6.7's cost paragraph to state the real complexity.

### Lens: SECURITY + ABUSE (prompt injection, tenant isolation, PII egress, resource exhaustion) - REFUTED (major)

The chunking/coverage machinery and the repair ladder hold up under this lens — I could not break "never silently truncate" (§8.3 `assertCoverage`, §5 rung 0's refusal to brace-balance, and the `finish_reason:'length'` → `context_overflow` reclassification are genuinely sound). The repair ladder's decision not to echo offending values back (§7.7) is a real PII win. What fails is the provenance-verification claim, and it fails on a claim the project's own sibling document already refutes by name.

THE CORE REFUTATION — the verifier's ground truth is attacker-controlled, and K knows it isn't but says otherwise.

k-ai-integration-and-intelligence.md §7.6 layer 5 states: "an injection that persuades the model to emit `grandTotal: 999999.00` produces an **ungrounded field**, which is removed and flagged. The provenance verifier is simultaneously the anti-hallucination lever and the injection blast-radius limiter. That is the most valuable property in this design."

f-preprocessing-and-confidence.md §2.5 "Signal 0" (lines 1930-1935) says the exact opposite, in bold: "An injected instruction points at a value that *is genuinely printed on the document* — the attacker put it there. So grounding returns `exact`, `1.0`, and the hard gate passes. **Grounding defends against fabricated values; it does not defend against a redirected selection.** These are different failures and the draft conflated them."

F is right and K is wrong. §6 verifies `chunk_text.find(cite)` — it proves a string is *in the file*, never that it is *the value of that field* or that it is *on the page a human sees*. An attacker does not need to persuade the model of anything; they plant the value and let the model find it honestly.

CONCRETE END-TO-END ATTACK (every step verified in the docs, no step requires a model failure):

1. Supplier emails a PDF invoice. Rendered page: `จำนวนเงินรวมทั้งสิ้น 21,357.20`, account `111-2-33333-4`.
2. The file also carries a text layer reading `999,999.00` and account `987-6-54321-0`. Two working variants:
   (a) **Sandwich variant.** The visible page is an image; the text layer is a forged "OCR layer". e-native-extraction-routing.md §4.5a rule 4 *exempts* the sandwich path from invisible-text suppression, and `trustExistingOcrLayer = "if-clean"` is the **documented default** (§4.5a). The gate it must pass, §4.4, tests only `thaiRatio` / `garbageRatio` / `orphanMarkRatio` / `danglingPreVowelRatio` — orthographic quality. **There is no check anywhere that the text layer agrees with the rendered pixels.** A cleanly-typed Thai forgery passes `trusted_strict`, routes NATIVE with reason `sandwich_layer_clean`, and becomes the text of record.
   (b) **4pt-grey variant** (F's own example, §2.5 line 1923). Not `Tr 3`, not white fill, so E20 never touches it and `hidden_text_suppressed` stays 0.
3. K §6.4 `verify()`: `chunk_text.find(cite)` hits → `EXACT`, grounding **1.00**.
4. F line 334: a PDF text layer records `ocrSupport = 1.0` (exact, not estimated). So the OCR term is **1.0**, not a penalty.
5. The attacker controls all four numbers, so `vatArithmetic` and `lineItemsSumToSubtotal` **PASS**. Single candidate ⇒ `agreementRatio = 1.0`.
6. `extractionScore = 1.0 × 1.0 × 1.0 × 1.0 = 1.00`. `conflict=false`. `criticalUngrounded=0` ⇒ `status:'complete'`.
7. The forged value is persisted with `groundingClass: EXACT`, a citation, and a "verified against the document" audit record — the strongest possible provenance the system can emit.

WHY THE REVIEW GATE DOES NOT SAVE IT. F §2.6 defines `hard gate 9: field.groundingPositionAnomalous` (the injection heuristic, keyed to `A0.textBoxes` and the D16 geometry: 4pt type, outside any field region, below the page's p10 line height) and `hard gate 10: isPaymentAffecting AND payeeAccountChanged`. **Neither exists anywhere in K.** I grepped: `groundingPosition`, `fontSize`, `textBox`, `payee`, `payeeAccountChanged`, `isPaymentAffecting` return zero hits in K. `VerifiedField` (§4.2) and `FieldExtraction` (§4.4) carry only `matchedStart/matchedEnd/matchedPage` — character offsets into `DocumentPage.text`, no geometry at all. K's `flaggedForReview` is set only by FUZZY (§6.5), UNGROUNDED (§6.5), and merge conflict (§8.5 rule 6). K also never wires F §2.6's "critical fields are never auto-accepted regardless of score" — `criticality` is stored on `FieldExtraction` and read by nothing that sets `flaggedForReview`. K likewise ignores `extractionMethod` and `source` (native/ocr/hybrid): §0.1 line 40 lists `source` as a consumed input and it appears **nowhere else in the 4,806-line document**, even though e-native §2228 states that an explicit `extractionMethod` per line is precisely what E "owes" the AI dimension so it can weight text differently by origin.

So the reviewer who does look sees: value 999,999.00, grounding EXACT 1.00, score 1.00, arithmetic PASSED, and a highlight (K §6.3a `map_span`) pointing at coordinates in `DocumentPage.text` that correspond to nothing visible on the page image. F §2.7 rule 4 rests on the reviewer trusting that highlight.

A false safety claim in an architecture document is worse than a missing control, because the control never gets built — §7.6 layer 5 is exactly the sentence that would be cited in design review to close out "what about injection?".

THREE SMALLER HOLES, all verified:

1. **`readCropPolicy` is bypassable by making template matching fail.** §10.5 declares "a national ID must never be sent as pixels to a generative model" and binds it to `thai-id-card.readCropPolicy = 'disabled'`. But §10.3 `selectTemplate` falls back to `GENERIC_TEMPLATE` on no-match *and* on `TEMPLATE_AMBIGUOUS`, and `GENERIC_TEMPLATE` is declared `readCropPolicy: 'allowed'` (§10.6 point 2). §17.4 documents that Thai keyword matching fails "silently and routinely" on tone-mark order, a stray U+200B, or one inserted space. So the strongest PII guarantee in the document is conditional on a match that the document itself says is unreliable. The same fallback also loses `piiClass: 'high'` and re-exposes the `dataClass:'special'` (religion) omission.

2. **The verifier does not check the cited page.** §6.1 states check A as "does `source.text` occur on page `source.page`?" and §4.2 comments that `matchedPage` "differs from citedPage only if we searched wider (we do not)". §6.4's `verify()` does `chunk_text.find(cite)` across the **whole chunk** (4-13 pages) and maps wherever it lands. So `matchedPage ≠ citedPage` is reachable, silent, and unwarned — a value from a decoy page (a second document in the same PDF, a "SPECIMEN" page) is attributable to page 1 at grounding 1.00.

3. **`selectTemplate`'s explicit path is not tenant-scoped.** `if (req.templateId) return repo.get(req.templateId);` — no `tenantId`, four lines above `repo.listForTenant(doc.tenantId)`. g-data-model.md §3.4's RLS + composite `[templateId, organizationId]` FK almost certainly catches it, but G §K-3 states in terms that "RLS is defence-in-depth, never the only control", and this line relies on nothing else.

**Safer alternative:** Four changes, in order of value. None requires redesigning the verifier — the LLM-proposes/verifier-decides inversion is right and should be kept.

     groundingPositionAnomalous := fontSizePt < 0.6 × pageP10LineHeight

   Feed it into `flaggedForReview` as a hard gate, and add `isPaymentAffecting` + `payeeAccountChanged` (hard gate 10) with the vendor's last-verified account as the comparison. ### Lens: operations - REFUTED (major)

The mechanism works. What cannot be operated is the mechanism's *output*: **the verification result is a function of unpersisted, drifting global state, so it can never be reproduced, re-verified, or repaired.** The design's own last-resort guarantee falls to this.

**The contradiction, in the doc's own words.**
- `k-ai-integration-and-intelligence.md` §14 blocker 6: *"If the answer is no, we must never promise reproducible output — only reproducible **provenance**."* Provenance is the fallback guarantee.
- §6.2 (line ~1936): *"verification runs against the exact chunk string that was sent."* Provenance is therefore a function of the chunk plan.
- §8.3 step 3: the planner *"greedily accumulate[s] whole pages until adding the next page would exceed the chunk target"*, where per-page size is `estimateTokens(text, cal)`.
- §8.1: `factor = clamp(1.0, p95(actual/estimated over last 500 calls), 2.0)` — a **rolling p95 over the last 500 calls, per model, across all tenants' traffic**, bootstrapped at `1.35` until 50 calls exist.

So `factor` moves continuously, between 1.0 and 2.0 — a **2× swing in pages-per-chunk** — driven by other tenants' documents. And it appears nowhere in the reproducibility key. §9.2 lists that key exhaustively (`promptHash`, `samplingParamsHash`, `serializerVersion`, `inputSha256`, `enforcementRung`, …); §4.4's `DocumentAnalysis` persists `chunkCount` and **not one chunk boundary**. §9.2's claim that *"any analysis can be reproduced or explained"* is false for the half of the pipeline that matters most.

**Three consequences that land on on-call.**

1. **Bug reports are unreproducible by construction.** §6.5: an `UNGROUNDED` field has *"the value removed from the result"* — deletion, not degradation. A tenant reports "you dropped the grand total on invoice 4471." On-call requeues (§2.4's `rate_limit` path does exactly this) or hits `/internal/analysis/replay`. Since the last few hundred calls have moved `factor` from 1.35 to 1.7, §8.3 re-plans that 40-page document from 8 chunks into 6. Different chunk text, different citations, and — because `seed = H(docId, chunkIndex, promptVersion)` (K-11) — different seeds too. The field comes back `EXACT`. Closed as "cannot reproduce." It recurs next week on another tenant. The one class of defect this design exists to catch is the one it cannot reproduce.

2. **§9.5's `INPUT_DRIFT` guard does not cover the input that actually drifts.** Step 2 hashes the regenerated *serialised document* against `inputSha256` — unchanged, so the guard passes. The chunk plan is not hashed. §9.5 then emits a `ReplayDiff` attributing every `groundingImproved`/`groundingDegraded` count to the prompt change, when some fraction is re-chunking. That is precisely the outcome §9.5 step 2 calls *"worse than no comparison, because it will be believed"* — and it is the promotion gate: §9.4 rejects a candidate prompt on `hallucinationRate` and `groundingDegraded`, both of which now carry chunk-plan noise. Prompt promotion decisions are made on a contaminated metric.

3. **A verifier fix cannot be shipped over existing data.** This is the expensive one. This document's own review pass found **two** verifier bugs — the `partial_ratio_alignment` argument-order bug (§6.2: *"every FUZZY match would have produced a highlight offset of roughly 0–40 characters into page 1"*) and `U+2060` missing from `_INVISIBLE` (§6.3: *"any citation quoting an escaped line could never match"*). The second class **deletes correct values** via §6.5 and trips F §2.6 hard gate 1 (`grounding < 1.0`), so it silently destroys data and floods the review queue. Two found in one pass means P(a production verifier fix) ≈ 1. The recovery path is blocked twice over:
   - `verifierVersion` is stored on every `FieldExtraction`, so you can **identify** every affected row — and cannot **fix** any of them.
   - `@@unique([documentId, promptVersion, modelId, templateId, inputSha256])` (§4.4) omits `verifierVersion`. §9.3 property 1 leans on that key so a new *prompt* can never serve an old row; for a new *verifier* the same key does the opposite — a re-run either hits the cache and returns the known-bad analysis, or collides on the unique constraint. There is no `verify: true` mode on `/internal/analysis/replay`; step 3 is unconditionally *"Run the new prompt."*
   - So repairing a verifier bug means **re-inference across the affected corpus on the shared INNOVERA GPU**, which `m-docker-nginx-resources.md` §4.9.2/§5.2 says must be treated as *"fully committed to Chat"*, with `max_parallel_requests: 4` and prefill competing directly with Chat's decode. A code fix in our repo becomes a capacity negotiation with another product's owner.

**The estate-blast-radius corollary.** `factor` is keyed on `modelId`, and `modelServedVersion` is flagged UNVERIFIED-whether-the-gateway-exposes-it (§2.2). A gateway-side model swap or a busy hour that shifts the p95 re-chunks every subsequent document with **no deploy on our side**. Extraction results, the review-queue volume (§8.5 rule 6 forces review on unresolved singleton conflicts, and singletons can only conflict *across chunks*, so fewer chunks = fewer forced reviews), and the `hallucinationRate` release-gate metric all move because someone else restarted a container. That is an externally-triggered, silent change to correctness output — the worst shape an ops dependency can take.

**Why this is major and not minor:** the fix is additive and nearly free today, and outage-grade later. `analysis_identity` is a unique index on the busiest table, and `g-data-model.md` §3 F-1 already documents that Prisma re-keys these *"non-concurrently — an `ACCESS EXCLUSIVE` lock … i.e. an outage."* Adding two members to that key before M0 closes costs a line; adding them after production data exists costs a maintenance window.

**Why it is not fatal:** none of the actual anti-hallucination logic is wrong. §6.7's closing of the `entities`/`tables`/`keyValues`-key gap is genuinely good, the money guard (`FUZZY_FORBIDDEN` + exact-digit containment) is the right call, §5's refusal to brace-balance is correct and rare, and §8.3's coverage assertion does mechanically prevent silent truncation. The defect is in persistence and identity, not in the verifier.

**Secondary finding, noted not argued at length:** `maxCallsPerDocument = 12` (§2.8) is a flat constant that repairs also consume (§5: *"Repairs count against maxCallsPerDocument"*), while §8.2's 32k profile yields 4–6 pages/chunk. A routine 60-page Thai document needs 10–15 map calls *before any repair*, so it finishes `partial` + `BUDGET_EXCEEDED` with the **tail** pages named — pages that have nothing wrong with them. On-call will chase page content for a budget-constant problem. Derive the cap from the plan (`chunks + ceil(0.3 × chunks) + 2`) with the flat value as an outer ceiling.

**Safer alternative:** Four additive changes, all M0 doc-level, all cheap now and expensive after the schema ships:

1. **Persist the chunk plan and put it in the identity.** Add `chunkPlan Json` (page ranges + char spans; ~200 bytes/chunk) and `chunkPlanHash Char(64)` to `DocumentAnalysis` (§4.4). Add **`chunkPlanHash` and `verifierVersion`** to the `analysis_identity` `@@unique`. A verifier or planner bump then legitimately misses the cache and writes a new immutable row — exactly the property §9.3 already gives prompt versions, extended to the two other inputs that determine the answer.

2. **Freeze the estimator per analysis.** Record `calibrationFactor` and `estimatorVersion` on `DocumentAnalysis`. `planBudget()`/the planner take the factor as an explicit argument; a replay re-uses the **recorded** factor, never the current rolling one. The §8.1 p95 loop keeps improving *new* documents; old documents replay at the plan they were actually run under. This alone restores "reproducible provenance" (§14 blocker 6) without touching the verifier.

3. **Add a no-inference verify mode to `/internal/analysis/replay`.** `{"mode": "reverify"}`: load `result.sourceReferences` (already persisted — `persistedAnalysisSchema` inherits it from `documentAnalysisSchema`, §4.2), regenerate the chunk text from `DocumentPage` + the recorded `serializerVersion` + the persisted `chunkPlan`, verify the `inputSha256` and `chunkPlanHash` both match, re-run §6 at the new `verifierVersion`, and write a new analysis row. **Zero GPU calls.** This turns "we shipped a verifier bug" from a re-inference bill on Chat's GPU into a batch job that can run at 3am against the whole corpus, and it makes `verifierVersion` an actionable field rather than a forensic one. It also gives §9.4 a clean lever: re-verify the golden set under a candidate verifier without re-running any prompt.

4. **Pin the sensitivity with a test, so the residual risk is a measured number.** On the M2 golden set, plan each document at `factor = 1.0` and `factor = 2.0` and assert that `groundingClass` is identical for every **critical** field. Publish the non-critical divergence rate as `chunkPlanSensitivity`. If it is near zero the whole concern is closed empirically; if it is not, it is a number in a dashboard instead of an unreproducible ticket. This is the cheapest way to find out whether items 1–2 are load-bearing or merely prudent.

Additionally (secondary finding): derive `maxCallsPerDocument` from the plan — `min(AI_MAX_CALLS_PER_DOC_CEILING, plan.chunks.length + ceil(0.3 × plan.chunks.length) + 2)` — and when the cap is the binding constraint, emit a distinct warning code (`CALL_BUDGET_BINDING`, naming the chunk count and the cap) rather than `BUDGET_EXCEEDED` with an arbitrary tail-page list, so on-call can tell a budget problem from a document problem at a glance.

## P7-unknown-gateway-risk

**Decision under review:** The architecture is genuinely safe to build through M1-M2 while the LiteLLM endpoint, model list and vision capability remain UNKNOWN - i.e. no M1/M2 decision is silently betting on an unverified gateway assumption.

### Lens: feasibility - REFUTED (major)

The decision is 80% right and I want to say so first: the sequencing genuinely is safe. Deterministic OCR is the system of record in both branches (c §6, k §12), branch T is a strict subset of V so T-first is never wasted, `readCrop?`/`extractFromImage?` optional-on-the-interface forces every call site to handle absence, `LITELLM_MODEL` has no default so the app refuses to boot rather than call an unconfirmed model, and k §8.2's chunk targets sit at 14–36% of usable input, which absorbs large context/tokenizer errors. If the claim were only "M1/M2 sequencing does not depend on the gateway," it would hold.

But the claim is stronger — "no M1/M2 decision is *silently* betting on an unverified gateway assumption" — and that rests entirely on the premise that each unknown is contained by an explicit, *loud* guard. Two load-bearing guards do not work as written, and the containment itself is specified three incompatible ways.

**F1 — the redirect guard is inert, and it fails silently. Verified empirically, not reasoned.** c §F.1a declares `redirect: 'error'` "NON-NEGOTIABLE" and says the rejection must be treated as "a circuit-breaker-tripping, page-the-owner condition, **not a retryable error**," because it is the only control that guards the URL we *end up* talking to rather than the one we configured. c §F.4 detects it with:
`if (e instanceof TypeError && /redirect/i.test(String(e.message))) throw new RedirectRefusedError(...)`
I ran this on Node 22.22.3 (house pin 22.23.1, same undici) against a loopback 302 server: undici rejects with `TypeError` whose `message` is **`"fetch failed"`**; the string `"unexpected redirect"` lives on `e.cause.message`. So `/redirect/i.test(e.message)` is **false**. `RedirectRefusedError` is never constructed, F.4a's `if (e instanceof RedirectRefusedError) { breaker.trip(); throw e; }` is dead code, and the error falls to `lastErr = e` → retried up to `AI_MAX_ATTEMPTS` → `countsAsFailure` (`e instanceof TypeError`) → breaker → `{ok:false, reason:'upstream_error'}` → `degraded`. k reproduces the gap independently: k §2.10 line 852 declares the same control, and k §2.4's `classify()` sees `status === null`, not a timeout, and returns `'transport'` — retry ×3, breaker-counted, then `degraded`. k's own "Layer 4 — a test that proves the failure path" (§2.10) only exercises `ECONNREFUSED`, so it passes green while the redirect path is untested. Same defect class: k's `connect.lookup` `PolicyViolationError` (§2.10, line 814) is delivered through undici's connect callback and also surfaces as a connect failure → `'transport'` → retried, despite line 841 declaring policy violations "never retried, never degraded-around, never counted by the breaker: a hard stop."
Failure scenario: an ops change puts an authenticating proxy in front of the gateway, or a stale/poisoned DNS entry redirects it. Under an *unknown* gateway you cannot rule this out — that is the whole premise. The system retries three times, opens the breaker, emits `AI_UNAVAILABLE`, and produces OCR-only results. It reads as flaky networking. Nobody is paged. This is precisely the silent bet the decision says does not exist, and it sits on the one guard both docs call non-negotiable.

**F2 — there is no single AI contract to implement; there are three, and they contradict on a gateway fact.** b §4.3 (decision B-5) mandates `LITELLM_BASE_URL` and hard-rejects a base ending in `/v1` (`.refine((u) => !/\/v1\/?$/.test(u))`), explicitly rejecting `AI_*` naming. c §5.2 and the *shipped* `docs/m0/discovery/probe_ai_gateway.py` mandate the opposite: line 45 `export AI_BASE_URL='https://<gateway-host>/v1'`, lines 258–263 `"AI_BASE_URL conventionally ends in /v1, so strip it for those calls"`. k §2.10/K-23 is a third shape again (`AI_ALLOWED_HOSTS`, `AI_ALLOWED_RESOLVED_CIDRS`, `AI_ALLOWED_PORTS`). k §0.1's dependency table cites the env contract to "`b-ai-topology-discovery.md` §5 (F.1–F.8)" — F.1–F.8 are in **c**, not b — and k §0.2 claims to enumerate its disagreements with B/C "in exactly two places"; neither the naming split nor the `/v1` split is one of them. The owner will supply one literal string, and per b's own evidence E2 it excludes `/v1`: the artifact that *answers* the gateway question and the artifact that *consumes* the answer enforce mutually exclusive conventions on it. This one fails loudly, so it is major-not-fatal — but it means the M0 claim "the contract is settled, only the value is missing" is not true today. Related: c §5.2's mandated parity test `readFile('docs/m0/discovery/probe_ai_gateway.py')` + `/^\s{4}"([a-z0-9.\-]+)",$/gm` will also capture unrelated 4-space-indented literals in that file (e.g. the vision matcher's `"text-only"`), so it is a false-failure generator coupling production unit tests to a diagnostic script's formatting.

**F3 — placeholders that disagree with the project's own best evidence, unflagged.** c §5.2 sets `AI_MAX_INPUT_TOKENS: default(32_768)` — a default for a pure gateway fact, justified as "a common `--max-model-len` default" — while c §3.i's own reasoning states erring *high* is the unsafe direction; b §4.3 sets the same concept to `default(16_000)`/`max(65_536)`. k §8.2 defines chunk profiles at only 32,768 and 131,072, and the single *evidenced* ceiling (b E6: 65,536) matches neither column, so the design has no defined answer for the value the evidence points at. k §8.1 uses Thai at 1.5 chars/token as "the pessimistic end," while b E15 (INNOVERA Chat's own production estimator — the only evidenced datapoint) and c §5.6's own correction both give ~1.0, i.e. k's "pessimistic" prior is 1.5× optimistic against the best evidence available. k's margins absorb it, but nothing anywhere flags the disagreement, which is the definition of silent.

None of this makes the program unbuildable, and I did not find a schema, storage, or queue decision that bakes in a gateway assumption. But "safe because every unknown is loudly contained" is the load-bearing claim, and as specified the containment leaks in one place I confirmed by execution and is triple-specified in another. Fix those and the decision holds.

**Safer alternative:** 1) Replace string-sniffing redirect detection with a deterministic, version-independent check: use `redirect: 'manual'` and treat any `res.status >= 300 && res.status < 400` as a `PolicyViolationError`. Add `policy_violation` as its own member of `AiErrorClass` (alongside `bad_request`) with retry=never, breaker-count=never, alert=CRITICAL, and route k's `connect.lookup` CIDR violation into it via a sentinel property on the error object rather than relying on undici's message text. If `redirect: 'error'` is kept anywhere, the predicate must be `/redirect/i.test(String(e?.cause?.message ?? e?.message))`.
2) Extend k §2.10's "Layer 4 — a test that proves the failure path" from one case (ECONNREFUSED) to four, each asserting the declared class and that no retry occurred: a 302 response, a DNS answer outside `AI_ALLOWED_RESOLVED_CIDRS`, a 401, and an unrecognised 400. The current test passes while the redirect path is broken, which is worse than no test.
3) Before any M1 code, write ONE normative `docs/architecture/m0/ai-contract.md` owning env var names, the `/v1` convention, the egress-guard layer stack, and the placeholder table; demote b §4.3, c §5.2 and k §2.10 to non-normative excerpts of it. Adopt b's `LITELLM_*` names and base-excludes-`/v1` (the only convention with evidence behind it — E2), and change `probe_ai_gateway.py` + `probe-ai-gateway.sh` + the run-book to append `/v1` themselves. Replace c §5.2's source-scraping parity test with a shared JSON file both the probe and the app read.
4) Give k §8.2 a formula instead of two columns (e.g. `target = min(8_000 * ctx/32_768, 0.25 * usable)`) so 65,536 has a defined answer, and reconcile the Thai chars/token prior to ~1.0 across b/c/k with a single cited source.

### Lens: security - REFUTED (major)

=== HOLE 1 (primary): the AI credential holder is decided in two opposite directions, and nobody cross-references. ===

That is exactly the row that fires j §6.10's "worker makes the call". ## 2. Two hard M1 correctness bugs a competent engineer hits on the first real document

**(a) `storage_object_org_fingerprint_key` rejects duplicate page renders.** §7.3 measure 1 puts `@@unique([organizationId, contentFingerprint, kind])` on `StorageObject`, and `contentFingerprint` is `NOT NULL` on *every* row (§5.4, plus `CHECK (content_fingerprint ~ '^[0-9a-f]{64}$')`). But §7.4 property 2 makes renders **identity-addressed** (`org/{org}/render/{docId}/{page:05d}@{dpi}.jpg`) precisely because they are derivatives. These two are directly contradictory: identity-addressed keys are distinct, but the *bytes* are not. A duplex-scanned or born-digital PDF with two blank pages rasterises to two byte-identical images (deterministic rasteriser + deterministic encoder at the same DPI) → identical fingerprint → same org → `kind='PAGE_RENDER'` → **`23505 unique_violation` on the second insert**. `PAGE_THUMBNAIL` is worse (heavy downscaling collapses near-identical pages to identical bytes); `ENGINE_PAYLOAD` collides on any two empty-page JSON payloads. The OCR job fails, retries under §5.5 backoff, exhausts `max_attempts`, goes `DEAD`, and the document goes `FAILED`. Blank backs and separator sheets are the single most common artifact in scanned-document workloads — this is not an edge case, it is the median 200-page scan the doc itself uses as its worked example in §6.1.

If you instead "reuse" the colliding row, `DocumentPage.renderStorageObjectId` in *two different documents* points at one blob, and PDPA erasure of document A destroys a blob document B still renders — which is the exact refcount argument §7.3 uses to reject cross-tenant dedup, reappearing intra-tenant and unnoticed.

**(b) `ocr_result_page_engine_key` makes the operator-requeue path permanently un-recoverable.** §7.1 step 5 mandates that a non-deterministic engine is "**never** reused — re-running is the only honest behaviour". §4.2 Level 2 mandates that `FAILED → QUEUED` re-enters at the *start* of the pipeline, and §4.2/§5.5 add `Document.requeueCount` and a generation-stamped `dedupeKey` specifically so a requeue is not blocked. But the re-run then tries to insert an `OcrResult` for the same `(documentPageId, engineId, engineVersion, renderDpi)` — which `@@unique` forbids — and `ocr_results` carries `ocr_results_no_update` (`reject_mutation`, §8.1), so there is **no `ON CONFLICT DO UPDATE` escape**. The doc fixed the collision on the job table and missed the identical collision one layer down on the evidence table. Concretely: a 60-page document dies on page 51; the operator requeues; the worker re-OCRs page 1 with the same engine build at the same DPI; `23505`; job `DEAD`; document `FAILED`. Every subsequent requeue reproduces it. `FAILED → QUEUED` is the *only* recovery edge in §4.2, so the document is permanently stuck and the only exit is deletion.

## 3. TEN-1's machine check certifies a schema that still permits cross-tenant pointers

The §3.3 DMMF test iterates only `f.kind === "object"` relation fields. Every cross-tenant pointer that is a **bare scalar with no relation** passes silently, and §5 has several: `DocumentPage.renderStorageObjectId` (grep confirms it appears exactly once in the entire doc — declared and never mentioned again, no FK, no composite anchor), `Document.createdByApiKeyId`, `Document.duplicateOfDocumentId`, `ExtractionFieldValue.sourceOcrResultId`, `ExtractionFieldValue.sourceAnalysisId`, and the two arrays `DocumentAnalysis.sourceOcrResultIds[]` / `sourceImageObjectIds[]` (PostgreSQL cannot FK array elements at all — and §5.6 Branch V says `sourceImageObjectIds` names "the exact `StorageObject` page renders sent to the gateway", so a mis-scoped id there ships another tenant's scan to the LLM).

Sharper still: `OcrResult.payloadRef` and `ExtractionJob.resultRef` are raw `VarChar(1024)` **object-storage keys**. Anything that resolves them reads object storage with the app credential and never touches PostgreSQL — so neither the composite FK nor RLS applies to them at all. §7.4 property 3 makes the `org/{organizationId}/` prefix the entire object-storage tenant boundary, yet §5.3 writes CHECKs for `public_id` shape, sha shape and key-hash shape and writes **no** CHECK pinning that prefix to the row's own `organization_id`. ### Lens: security - REFUTED (major)

## 1. The load-bearing hole: the schema omits a mandate its own threat model issued

`j-security-threat-model.md` §7.1.1 ("Horizontal escalation *inside* a tenant"), lines 1117-1168, ends with this, in bold, in the reviewed version:

> "**Schema consequence (for the data-model dimension):** `documents.ownerId`, `documents.workspaceId`, a `workspaces` table, a `workspace_members` join, and a `document_grants` table. **This is a schema constraint discovered in review and it must land in M1** — retrofitting a visibility model onto an existing document corpus means backfilling ownership for rows whose real owner is no longer knowable."

`grep -in "workspace|document_grant|visibility" g-data-model.md` returns **zero schema hits** (the only two matches are the word "invisibility" about `prisma migrate diff`). `l-api-ui-export.md` §2.2's `tenantScoped()` extension likewise injects only `tenantId` and has no `visibilityFilter`. So the mandate was issued and not received. What §5.4 actually ships is `Document.ownerUserId String? @db.Uuid` — nullable, **no `@relation` and therefore no foreign key at all**, and used by exactly one index (`document_org_owner_created_idx`) for a convenience "my documents" list. That is a display field, not an authorization column.

All three of K-3's "independent isolation layers" are keyed on `organizationId` and nothing else: `TenantScope` carries one field; the composite FK is `(id, organizationId)`; the RLS predicate is `organization_id = current_setting('app.current_org', true)::uuid`. Every one of them passes for the attack j §7.1.1 rates **High likelihood** and says "does not need an attacker": a 200-person customer's AP clerk requests a document HR uploaded — a scanned employment contract carrying a colleague's national ID, salary, address and religion (j §9.1's inventory). This directly falsifies both halves of the decision:
- **"IDOR-proof by construction"** is true for cross-tenant IDOR and false for intra-tenant IDOR, which j rates as the more likely of the two and "the single most likely finding in a customer's own security review."
- **"will not need a destructive migration by M5"** — j §7.1.1 names the exact migration and states it is unbackfillable. `documents.workspace_id` cannot be made `NOT NULL` retroactively because the correct workspace for rows already uploaded "is no longer knowable"; `document_grants` cannot be reconstructed from history because no grant was ever recorded. This is not a column addition, it is a permanent data-quality loss. And it is cheap only right now, before any document exists.

## 2. Second hole: the CHECK constraints are 8x and 40x looser than the DoS budget that was computed for them

§5.3 writes the limits into the database as the stated enforcement point:

```sql
ALTER TABLE documents ADD CONSTRAINT document_size_bounds       CHECK (size_bytes BETWEEN 1 AND 209715200);   -- 200 MiB
ALTER TABLE documents ADD CONSTRAINT document_page_count_bounds CHECK (page_count IS NULL OR page_count BETWEEN 1 AND 2000);
```

and §5.3's table says "Upload size **200 MiB** — enforced where: `document_size_bounds` CHECK + the HTTP body limit; Page count **2 000** — enforced where: `document_page_count_bounds` CHECK, checked during `VALIDATING`."

`j-security-threat-model.md` §8.1: "**Global hard cap 25 MB.** This is the number every other layer must agree with." §8.2: "**50 pages per document (hard reject at 51)** ... 50 pages x 12 s/page OCR = 600 s = 10 minutes, which is the per-document OCR budget (§8.7). The page cap and the time budget are the same constraint expressed twice; **they must be changed together**." §3.4 repeats it: "Hard cap 50 pages (§8.2), rejected before rendering."

The g doc's §5.3 explicitly reconciles 200 MiB against 2 000 pages **and never once looks at j** — it derives its own envelope from §6.1's "brief's 200-page scan". §12.3 ("Cross-document inconsistency to resolve") lists only the PostgreSQL 16-vs-18 diagram error, so this was not noticed.

Concrete abuse, using only limits the schema permits: j §8.6 allows 2 concurrent jobs/user and 25 queued documents/user against a **global worker pool of 4**. One authenticated tenant uploads 25 x 2 000-page born-digital PDFs, each comfortably under 200 MiB (j §8.1's own arithmetic: ~100 KB/page for born-digital). At j §8.2's 12 s/page that is 50 000 pages = **~167 worker-hours**, with two of the pool's four slots pinned for **6.7 hours by a single document**. The only backstop is the per-day page quota — and §5.8 concedes "Quota enforcement is check-then-act and therefore racy... For a *soft* quota that is acceptable and it is what we ship in M1." Every downstream number in j §8.3 (40 Mpx / 160 MB decoded page), §8.6 (pool of 4), §8.7 (10-minute per-document budget) and §8.8 (2 GB worker container) was derived from the 50-page/25 MB envelope and is invalid at 40x/8x.

Note also that fixing this later is not free either: `ALTER TABLE ... ADD CONSTRAINT ... CHECK` validates existing rows by default, so tightening 2 000 -> 50 fails outright once one oversized document has landed.

## 3. Three smaller ones, each substantiated

**(a) `storage_object_org_fingerprint_key` wedges the render pipeline on blank pages.** §5.4 declares `@@unique([organizationId, contentFingerprint, kind])` with `contentFingerprint` NOT NULL on *every* kind, while §7.4's key grammar makes only `ORIGINAL` content-addressed (`org/{org}/blob/{fp}`) and renders identity-addressed (`org/{org}/render/{docId}/{page:05d}@{dpi}.jpg`). Two page renders with identical bytes — two blank pages, two identical letterhead pages, two blank reverse sides of a duplex scan — produce the same `(organizationId, contentFingerprint, 'PAGE_RENDER')` and collide with `23505`, while `storage_object_bucket_key_key` simultaneously says they are two distinct objects. The two unique constraints disagree by construction. Self-harm: this fires on ordinary multi-page scans. Abuse: a 50-page PDF of one repeated page permanently wedges its own render job through all 5 retries into `DEAD`, at the cost of one upload. The comment on that index says it is "THE dedup probe ... AND kind='ORIGINAL'" — the intent is right, the constraint is not scoped to it.

**(b) Every JSONB column got a size cap; not one text column did.** §5.3 writes five `pg_column_size()` CHECKs (`audit_metadata_size`, `document_source_meta_size`, `ocr_lines_json_size`, `job_requirements_size`, `field_value_json_size`) and zero caps on `document_pages.plain_text`, `plain_text_raw`, `search_tokens`, `search_tokens_subword`, `ocr_results.raw_text`, `normalized_text`, `markdown`, or `document_analyses.raw_response`. §6.2 states the rule — "Any single value that can exceed **256 KB**, or that is binary, goes to object storage" — and then enforces it nowhere. j §3.4 caps *decompressed PDF stream* bytes at 500 MB/document, which bounds the input but not the fan-out: one document's extracted text is written to `plain_text` **and** `plain_text_raw` **and** `search_tokens` **and** `search_tokens_subword` (§9.3/§9.8), so a text-bomb PDF amplifies ~4x into PostgreSQL, inside the tenant's transaction, counted against **no** `UsageMetric` (the enum has `STORAGE_BYTES` for blobs, nothing for database text). A `pg_column_size(plain_text) <= 262144` CHECK costs one line and matches the rule the document already wrote.

**(c) `users` is protected by prose, in a document whose whole thesis is that prose is not protection.** §5.3: "`users` is GLOBAL, not tenant-scoped, and carries NO RLS policy... It is reachable only through a Membership the caller shares; there is no endpoint that lists users outside an organization" — and §3.4 requires a test asserting `users` is *deliberately absent* from `TENANT_TABLES`. So the one table holding every customer's staff email addresses has zero of the three layers. Meanwhile six actor-pointer columns have **no FK at all** — `Document.ownerUserId`, `Correction.actorUserId`, `ExtractionFieldValue.createdByUserId`, `ApiKey.createdByUserId`, `Membership.invitedByUserId`, `AuditLog.actorId` — and invariant TEN-1's DMMF test cannot see them: it iterates `model.fields` and `continue`s on `f.kind !== "object"`, so a bare `String @db.Uuid` with no relation is structurally invisible to the check that exists to catch exactly this. §15.7 concedes the missing relations ("Each is defensible; none was defended") without noticing that the combination — unconstrained id + unprotected referent — is a cross-tenant PII resolution path the moment any "uploaded by" / "corrected by" display joins `users`.

**(d) The two documents do not even agree on the tenancy column's name.** `l-api-ui-export.md` §2.2's fail-closed extension throws `tenant-scope: model ${model} has no tenantId and is not in GLOBAL_MODELS` and lists `GLOBAL_MODELS = ['Tenant','SystemSetting','MigrationLock']`. g-data-model names the column `organizationId` and its globals are `User`, `PromptVersion`, `OutboxEvent`, `IdempotencyRecord`. Run as written against this schema, l's security control throws on **every** model including `User` — i.e. login. That is not a security hole by itself, but it means the API layer's IDOR control has never been read against the schema it is supposed to protect, which is why (1) went unnoticed.

## What convinced me it is not merely theoretical
The strongest evidence is not my inference — it is that the project's own security document, reviewed the same day by the same process, wrote the requirement down in bold, addressed it explicitly to "the data-model dimension", labelled it M1, and stated its own retrofit is impossible. The data model then shipped without it and its §12.3 inconsistency register did not catch it. When two reviewed documents in one M0 disagree about the authorization boundary and about the ingest limits by 40x, the claim "correct and IDOR-proof by construction" cannot stand as written.

**Safer alternative:** Do not ship P8 as approved. Four concrete, additive changes — all cheap now, all irreversible-or-expensive later. None requires re-litigating UUIDv7, RLS, append-only, or the large-text placement, which hold up under this lens.

**A. Land the intra-tenant visibility model in the M1 schema (blocking).** Add exactly what j §7.1.1 specified, and make it the fourth isolation layer rather than an application filter:

```prisma
model Workspace {
  id String @id @db.Uuid
  organizationId String @map("organization_id") @db.Uuid
  slug String @db.VarChar(80)
  name String @db.VarChar(200)
  isDefault Boolean @default(false) @map("is_default")
  organization Organization @relation(fields: [organizationId], references: [id], onDelete: Restrict)
  @@unique([organizationId, slug], map: "workspace_org_slug_key")
  @@unique([id, organizationId], map: "workspace_id_org_key")
  @@map("workspaces")
}

model WorkspaceMember {
  id String @id @db.Uuid
  organizationId String @map("organization_id") @db.Uuid
  workspaceId String @map("workspace_id") @db.Uuid
  userId String @map("user_id") @db.Uuid
  role OrgRole
  workspace Workspace @relation(fields: [workspaceId, organizationId], references: [id, organizationId], onDelete: Cascade)
  @@unique([workspaceId, userId], map: "workspace_member_ws_user_key")
  @@index([userId, organizationId], map: "workspace_member_user_org_idx")
  @@map("workspace_members")
}

model DocumentGrant {
  id String @id @db.Uuid
  organizationId String @map("organization_id") @db.Uuid
  documentId String @map("document_id") @db.Uuid
  userId String @map("user_id") @db.Uuid
  grantedByUserId String @map("granted_by_user_id") @db.Uuid
  canApprove Boolean @default(false) @map("can_approve")
  createdAt DateTime @default(now()) @map("created_at") @db.Timestamptz(3)
  document Document @relation(fields: [documentId, organizationId], references: [id, organizationId], onDelete: Cascade)
  @@unique([documentId, userId], map: "document_grant_doc_user_key")
  @@index([organizationId, userId], map: "document_grant_org_user_idx")
  @@map("document_grants")
}
```

On `Document`: make `ownerUserId` **`String` NOT NULL** and add `workspaceId String @map("workspace_id") @db.Uuid` **NOT NULL** with a composite FK `(workspaceId, organizationId) -> Workspace(id, organizationId)`. Both NOT NULL is the whole point — the un-backfillable value must be captured at insert. Organization creation installs a `default` workspace in the same transaction that installs the starter templates (§5.7's existing `installStarterTemplates` pattern), so no org can exist without one and the migration to a real multi-workspace product is a data move inside a tenant, not a guess.

Then extend the RLS predicate on `documents` from a tenant check to a *visibility* check, so intra-tenant IDOR fails closed at the same layer cross-tenant IDOR does:

```sql
CREATE POLICY doc_visibility ON documents FOR ALL TO ocr_app
USING (
  organization_id = current_setting('app.current_org', true)::uuid
  AND ( current_setting('app.is_org_admin', true) = 'on'
     OR owner_user_id = current_setting('app.current_user', true)::uuid
     OR EXISTS (SELECT 1 FROM workspace_members wm
                WHERE wm.workspace_id = documents.workspace_id
                  AND wm.user_id = current_setting('app.current_user', true)::uuid)
     OR EXISTS (SELECT 1 FROM document_grants g
                WHERE g.document_id = documents.id
                  AND g.user_id = current_setting('app.current_user', true)::uuid) )
)
WITH CHECK (organization_id = current_setting('app.current_org', true)::uuid);
```

`TenantScope` gains `userId` and `isOrgAdmin`; `withTenant` sets all three GUCs with `set_config(..., true)` in the same statement batch. `app.is_org_admin = 'on'` is set only by the authorization port and every admin-scope transaction writes an `AuditLog` row (j §7.1.1's "permitted, and written to the audit log"). Approval authority reads `document_grants.can_approve` / workspace role, never visibility.

**B. Reconcile the ingest limits to j §8.1/§8.2 and make the disagreement impossible to reintroduce.** Change the CHECKs to `size_bytes BETWEEN 1 AND 26214400` (25 MiB) and `page_count BETWEEN 1 AND 50`, and delete §5.3's independently-derived 200 MiB/2 000-page table, replacing it with a pointer to j §8. Then add a test that reads the limit constants from **one** shared module (`src/modules/shared/domain/ingest-limits.ts`) and asserts they equal the values in the migration's CHECK constraints via `pg_get_constraintdef()` — so the schema and the threat model cannot drift again without failing CI. If the product genuinely needs 2 000-page documents, that is a decision to reopen j §8.2 and §8.7 together (as j itself demands), not to encode silently in a CHECK.

**C. Scope the fingerprint uniqueness to the kind it was designed for.** Replace `@@unique([organizationId, contentFingerprint, kind])` with a partial unique index (same `partialIndexes` mechanism §5.7 already adopts for `field_value_one_current_key`):
`CREATE UNIQUE INDEX storage_object_org_fingerprint_key ON storage_objects (organization_id, content_fingerprint) WHERE kind = 'ORIGINAL' AND deleted_at IS NULL;`
Derivatives keep only `storage_object_bucket_key_key`, which is already correct for them. Add an integration test that ingests a 3-page PDF whose pages 2 and 3 are blank and asserts three `PAGE_RENDER` rows exist.

**D. Close the two remaining gaps with one line each.** (i) Add `CHECK (pg_column_size(<col>) <= 262144)` to `plain_text`, `plain_text_raw`, `search_tokens`, `search_tokens_subword`, `raw_text`, `normalized_text`, `markdown`, `raw_response`, enforcing §6.2's own 256 KB rule, and add a `PAGES_TEXT_BYTES` (or reuse `STORAGE_BYTES`) increment at the page-write site so database text is metered. (ii) Give `users` an RLS policy instead of a paragraph — `FOR SELECT TO ocr_app USING (EXISTS (SELECT 1 FROM memberships m WHERE m.user_id = users.id AND m.organization_id = current_setting('app.current_org', true)::uuid AND m.revoked_at IS NULL))` — with the pre-org-selection login lookup moved to a separate `ocr_auth` role or a `SECURITY DEFINER` function that returns only `(id, status)`. And extend the TEN-1 DMMF test to a second assertion: any scalar field matching `/UserId$|ApiKeyId$/` must either have a relation or appear in an explicit, commented `NO_FK_BY_DESIGN` allowlist — so "defensible but undefended" (§15.7's own phrase) becomes a CI failure rather than a footnote.

### Lens: OPERATIONS (production ops / cost / blast radius) - REFUTED (major)

The tenancy scoping and the append-only design hold up under my lens — the composite-FK invariant TEN-1 plus the DMMF CI test is a genuinely good, cheap control, and the operator escape hatches in the status machine exist (every transient state has a legal `→ FAILED` edge, so a stuck document is recoverable without owner DDL — I checked this expecting a break-glass problem and did not find one). What does not hold is the claim "will not need a destructive migration by M5", and the reason is that the schema hard-codes exactly ONE lifetime per document while the project's own compliance document specifies five.

**1. The retention model is not implementable on this schema, and it is the change that IS destructive.** `j-security-threat-model.md` §9.5 specifies: originals 90 d, page renders 90 d (or approval+30 d), OCR text 90 d, extracted fields 365 d, corrections + audit log **7 years**. `g-data-model.md` makes `document_pages`, `ocr_results`, `extraction_field_values`, `corrections`, `document_analyses` and `extraction_jobs` all `onDelete: Cascade` children of `documents` (§5.4–§5.7). There is no per-artifact expiry column anywhere except `StorageObject.expiresAt`, and g's only purge query is `WHERE deleted_at < now() - interval '30 days'` (§5.4 index comment) — a user-delete sweeper, not a retention sweeper. You cannot expire OCR text at 90 d while the fields live to 365 d and the corrections live to 7 y, because deleting the parent takes all three. `l-api-ui-export.md` open question 16 says this out loud from the other side: *"corrections… may need to outlive the documents they describe, in de-identified form"* — which `Correction.document → onDelete: Cascade` forbids by construction. Adding an independent lifetime later means altering cascade semantics on live FKs and backfilling expiry columns across 1.44 M `document_pages` and 1.56 M `ocr_results`. That is the destructive migration the decision says will not happen, and it lands well before M5.

**2. g §8.3's partitioning arithmetic is falsified by the project's own security doc.** g concludes audit_logs is *"bounded at 200 000 × 13.2 ≈ 2.6 M rows and never approaches 50 M — not in year 20, not ever"* on a 400-day retention, and defers partitioning indefinitely. j §9.5 says 7 years. At g's own 200 k rows/month that is ~16.8 M rows, and g §8.3 already names this exact reversal trigger — *"(b) a regulator requires a retention longer than ~5 years, which removes the bound"* — without noticing that the sibling document has already tripped it. `@@id([id, occurredAt])` keeps the option open, but converting a populated table to `PARTITION BY RANGE` is a rewrite, not an `ALTER`.

**3. The render-TTL cost saving is void from day 91.** g §11 calls the 30-day render TTL *"the single highest-leverage storage decision — it removes ~600 GB/year for the cost of re-rasterising a page when someone opens a document older than 30 days"*, and §6.2 justifies it as *"regenerable"*. j §9.5 deletes the original at 90 days. From day 91 there is nothing to re-rasterise from: a document still inside its 365-day field retention, still legally in `READY_FOR_REVIEW` (no deadline exists on that state), opens to a permanently blank viewer with confidence-scored fields and no page to check them against. Either the ~390 GB/year figure is wrong or the 90-day original retention is.

**4. Blast radius: the nightly retention job becomes the most-executed privileged path in the system.** Because `ocr_results`, `corrections` and `audit_logs` carry `BEFORE DELETE` guards, any time-based expiry must run as `ocr_erasure` inside `app.erasure_window='on'`. g §12.1.7 mitigates that GUC with *"it is set in exactly one function, that function is only reachable from the purge job"* — sound when the purge job is a rare compliance action, not when it runs unattended every night over ~130 k `ocr_results`/month with DELETE granted on documents, pages, results, corrections, field values, audit logs and storage objects. A missing `deleted_at IS NULL`, a reused `orgId` in the per-tenant loop, or an interval typo destroys evidence at scale on tables that by design have no `updated_at`, no `deleted_at` and no undo. Recovery is a 35-day backup (j §9.5) restored by a procedure j itself says *"must re-apply the deletion log"* — i.e. it re-deletes what you are restoring. g also gives no batch size, lock budget or dry-run mode for this job (only for `audit_logs`), and every cascaded child row fires a PL/pgSQL row trigger, so the highest-volume delete path is also the slowest per row.

**5. Verified DR gap: `pg_dump` does not carry the roles the whole isolation model rests on.** g §11 asserts *"a nightly `pg_dump` is still practical"*, and §10.2 puts role creation in an out-of-band bootstrap script (*"Migration 0000 is not a migration"*). PostgreSQL 18 docs, `pg_dump`, verbatim: *"pg_dump only dumps a single database. To export an entire cluster, or to export global objects that are common to all databases in a cluster (such as roles and tablespaces), use pg_dumpall."* pg_dump **does** emit GRANT/REVOKE, `CREATE POLICY … TO ocr_app`, and `ENABLE/FORCE ROW LEVEL SECURITY`. So the 3am restore-to-a-fresh-instance path yields: policy and grant statements failing with `role "ocr_app" does not exist` (pg_restore continues past these by default), FORCE RLS enabled, **zero policies** — and the app then returns **zero rows for every tenant query with no error raised**, which is precisely the "my query returns nothing" debugging trap g §3.4 point 1 names. Neither g §12.4 nor j §9.5 mentions `pg_dumpall --globals-only`, and nothing asserts role/policy presence at startup.

**6. Two more rewrites already scheduled before M5, by the document's own text.** §9.4's M4 index plan adds `search_tsv tsvector GENERATED ALWAYS AS … STORED`; PostgreSQL's ALTER TABLE docs confirm *"a stored generated column … will cause the entire table and its indexes to be rewritten"* under ACCESS EXCLUSIVE — g concedes this is *"a maintenance window, not a rolling deploy"*. And migration 0011 (ICU collation) must run while tables are empty, against a managed provider that has not been chosen and whose ICU support is g §12.4's own **blocking** open question 8.

None of this requires redesigning the schema. It requires settling retention before the M1 tables are created, because retention is the one thing here that is genuinely irreversible once FKs and cascades are live.

**Safer alternative:** Do not freeze migrations 0004–0007 until retention is answered. Concretely:

1. **Reconcile the three retention statements first.** Make one document authoritative for `j §9.5` (5 tiers), `g §8.3` (400 d audit), `g §5.4` (30-d soft-delete purge) and `l` open Q7/Q16. Q16 — do corrections outlive their documents? — must be answered before any FK is written, because it alone decides whether `Correction.documentId` can be `onDelete: Cascade`.

2. **Give every independently-expiring artifact its own clock instead of inheriting the document cascade.** Add `OcrResult.expiresAt`, `DocumentPage.textExpiresAt`, and `Document.purgedAt` (a tombstone — `l` §1.3's `410 resource_gone` and the partial dedupe index at `l`:971 both already assume the row survives its content). Expiring OCR text then becomes: null `document_pages.plain_text`/`plain_text_raw`/`search_tokens` (that table is mutable and has `updated_at`) plus a guarded delete of `ocr_results` on its own `expires_at` — not a cascade from `documents`. If corrections must reach 7 years, drop `Correction.documentId`'s cascade to `NoAction` and carry a denormalised de-identified copy, or move the 7-year copy to the WORM export path §8.3 already builds for audit.

3. **Split the retention role from the erasure role.** Introduce `ocr_retention` with a separate `app.retention_window` GUC and DELETE granted **only** on `ocr_results`, `storage_objects` and `job_events`. The nightly job then structurally cannot reach `audit_logs`, `corrections` or `documents`, and `ocr_erasure` stays what §12.1.7 assumes it is: rare, deliberate, and audited. Specify a batch size, a per-batch lock budget, and a `--dry-run` mode that reports `RETURNING` counts without committing.

4. **Re-cost the render TTL against the original's real retention.** Either raise the original above the render TTL and state that the ~600 GB/year saving depends on it, or keep a low-DPI page JPEG for the full field-value retention and put the recovered storage back into §11's projection. Do not ship a viewer that goes blank at day 91 on a document that is still open for review.

5. **Fix the DR runbook and fail loud instead of silent.** Nightly `pg_dumpall --globals-only` alongside `pg_dump`; and an application startup assertion — reuse §10.2's `DO $$ … $$` block — that the four roles exist and `pg_policies` returns the expected count for every tenant table, refusing to serve traffic if not. A role-less restore must produce a crash-loop, never zero rows.

6. **Restate the claim honestly rather than defending it.** Replace "no destructive migration by M5" with a named list of the rewrites already planned: `search_tsv` (M4, ACCESS EXCLUSIVE, full table+index rewrite), migration 0011 collation (empty-table only, blocked on §12.4 Q8), and any audit partitioning that a 7-year retention forces. Then decide whether to pull `search_tsv` and the collation into M1 while the tables are empty — which is cheap now and a maintenance window later.
