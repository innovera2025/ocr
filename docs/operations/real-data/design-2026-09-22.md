# INNOVERA OCR: design for real-world input (multi-page files, varied formats, export)

Repo `/tmp/ocr-push` at `32e75e4` (main, the production code). This was research only: no file in the repo was changed, and the only thing run was a read-only check of the Local AI normalizer. File references use `path:function`.

## Summary

- **Why the 95-page file failed.** The worker sends the whole PDF (44.8 MB) to the Local AI. The nginx on the Local AI host limits requests to 25 MB, so it answered HTTP 413. The system treats 413 as non-retryable, so the job went DEAD and the document went FAILED. Even with a larger limit, Local AI v3 only reads page 1 of a PDF.
- **Main proposal.** The worker splits each PDF into page images with poppler `pdftoppm`. Each page becomes a child document: one table row per page, in the same batch. The parent row keeps the original PDF. Only page images of about 1–4 MB are sent to the AI, so the 25 MB nginx limit no longer matters for PDFs.
- **The user can be unblocked today with no deploy.** Convert the PDF to 95 PNG files on a trusted machine and upload them all in one selection. The picker accepts up to 100 files.
- **Other formats and phone photos.** The Local AI checks whether a page is the Makkha form by scoring the printed checkbox grid. It tries rotations of 0/90/180/270, straightens small skew, and corrects the perspective of phone photos. If the page is still not recognised, Typhoon transcribes the whole page as markdown, key-value pairs are pulled out, and the page is sent to review. No data is dropped.
- **Export.** A CSV file (UTF-8 with a BOM so Excel shows Thai correctly) plus a lossless JSONL file, streamed and limited to the caller's tenant. **Do not turn on the Export button while `/api/web-token` still gives a token to any visitor.**
- **Queue fairness.** `extraction_jobs.priority` already exists and the claim function already orders by it. Setting it when a job is inserted lets a single urgent upload go ahead of a large batch, with no change to the queue functions.

## 0. What actually happened, and the constraints

**Failure path, traced through the code**
1. `POST /api/documents`: 44.8 MB is under `limits.maxUploadBytes` (209,715,200 bytes, in `packages/config/src/index.ts`). `packages/ingest/src/http.ts:readRawUpload` loads the whole body into memory, ClamAV scans it, and one `documents` row plus one job of kind `OCR` are created (`apps/ocr-web/src/runtime.ts:createRuntimeIngest.enqueuePersistent` → `packages/queue/src/postgres.ts:PostgresQueue.enqueue`).
2. `services/ocr-worker/src/index.ts:processOcrJob` reads the whole file and `packages/ocr-client/src/index.ts:OcrClient.processDocument` posts it to `/v1/ocr`.
3. The Local AI host's nginx (`client_max_body_size 25M`) answers 413. `OcrClient.requestJson` treats 413 as non-retryable (only 5xx/429/408 are retried). `failJob` finishes the job `DEAD` and `markFailure` sets the document FAILED with "OCR API returned HTTP 413".
4. Even past nginx, `local-ai/api.py:ocr` refuses anything over `OCR_MAX_UPLOAD_BYTES` (30 MiB) with 413. `_decode` then renders page 1 only and adds the warning `"PDF has 95 pages; only page 1 was processed"`.

**Constraints the design must respect**

| Fact | Where it is | Consequence |
|---|---|---|
| `ocr_claim_v1` orders by `priority ASC, available_at ASC`; `extraction_jobs.priority` defaults to 100; a partial index exists | 0001, 0005 | Priority can be set when a job is inserted, without touching any queue function. |
| `ocr_finish_retry_v1` passes any outcome other than FAILED straight through, including `CANCELLED` | 0007 | The worker can finish a job as CANCELLED without a function change. |
| `ocr_app` has table-level INSERT on `extraction_jobs` plus `SELECT (id, organization_id, run_id)` | 0016 | The web can set `priority` and `kind`. |
| `ocr_worker` has `SELECT, UPDATE` (no INSERT) on `documents` and `document_runs`, and no rights at all on `extraction_jobs` (`REVOKE ALL`) | 0002, 0009 | **A worker-side split needs new grants.** |
| Queue and outbox SECURITY DEFINER functions are owned by `ocr_queue_definer`; the migrator must never `CREATE OR REPLACE` them | `deploy/sql/queue-definer.sql`, `test/batch-migration.test.ts` | New migrations use grants only and define no functions. |
| `document_status` enum; values have been added before inside the runner's transaction (0003) | 0001, 0003 | `ADD VALUE` is allowed on PG 17, but the new value cannot be used in the same migration. |
| Batch counters are computed on read; `finished = completed >= expectedTotal` | `packages/ocr-persistence/src/index.ts:toBatchSummary`; the UI does the same in `workbench.ts:renderBatch` | With pages, a 1-file batch would show "finished" after its first page. **Must change.** |
| The BATCH_FULL capacity check counts every document in the batch | `index.ts:createUploadedDocument` | Child pages would fill the batch and later uploads would be refused. **Must count top-level files only.** |
| The list is ordered by `created_at DESC, id DESC` | `index.ts:listDocuments` | Pages inserted in one transaction share `created_at`, so they would appear shuffled. **Needs an explicit page order.** |
| The Local AI picks the decoder from the filename extension first | `api.py:ocr` (`Path(filename).suffix`) | A PNG page sent under the parent's name `x.pdf` would be decoded as a PDF and fail with 400. **The name sent must carry an extension that matches the MIME type.** |
| `normalizeStructuredResult` keeps only the three Makkha sections | `document-view.ts:normalizeUnsafe` | A generic result would come back empty on every read. **The view type must become a union.** |
| `_NOISE_TEXT` knows only `ploenchit` | `local-ai/ocr_normalize.py` | Checked by running it: `"ไทย 90 นาที\nSUKHUMVIT 33"` produces a fake treatment `{raw:"SUKHUMVIT 33", value:null, durationMinutes:33, needsReview:true}`. Every SUKHUMVIT 33 page would go to review and the export would carry a false treatment, if the model reads the printed branch name (it does for PLOENCHIT). |
| `limits.maxOcrPagesPerDocument = 50`, and `test/m1-scaffold.test.ts` asserts it | config | Raise it (see 1.4) and update the test. |
| The ingest allowlist accepts DOCX and XLSX; the Local AI refuses them (400 → DEAD) | `packages/ingest/src/index.ts:supportedMimeTypes` | They are silently lost through the API. Refuse with 415 at upload until they are supported. |

## 1. Splitting multi-page PDFs (and multi-frame TIFF)

### 1.1 Where to split

| | A. In the web upload request | **B. In a worker job (recommended)** | C. New Local AI endpoint | D. In the browser (pdf.js) |
|---|---|---|---|---|
| Upload size problem | fixed | fixed | **not fixed**: the whole PDF still crosses the 25 MB nginx | fixed |
| Original PDF kept | yes | yes | yes | no (unless also uploaded) |
| Latency | adds ~40 s of rendering to the HTTP request; complicates replay/resume in `ingestDocument` | none (async) | two network hops | uses client CPU |
| Attack surface | PDF parser inside the public-facing process | isolated child process in the worker (no inbound traffic) | on the AI host, next to Ollama | client |
| New grants | none (`ocr_app` can already insert) | worker INSERT on 3 tables | worker INSERT | none |
| Progress / idempotency | tied to the request | job lease + unique index | fragile | per-file uploads |
| API clients | yes | yes | yes | **no** |

**Recommendation: B.** B is the only option that removes the size problem, keeps the original, stays asynchronous, and keeps untrusted PDF parsing out of the web process. D is essentially the Phase 0 manual workaround in automated form.

### 1.2 Renderer

| Option | Notes | Verdict |
|---|---|---|
| **poppler-utils `pdfinfo` + `pdftoppm` in `deploy/Dockerfile.worker`** (`apt-get install -y --no-install-recommends poppler-utils`, about +15–25 MB) | Run as a subprocess (`execFile`, no shell) with a timeout and `prlimit --as=1G --cpu=120`. Honours `/Rotate`. `-scale-to 1610` gives the same 1610 px long side that `api.py:_render_scale` uses today, so pixels match the validated path. One process can render a range of pages (`-f a -l b`). | **Recommended** |
| Local AI endpoint using pypdfium2 (already installed) | Needs the whole PDF sent across the 25 MB nginx, or an nginx change. Rendering is serialised by `_PDF_LOCK` and competes with Ollama for CPU. | Rejected |
| pdfjs-dist + `@napi-rs/canvas` in Node | New native dependency (~30 MB); font and fidelity problems on scans; runs in-process. | Rejected |
| B2 variant: `pdfseparate` (also poppler) to make 1-page PDFs and let the Local AI render them | Storage is about the original size and fidelity is exact. But a single page can still exceed 25 MB, previews become PDF iframes, and it depends on the Local AI's PDF support. | Keep as a fallback if PNG storage becomes a problem. |

*Correction (review, 2026-09-22):* `-scale-to 1610` does **not** match the validated path for the real scans: it upsamples their ~1400 px images, and even at 1400 px pdftoppm resamples the image by up to a pixel, which cost 3 pages of the A8 checkbox-list target and added unflagged false positives. The worker now renders the CropBox (`-cropbox`), a plain scan page pixel for pixel (`-rx/-ry` from the image size; all 95 real pages came out bit-identical to their JPEG decode), other scans at their own density and other pages at 1610 px (`full-document-batch-spec.md` §9).

**Page format:** PNG, which is lossless compared with the render. It matches the README advice ("PNG, or JPEG ≥ 90") and the deterministic checkbox thresholds. Estimate for an 832×590 pt scan rendered at 1610×1142: about 2–3 MB per page, so roughly 200–300 MB for 95 pages. Provide `OCR_PAGE_FORMAT=png|jpeg` (`-jpeg -jpegopt quality=95`, about 0.5–0.9 MB) as the switch if disk becomes tight. Measure this in the test plan.

### 1.3 Recommended flow

1. Upload: unchanged. The parent document keeps the PDF and has already been scanned by ClamAV.
2. The worker claims the job (`runWorkerOnce`). **The decision is made from the document, not a new job kind:** if `mime_type='application/pdf'`, `parent_document_id IS NULL` and `status IN ('CLEAN','PROCESSING')`, it runs `splitPdf` instead of `processOcrJob`. Because of this, an old web plus a new worker works once 0018 is applied (i.e. after a web rollback; the worker refuses to start before 0018, see §1.9), and **retrying the user's existing FAILED 95-page row splits it**, since `retryDocument` re-queues FAILED documents.
3. `pdfinfo` gives the page count, encryption flag and page sizes. Refuse (parent FAILED with a coded message) if it is encrypted (`PDF_ENCRYPTED`), has 0 pages or more than `OCR_MAX_PDF_PAGES` (`PDF_TOO_MANY_PAGES`), any page is over 14,400 pt (the same rule as `MAX_PDF_PAGE_PT`), or the renderer times out (`PDF_RENDER_FAILED`). Then set the parent's `page_count = N`.
4. Render in chunks of 10 pages into `${OCR_STORAGE_ROOT}/tmp/split-<jobId>/`. This folder is already cleaned by `deploy/cleanup-retention.sh` after one day, and is also removed in a `finally`. For each page: write the file to its deterministic key with `storage.put`. Then, in **one transaction per chunk**, insert the child documents, their runs and their OCR jobs (`ON CONFLICT DO NOTHING`). OCR of page 1 therefore starts about 5 s after the split begins, while rendering continues.
5. After the last chunk, set the parent status to `SPLIT` and finish the job `SUCCEEDED`. The existing 30 s heartbeat keeps the lease; if a heartbeat fails, the split stops.
6. Children are ordinary documents: status `CLEAN`, `mime_type='image/png'`, `filename` equal to the parent's (for display), `batch_id` copied from the parent, and `created_at` set explicitly to the parent's `created_at`. When sending a child to the OCR API, `processOcrJob` uses the name `page-0012.png`, i.e. an extension derived from the MIME type (new helper `ocrUploadName(document)`).
7. Children are not re-scanned by ClamAV: they are our own renders of a file that was already scanned. This is stated explicitly.

### 1.4 Data model and semantics

- **Parent and child.** New columns `documents.parent_document_id`, `page_number` and `page_count`. `page_count` is set on the parent and on every child, so the list can show "page 12/95" without a join. Composite FK `(parent_document_id, organization_id) → documents(id, organization_id)`, so a parent and its pages are always in the same tenant.
- **Parent lifecycle:** SCANNING → CLEAN → PROCESSING ("splitting PDF") → **`SPLIT`** (new enum value) or FAILED. A `SPLIT` parent is left out of the list and the row counters but still counts as a file. A parent whose split FAILED stays visible as a row with a Retry button, so nothing is dropped. Add `statusCategoryOf('SPLIT')` → `split`. The drawer then shows "ไฟล์นี้ถูกแยกเป็น 95 หน้า" with a link that filters to `parentId`.
- **Storage keys.** Keep the existing grammar: child `storage_key = mintOriginalKey(tenant, sha256("page:"+parentId+":"+n).hex.slice(0,32))`. The result is deterministic, so a re-render overwrites the same object. It matches `PUBLIC_ID` and passes the worker's `validatePayload` prefix check unchanged. The content route serves the page image with no changes.
- **Batch counters, i.e. what `expected_total` means.** It stays **the number of files the client promised** (1..500, used for BATCH_FULL). Rows are derived. Changes to `BATCH_SELECT` and `toBatchSummary`:
  - `uploaded` = top-level files (`parent_document_id IS NULL`), the same meaning as today.
  - New `rows` = visible rows (`status <> 'SPLIT'`); `pages` = number of children; `pagesExpected` = sum of parent `page_count`; `splitting` = PDF parents not yet split.
  - queued/processing/succeeded/... count rows. A parent that is still splitting counts as one processing row.
  - `finished = uploaded >= expectedTotal && queued + processing === 0 && lastCompleted !== null`, replacing `completed >= expectedTotal`. The existing 5-minute idle rule stays.
  - The capacity check in `createUploadedDocument` adds `AND d.parent_document_id IS NULL`.
- **Ordering.** `ORDER BY d.created_at DESC, COALESCE(d.parent_document_id, d.id) DESC, d.page_number ASC NULLS FIRST, d.id DESC`. Pages sit together, in page order, at the position of the original upload.
- **Page limit.** `OCR_MAX_PDF_PAGES` defaults to 300 (reuse `limits.maxOcrPagesPerDocument`, raising it from 50 and updating `test/m1-scaffold.test.ts`). The CHECK constraint allows up to 1000. 300 pages at ~25 s each is about 2 hours, which the UI must say.
- **Idempotency.** Upload idempotency is unchanged (the parent carries the key). The split relies on the partial unique index `(organization_id, parent_document_id, page_number)`, deterministic keys, `pg_advisory_xact_lock(hashtext('innovera_ocr:split'), hashtext(parentId))` per chunk, and a child row, its run and its job inserted in the same transaction. A re-run (lost lease, crash, or retry of a FAILED parent) renders only the missing pages.
- **Page render failures.** If page k fails to render, still insert child k with `status='FAILED'`, `storage_key=NULL` and `error_message='PAGE_RENDER_FAILED'`, so every page from 1 to N has a row. When a child's storage object is missing (render failed, or the file was deleted), its OCR job re-renders that page from the parent's PDF before calling the OCR API.
- **Retrying one page.** Uses the existing `retryDocument` on the child: FAILED → CLEAN plus a new `OCR` job on the child's run. No re-split.
- **Page preview.** `GET /api/documents/:childId/content` returns the PNG, and the existing image viewer with zoom works. Add a drawer link "เปิด PDF ต้นฉบับ (หน้า 12)" that fetches the parent's content blob and opens `blobUrl#page=12`. The CSP already allows `frame-src 'self' blob:`.
- **Deletion** (Phase 2, since no delete endpoint exists yet): a soft delete that sets `deleted_at` and `status='DELETED'` (`ocr_app` already has UPDATE). Deleting a parent also soft-deletes its children in the same transaction. Deleting a child removes that page only. Pending jobs of deleted documents end on their own: `getWorkerDocument` filters `deleted_at IS NULL`, returns null, and the job finishes. Storage files are removed only by the retention workflow, as `docs/operations/retention.md` requires.

### 1.5 Upload size limits, end to end

**Confirmed:** once pages are sent as images, the AI-host nginx limit of 25 MB no longer matters for PDFs, because a page PNG is about 1–4 MB. **It still matters for large raw images** (108 MP phone photos, 600 dpi PNG scans).

| Layer | Now | Proposed |
|---|---|---|
| UI `MAX_BYTES` (`workbench.ts`) | 200 MB for every type; XHR `timeout=300000` | PDF 200 MB; images 60 MB; XHR timeout scaled to size (at least 300 s, about 100 KB/s × size) |
| App-host nginx-proxy (vhost) | unknown, at least 45 MB (the upload passed) | **verify**; set to at least the app limit + 1 MB |
| Web `limits.maxUploadBytes` | 200 MB, fully buffered (up to 600 MB of RAM with 3 concurrent uploads) | keep for PDF; add a per-type image limit of 60 MB in `validateUpload`; streaming to disk later |
| ClamAV `StreamMaxLength`/`MaxFileSize`/`MaxScanSize` | unknown, at least 45 MB | **verify** (`clamconf`) and set to at least the app limit. `createClamAvTcpClient` treats "INSTREAM size limit exceeded" as QUARANTINED, which is misleading: map it to a distinct `SCAN_SIZE_LIMIT` FAILED status |
| Worker → Local AI (PDF) | whole PDF | page PNGs of about 1–4 MB |
| AI-host nginx `client_max_body_size` for `/ocr` | 25M | 64M (for raw images only) |
| Local AI `OCR_MAX_UPLOAD_BYTES` | 30 MiB | 64 MiB |
| Ingest allowlist | includes DOCX/XLSX | remove them (415 at upload) until they are supported |

### 1.6 Migration `0018_multipage_documents` (runs as `ocr_migrator`, one transaction, defines no functions)

```sql
-- Multi-page files: one child document per page. Defines no function (queue/outbox functions are owned by ocr_queue_definer).
ALTER TYPE document_status ADD VALUE IF NOT EXISTS 'SPLIT';   -- not referenced again in this migration (unusable in the adding transaction)
ALTER TABLE documents ADD COLUMN IF NOT EXISTS parent_document_id uuid;
ALTER TABLE documents ADD COLUMN IF NOT EXISTS page_number integer;
ALTER TABLE documents ADD COLUMN IF NOT EXISTS page_count integer;
DO $$ BEGIN
  IF NOT EXISTS (SELECT 1 FROM pg_constraint WHERE conname='documents_parent_fk' AND conrelid='documents'::regclass) THEN
    ALTER TABLE documents ADD CONSTRAINT documents_parent_fk
      FOREIGN KEY (parent_document_id, organization_id) REFERENCES documents(id, organization_id);
  END IF;
  IF NOT EXISTS (SELECT 1 FROM pg_constraint WHERE conname='documents_page_shape_chk' AND conrelid='documents'::regclass) THEN
    ALTER TABLE documents ADD CONSTRAINT documents_page_shape_chk CHECK (
      (parent_document_id IS NULL) = (page_number IS NULL)
      AND (page_number IS NULL OR page_number BETWEEN 1 AND 1000)
      AND (page_count  IS NULL OR page_count  BETWEEN 1 AND 1000));
  END IF;
END $$;
CREATE UNIQUE INDEX IF NOT EXISTS documents_parent_page_uidx
  ON documents(organization_id, parent_document_id, page_number) WHERE parent_document_id IS NOT NULL;

-- The worker creates page documents, their runs and their OCR jobs under the same tenant RLS as ocr_app (mirrors 0016).
-- No SELECT on extraction_jobs: its job INSERT has no RETURNING / ON CONFLICT, and RLS WITH CHECK needs no column grant.
GRANT INSERT ON documents, document_runs TO ocr_worker;
GRANT INSERT ON extraction_jobs TO ocr_worker;
```

*Correction (review, 2026-09-22):* an earlier draft also granted `SELECT (id, organization_id, run_id) ON extraction_jobs` "for INSERT … RETURNING". The worker's job INSERT has no RETURNING, so that grant only let `ocr_worker` list every job of any tenant it sets in `app.current_org`; it was removed before 0018 ran anywhere.

- The existing grants already cover the FK checks: `REFERENCES` on documents and document_runs (0013) and on ocr_batches (0017) for `ocr_worker`. The worker inserts inside `tenantTransaction` with `app.current_org` set, so the RLS `USING` clause acts as `WITH CHECK` and a row for another tenant is rejected.
- **Grant alternative G2 (tighter, more work):** a SECURITY DEFINER function `ocr_create_page_document_v1(parent uuid, page int, key text, size bigint, hash text, priority int)` owned by `ocr_migrator`. That works because FORCE RLS still applies with the caller's `app.current_org`. The worker would get only EXECUTE. **Not recommended:** the worker already runs across tenants (it sets `app.current_org` itself and has UPDATE on every document), so table INSERT adds little real risk. G1 follows the existing 0016 pattern and adds no new function to own.
- Add to `deploy/verify-db-roles.sh`: `worker:insert-documents=1`, `worker:insert-extraction-jobs=1`, `worker:no-update-extraction-jobs=0`, `worker:no-select-extraction-jobs=0` (`has_any_column_privilege`), `worker:no-delete-documents=0`, `queue:no-table-select` unchanged.
- Add `test/multipage-migration.test.ts`: no `FUNCTION` or `SECURITY DEFINER`; exactly these two GRANT statements; no `ocr_queue`; no `DROP`; `SPLIT` appears only in the `ADD VALUE` line.

### 1.9 Failure modes

| Failure | Mitigation |
|---|---|
| New worker starts before the web has run 0018 | Deploy the web first; it migrates at startup. *Corrected:* without a guard every claimed job — images too, not only splits — fails in `getWorkerDocument` with 42703 (`parent_document_id` does not exist) and ends DEAD after 3 attempts. The worker therefore checks `schema_migrations` for `0018_multipage_documents` at startup and exits (`SCHEMA_NOT_READY`, Docker restarts it) until the web has migrated; no job is claimed before. |
| Old web reads a `SPLIT` parent (`statusCategoryOf` → null → shown as "failed") | Deploy order web → worker. A web rollback leaves only cosmetic leftovers; 0018 is additive. *Corrected for a worker rollback:* page rows carry their parent's name (`x.pdf`) with an image MIME type, and a pre-Release-1 worker sends them under that name; the Local AI v3.1 (deployed first) decodes a `*.pdf`-named image by its bytes, so queued page jobs still succeed. |
| Old worker still running while the new web is live | It would read a small multi-page PDF uploaded in that window page 1 only, and that row can never be split later. Stop the old worker before deploying the web; jobs wait in PENDING. |
| Child sent as `x.pdf` → Local AI 400 | `ocrUploadName`, plus a unit test. |
| Children fill the batch → BATCH_FULL; batch "finished" after the first page | Capacity counts top-level files; new `finished` rule; the UI uses the server's `finished`. |
| Split crashes halfway | Unique index, deterministic keys and per-parent lock allow an idempotent resume; the tmp folder is cleaned. |
| PDF bomb (huge page count or page size, deep object graphs) | `pdfinfo` checks first; timeout and memory limit on every subprocess; page and size caps; parent FAILED with a code, retry allowed. *Added in review:* a time budget per split (`limits.jobProcessingBudgetMs`, 30 min; every render call gets at most the time left) — a small PDF whose every page renders just under the 120 s limit could otherwise hold a job loop for hours. |
| Encrypted or corrupt PDF | Parent FAILED `PDF_ENCRYPTED` / `PDF_RENDER_FAILED` with Thai text; the row stays visible. |
| Disk fills up (≈1.4 MB × pages for the real scans) | Measure; the retention workflow. A full scratch disk (pdftoppm exits 0 with a cut-off file) or a vanished source is a retryable `PDF_RENDERER_UNAVAILABLE`, never per-page FAILED rows. (`OCR_PAGE_FORMAT=jpeg` did not meet A8 on the real scans: unvalidated.) The Local AI also keeps each page in `/opt/innovera-ocr/uploads` (an existing retention issue). |
| Worker stops mid-split (`STOP_TIMEOUT_MS` 8 s) | The lease expires, the job is recovered, and the split resumes idempotently. |

## 2. Format detection and robustness

### 2.1 Options

| Concern | Options | Recommendation |
|---|---|---|
| Is this the Makkha form? | **D1: grid score**, extending `ocr_marks.register` (ring contrast plus the share of printed checkbox squares found); D2: ORB + RANSAC homography against a blank reference image (inlier ratio); D3: ask the model to classify (+25 s per page) | **D1**, computed after geometric normalisation. D2 as a fallback once blank reference forms exist for each version (none are in the repo, and the real fixture must not leave it). D3 rejected. |
| Where to normalise | **N1: in the Local AI** (Pillow, numpy and cv2 4.10 are present); N2: in the worker (would need new native Node dependencies); N3: manual rotate/crop in the UI | **N1**. N3 later as an escape hatch ("หมุนแล้วอ่านใหม่"). |
| Unknown documents | **G1: Typhoon full-page native transcription + deterministic key-value parse**; G2: store the image only and send it to review (breaks "must still be read"); G3: a second general LLM for key-value extraction (too slow on CPU, another model to run) | **G1** |
| Branch or version variants | **V1: same geometry, branch list in `master_data.json`**; V2: a template registry (several calibrated coordinate sets, best score wins); V3: an uncalibrated version goes to the generic path | V1 for SUKHUMVIT 33 if the geometry matches (832×590 pt has aspect 1.410 against the template's 1.415, within `ASPECT_TOLERANCE`). V2 and V3 for truly new layouts. |

### 2.2 Recommended pipeline (new `local-ai/ocr_detect.py`, called at the start of `api.py:process_image`)

1. `ImageOps.exif_transpose` (already done).
2. **Perspective (phone photos), only when cv2 is available:** downscale to about 800 px, blur, Canny, dilate, `findContours`, `approxPolyDP` (2% of the perimeter); take the largest convex 4-point shape covering more than 25% of the frame; order the corners; `warpPerspective` to 1610×1138 (twice 805×569). If no shape is found, keep the image and flag it.
3. **Orientation:** candidates come from the aspect ratio (landscape → 0/180; portrait → 90/270; near-square → all four). Each candidate is resized to 805×569, run through `border_darkness` + `register`, and scored. Keep the best.
4. **Deskew:** `HoughLinesP` on the printed rules; take the median angle of near-horizontal segments longer than 15% of the width. If 0.3° < |angle| ≤ 10°, rotate (`warpAffine`, white border; `Image.rotate` if cv2 is missing). Then register and score again.
5. **Template score:** `score = 0.5·min(1, contrast/30) + 0.5·hitRatio`, where `hitRatio` is the share of all 45 `CHECKBOXES` squares whose ring contrast at the registered shift is at least 10. Starting thresholds, **to be calibrated on real pages on the Local AI host**:
   - known if score ≥ 0.6;
   - uncertain between 0.35 and 0.6, which runs the **hybrid**: template extraction plus full-page transcription, with needsReview;
   - unknown below 0.35, which runs the generic path.
6. Response additions: `layout.detection = {score, contrast, hitRatio, orientation, skewDeg, perspective, method}`, `layout.template` (`makkha-intake-v1` or `unknown`), `layout.branch`, `version: "3.1"`, and `/health` gains `cvSupport` and `genericMode`.

### 2.3 Generic path (`local-ai/ocr_generic.py`; `GENERIC_PROMPT` in `ocr_model.py`)

- One call with Typhoon OCR 1.5's **native** full-page prompt, copied verbatim from the `typhoon-ocr` package (`v1.5` prompt: markdown, HTML tables, ☐/☑ for checkboxes). `docs/architecture/m0/d-ocr-engine.md` notes that the v1 models fail with custom prompts. Settings: `max_tokens` 2048 (fits the `n_ctx_slot` of 4096), temperature 0. A/B-test the prompt's `<figure>` description instruction, which spends tokens describing images in Thai.
- Deterministic parse with no second model call:
  - `Label: value` lines (ASCII and full-width colons);
  - two-column tables become pairs; wider tables become `tables[]`;
  - `☑ label` lines become `checkboxes[]`.
- Stored result `schemaVersion "generic-1"`, always `needsReview: true` (every value shows `needsReview:true`; generic results are never auto-confirmed):

```jsonc
{ "schemaVersion": "generic-1", "documentType": "unknown",          // or a keyword hint, e.g. "makkha-unknown-version"
  "detection": { "template": null, "score": 0.12, "orientation": 90, "skewDeg": 1.4, "perspective": true },
  "text": { "markdown": "…", "chars": 1834, "truncated": false },
  "keyValues": [ { "key": "Name", "value": "Chun", "raw": "Name: Chun", "confidence": null, "source": "ocr", "needsReview": true } ],
  "tables": [ { "rows": [["…","…"]] } ],
  "checkboxes": [ { "label": "Female", "checked": true, "raw": "☑ Female", "needsReview": true } ] }
```

- The Local AI returns it under `response.generic`. Nothing is lost even before the app understands it, because `raw_response` stores the whole response.
- **Prompt injection:** Typhoon has no guardrails (see the engine doc). Its output is stored as data and rendered only via `textContent`; nothing executes it. The residual risk is a wrong transcription, which review catches.

### 2.6 Failure modes

| Failure | Mitigation |
|---|---|
| Thresholds wrong for other branches or photos | Calibrate on the 95 real pages plus the 16 earlier ones on the Local AI host (data never leaves). Log `layout.detection` for monitoring. |
| cv2 missing in some image | Pillow-only fallback (orientation and deskew via `Image.rotate`); `cvSupport:false` in `/health`. |
| Wrong perspective quad (for example a table edge) | Accept a warp only if the score improves over the unwarped image; otherwise keep the original and flag it. |
| Generic output hits `max_tokens` | `text.truncated:true` plus needsReview; the page image is always kept. |
| Generic call exceeds the worker's `OCR_REQUEST_TIMEOUT` (120 s by default) and the client retries, stacking duplicate work in Ollama (FastAPI does not cancel the thread) | Raise `OCR_REQUEST_TIMEOUT` to 600–900 s before enabling the generic path; set `OCR_MODEL_TIMEOUT` to match; see §4.4. |
| App deployed older than the Local AI | No loss: `raw_response` keeps `generic`. Deploy the app first anyway. |
| New-version Makkha form wrongly classified as known | The hybrid band keeps the full-page text; the review queue catches it. |

## 3. Export

### 3.1 Format options

| Option | Dependencies | Verdict |
|---|---|---|
| **CSV, UTF-8 with BOM**, CRLF, RFC 4180 quoting | none | **Phase 2.** Excel on Windows and macOS opens Thai correctly with the BOM. |

### 3.2 Columns (one row per page or document; headers Thai by default, `?headers=en` gives snake_case)

- **Identity and status:** `document_id, batch_id, batch_label, file_name, page_number, page_count, parent_document_id, status_code, status (Thai label), needs_review (TRUE/FALSE), review_fields (flagged paths joined with "; "), min_confidence (number 0–1), reviewed (TRUE/FALSE), reviewed_at, reviewed_by, delivery_status, created_at, processed_at, template, branch, result_type (makkha-v3|generic-1), error_message, review_url`.
- **Customer:** `name, gender, nationality, hotel_name, referral_sources, health_conditions`. Checkbox lists are joined with "; ".
- **Recommendation card:** `pressure, massage_oil_scrub, preferred_areas, avoid_areas`.
- **Staff:** `treatments` (all of them, for example "นวดไทย 90 นาที; นวดหน้า 60 นาที"), `treatment_1_name/_duration/_minutes` … `treatment_4_*`, `treatments_more` (items 5 and up, joined), `total_minutes`, `therapist, room`.
- **Generic:** `generic_fields` ("key: value" lines), `generic_text`.
- **Detailed column set** (`columns=detailed`): per scalar field, `_raw, _confidence, _needs_review, _source`.

Cell rules:
- A compact cell shows `value`. If `value` is null but `raw` exists, it shows `raw + " (?)"`, so no data is dropped. Items still flagged for review get the " (?)" suffix.
- Times are Asia/Bangkok `YYYY-MM-DD HH:MM:SS`, which Excel can parse; JSONL keeps ISO UTC.
- Any text cell longer than 32,000 characters is truncated with "…[ตัดทอน]" (Excel's cell limit is 32,767).
- `review_url` is built from a configured `OCR_PUBLIC_BASE_URL`, never from the Host header.
- **CSV formula injection:** a text cell that starts with `= + - @ \t \r` gets a leading `'`. Numeric columns are emitted as numbers.

### 3.3 Filters, streaming, tenant scoping

- **Filters:**
  - `batchId`, `status` (several categories allowed), `confirmedOnly`, `template`, `q`;
  - `from`/`to` as `YYYY-MM-DD` in Asia/Bangkok, applied to `created_at` (or `dateField=reviewed_at`);
  - `SPLIT` parents and deleted documents are always excluded.
- **Streaming with no new dependency:**
  - `PostgresOcrDocumentStore.exportDocuments(tenantId, filters)` is an async generator using keyset pages of 500 rows on `(created_at, group, page_number, id)`. It runs inside one `tenantTransaction` opened as `REPEATABLE READ READ ONLY`, which gives one consistent snapshot, RLS through `app.current_org`, and the tenant only ever from the verified token.
  - The CSV encoder writes each chunk and waits for `drain` when a write returns false, so memory stays bounded.
  - A `count(*)` runs first; above `OCR_EXPORT_MAX_ROWS` (50,000) the request gets 400 `EXPORT_TOO_LARGE`.
  - At most 2 exports run at once per process (each holds a pooled connection); beyond that, 429 `EXPORT_BUSY`, with 429 added to `errorStatus`.
- **No new grants:** `ocr_app` can already SELECT documents, ocr_batches, ocr_corrections and ocr_confirm_outbox.

### 3.4 API, UI and files

- **Routes:**
  - `GET /api/exports/documents.csv` and `GET /api/exports/documents.jsonl` with the filters above, returning `Content-Disposition: attachment; filename="ocr-export-YYYYMMDD-HHMM.csv"`;
  - `GET /api/exports/preview` returning `{columns, total, rows (first 20)}`;
  - add these paths to `routeLabel`;
  - log an `export_completed` audit event with tenant, user, filters and row count.
- **Files:**
  - `packages/ocr-persistence/src/export.ts` (new, pure): `EXPORT_COLUMNS`, `flattenDocument(row, set)`;
  - `index.ts:exportDocuments`;
  - `apps/ocr-web/src/export.ts` (new): `csvCell`, `csvRow`, `streamCsv`;
  - `server.ts`: the routes.
- **UI** (`workbench.ts`): an "ส่งออก" secondary pill in the toolbar opens a `<dialog>`. It is pre-filled from the current filters (status, batch, search) and adds a date range, "เฉพาะที่ยืนยันแล้ว", a column set (สรุป/ละเอียด) and a format (Excel CSV / JSONL). It shows the **export table**, i.e. the preview of the first 20 rows in the real export columns, plus the row count. A black "ดาวน์โหลด" pill fetches with the Bearer token, turns the response into a Blob and triggers `a[download]`. The token stays in memory, and the CSP (`connect-src 'self'`) needs no change. Later: an HMAC-signed short-lived download URL so very large files stream straight to disk.

### 3.5 Failure modes and security

- **Blocker:** `/api/web-token` gives a tenant token to every visitor (report §8). With export, anyone can download every customer's health data in one click. **Put Basic Auth, an IP allowlist or a real login in front before this ships**, or at minimum hide export behind `OCR_EXPORT_ENABLED` plus a separate secret.
- Holding a pool connection for a long time: the concurrency cap plus a statement timeout.
- Excel corrupting leading zeros in room numbers: keep them as text (no numeric coercion). Document that `="…"` is not used.
- Values containing newlines: quoted, which is valid CSV.

- CSV encoder: BOM exactly once; quotes, commas and CR/LF; Thai; formula prefix; 32,000-character truncation.
- Flattening: v3, legacy v2.2 and generic rows; more than 4 treatments; joined lists; the raw fallback marker.

## 4. Throughput and UX for large files

### 4.1 Priority

| Option | Needs | Verdict |
|---|---|---|
| **P1: fair-share priority set when the job is inserted.** Each upload group interleaves: PDF pages get `100 + (page_number-1)`; the k-th image in a batch gets `100 + k` (k is already counted under the batch lock in `createUploadedDocument`); a single upload and a manual `retryDocument` get 100; capped at 10,000. | Nothing new (INSERT rights exist; `ocr_claim_v1` already orders by priority; retry and recovery keep priority) | **Phase 1** |
| P2: separate lanes (per-kind claim) | A new claim function owned by `ocr_queue_definer` | Rejected for now |
| P3: a manual "อ่านก่อน" button that changes priority later | `GRANT SELECT (status), UPDATE (priority) ON extraction_jobs TO ocr_app` (RLS-scoped) | Phase 4 |

Effect: a single upload arriving during the 95-page run waits at most for the jobs already in flight (worker concurrency 2, so up to about 50 s) plus its own 25 s, i.e. under about 75 s. Two large batches share the slot about 1:1.

### 4.2 Progress, ordering and ETA

- Page rows update through the existing polling (every 3 s while work is active). Pages are processed in page order.
- The batch strip shows "หน้า 37/95", and while splitting, "กำลังแยกหน้า 30/95".
- **ETA:** the server computes `etaSeconds` in `getBatch` as remaining rows × the median duration of the tenant's last 20 completions (from `processed_at`), shown as "เหลือประมาณ 24 นาที".
- **Queue position** (Phase 2): needs `GRANT SELECT (status, priority, available_at) ON extraction_jobs TO ocr_app`. Read-only, column-level and tenant-scoped by RLS; `deploy/verify-db-roles.sh` should check that `ocr_app` still cannot UPDATE `extraction_jobs`.

### 4.3 Cancellation

| Option | Needs | Verdict |
|---|---|---|
| **C1: lazy cancel through the document status.** The web sets `status='CANCELLED'` on CLEAN rows (by batch, parent or document; `ocr_app` has UPDATE). The worker claims the document with `UPDATE … SET status='PROCESSING' WHERE status IN ('CLEAN','PROCESSING') RETURNING`; zero rows means `finishDetailed(…, 'CANCELLED')`, about 5 ms per job and no model call. `saveOcrResult` only writes while the document is `PROCESSING`. | Enum `CANCELLED`; `FinishOutcome`/`FINAL_STATUSES` gain `CANCELLED`. `ocr_finish_retry_v1` already accepts it. | **Phase 2** |
| C2: a definer function that cancels PENDING jobs | A new function owned by `ocr_queue_definer` | Rejected |
| C3: `GRANT UPDATE (status)` on `extraction_jobs` | Column grant | Unnecessary |

**Resume** ("อ่านต่อ"): `retryDocument` also accepts CANCELLED. If a PENDING job for that run still exists (checked through the §4.2 column grant), it only sets CLEAN, so no duplicate job is created. Otherwise it inserts a new job. A job already in flight finishes and its result is discarded.

**Migration `0019_cancel_queue_visibility`:**
```sql
ALTER TYPE document_status ADD VALUE IF NOT EXISTS 'CANCELLED';
GRANT SELECT (status, priority, available_at) ON extraction_jobs TO ocr_app;
```
Code impact:
- persistence: `statusCategoryOf`, `CATEGORY_SQL` and `BATCH_SELECT` treat `cancelled` as a terminal state;
- server: `POST /api/documents/:id/cancel`, `POST /api/batches/:id/cancel`, `DELETE /api/documents/:id`;
- UI: a "หยุดอ่านส่วนที่เหลือ" button on the batch strip and a `cancelled` status badge.

### 4.4 Timeouts (set now)

`OCR_REQUEST_TIMEOUT` defaults to 120 s. With 2 loops sharing one Ollama slot plus a fallback call, the worst case today is already about 100 s. Set it to **300 s now**, and to **600–900 s** before the generic path is enabled (the config schema allows up to 900). Otherwise timeouts trip the OCR gate, and `OcrClient` retries resubmit work that the Local AI keeps running.
